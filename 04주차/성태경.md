# 8장. AI 프로젝트

## Q100. LLM의 응답 지연 문제를 사용자 경험 측면에서 어떻게 해결할 수 있나요?

### 면접 답변

LLM의 응답 지연은 완전히 제거하기 어려우므로, 프런트엔드에서는 실제 대기 시간을 줄이는 방법과 사용자가 느끼는 대기 시간을 줄이는 방법을 함께 적용해야 합니다. 먼저 요청을 전송한 직후 사용자 메시지를 화면에 표시하고, 첫 토큰이 도착하기 전에는 생성 준비 상태를 보여 줍니다. 응답이 시작되면 전체 답변을 기다리지 않고 스트리밍으로 받은 내용을 점진적으로 렌더링하여 시스템이 정상적으로 동작하고 있음을 전달합니다.

이 과정은 `대기`, `스트리밍`, `완료`, `실패`, `중단`처럼 명확한 상태로 관리하는 것이 좋습니다. 사용자가 생성을 중단할 수 있도록 `AbortController`를 제공하고, 실패한 요청에는 재시도 수단을 제공합니다. 자동 스크롤은 사용자가 화면 하단을 보고 있을 때만 유지하고, 이전 내용을 읽기 위해 위로 이동했다면 중단하여 사용자의 의도를 방해하지 않아야 합니다.

또한 작은 데이터 조각이 도착할 때마다 화면을 다시 그리면 오히려 성능이 저하될 수 있으므로, 여러 청크를 짧은 주기로 묶어 렌더링해야 합니다. 결국 핵심은 단순한 로딩 아이콘이 아니라 즉각적인 상태 피드백, 점진적인 결과 표시, 사용자 제어권, 안정적인 오류 처리를 함께 설계하는 것입니다.

### 핵심 개념

#### LLM 응답 지연을 나누어 보기

- **전체 응답 시간**: 요청을 전송한 시점부터 답변 생성이 모두 끝날 때까지의 시간
- **TTFT(Time To First Token)**: 요청 전송부터 첫 번째 토큰 또는 첫 번째 응답 조각을 받기까지의 시간
- **토큰 간 지연**: 첫 응답 이후 다음 토큰이나 청크가 도착할 때까지의 간격
- **네트워크 지연**: 사용자와 서버 사이에서 요청과 응답이 이동하는 데 걸리는 시간
- **모델 처리 시간**: 프롬프트 처리, 검색, 추론과 답변 생성에 걸리는 시간
- **렌더링 비용**: 수신한 데이터를 브라우저가 화면에 반영하는 데 필요한 시간

사용자가 특히 불안함을 느끼는 구간은 아무런 결과도 보이지 않는 TTFT 구간입니다. 따라서 전체 처리 시간을 줄이지 못하더라도 요청이 접수되었다는 신호를 즉시 제공하고, 첫 데이터가 도착한 뒤에는 결과를 점진적으로 보여 주면 체감 지연을 낮출 수 있습니다.

> 스트리밍은 모델의 계산 자체를 빠르게 만드는 기술이 아니라, 생성된 결과를 먼저 전달하여 사용자가 기다림을 다르게 경험하도록 만드는 방법

#### 응답 상태 모델링

LLM 인터페이스를 하나의 `isLoading` 값만으로 관리하면 첫 토큰을 기다리는 상태와 이미 답변을 받고 있는 상태를 구분하기 어렵습니다. 다음과 같이 상태를 나누면 각 단계에 알맞은 UI와 예외 처리를 설계하기 쉽습니다.

| 상태 | 의미 | 대표 UI |
| --- | --- | --- |
| **`idle`** | 요청 전 또는 모든 작업 종료 | 입력창과 전송 버튼 |
| **`submitting`** | 질문 전송과 요청 준비 중 | 사용자 메시지 즉시 표시, 전송 버튼 비활성화 |
| **`waiting`** | 요청은 전송됐지만 첫 응답은 아직 도착하지 않음 | 타이핑 인디케이터, 생성 준비 메시지 |
| **`streaming`** | 응답 청크를 받고 있는 중 | 점진적으로 늘어나는 답변, 중단 버튼 |
| **`completed`** | 스트림을 모두 읽고 답변 생성 완료 | 완성된 답변, 복사·피드백 버튼 |
| **`failed`** | 네트워크 또는 서버 오류 발생 | 오류 원인과 재시도 버튼 |
| **`aborted`** | 사용자가 생성을 중단 | 중단된 답변 표시, 다시 생성 버튼 |

- **상태 전이의 명시성**: 가능한 이동 경로와 각 상태에서 허용할 동작을 분명하게 정의
- **중복 요청 방지**: 진행 중 연속 제출을 막거나 기존 요청을 취소한 뒤 새 요청 실행
- **경쟁 상태 방지**: 늦게 끝난 이전 요청이 최신 답변을 덮어쓰지 않도록 요청 식별자 확인
- **부분 결과 보존**: 스트리밍 도중 실패하거나 중단된 답변을 무조건 삭제하지 않고 상태와 함께 보존

```text
idle
  └─ 질문 전송 → submitting → waiting
                              ├─ 첫 청크 도착 → streaming → completed
                              ├─ 오류 ────────────────→ failed
                              └─ 사용자 중단 ─────────→ aborted
```

#### TTFT 동안의 피드백

- **즉시 반영되는 사용자 메시지**: 서버 응답을 기다리지 않고 질문을 대화 목록에 먼저 추가
- **타이핑 인디케이터**: 모델이 응답을 준비 중임을 알리는 움직임 또는 상태 문구
- **스켈레톤 UI**: 답변의 구조가 어느 정도 예측될 때 사용할 자리 표시자
- **취소 버튼**: 사용자가 잘못된 질문을 보냈거나 기다리지 않기로 했을 때 요청을 종료할 수 있는 제어 장치
- **정직한 진행 표현**: 진행률을 정확히 계산할 수 없다면 임의의 백분율 대신 불확정 상태 표시 사용

낙관적 UI는 성공할 것이라고 가정하고 사용자 메시지를 먼저 표시하는 데 적합합니다. 다만 아직 생성되지 않은 AI 답변을 미리 만들어 보여 주는 방식은 결과의 신뢰성을 해칠 수 있으므로, 질문과 요청 상태까지만 낙관적으로 반영해야 합니다.

#### 스트리밍 응답

- **점진적 전달**: 완성된 응답 하나를 기다리지 않고 생성된 데이터 조각을 순차적으로 전달
- **Fetch 스트리밍**: `Response.body`의 `ReadableStream`을 읽어 POST 요청의 응답도 점진적으로 처리 가능
- **SSE(Server-Sent Events)**: 서버에서 클라이언트로 이벤트를 지속적으로 전송하는 `text/event-stream` 기반 방식
- **단방향 통신**: 일반적인 LLM 응답처럼 서버에서 브라우저로 계속 데이터를 보내는 흐름에 적합
- **청크와 토큰의 차이**: 네트워크 청크 하나가 모델 토큰 하나와 정확히 일치한다는 보장 없음
- **메시지 경계 처리**: SSE나 NDJSON을 사용할 경우 청크가 프로토콜 메시지 중간에서 나뉠 수 있으므로 버퍼를 두고 완전한 메시지만 파싱

`EventSource`는 재연결과 이벤트 파싱을 기본 제공하지만 일반적으로 GET 요청 중심이며 임의의 요청 본문이나 헤더를 다루기 어렵습니다. 질문을 POST 본문으로 보내야 하는 채팅 API에서는 `fetch()`와 `ReadableStream`을 함께 사용하는 방식이 유연합니다.

다음은 서버가 UTF-8 일반 텍스트를 청크 단위로 반환한다는 가정의 간단한 예제입니다.

```javascript
async function streamAnswer(question, { signal, onStatus, onChunk }) {
  onStatus("waiting");

  const response = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question }),
    signal,
  });

  if (!response.ok) {
    throw new Error(`요청 실패: ${response.status}`);
  }

  if (!response.body) {
    throw new Error("이 환경에서는 스트리밍 응답을 읽을 수 없습니다.");
  }

  const reader = response.body
    .pipeThrough(new TextDecoderStream())
    .getReader();
  let isFirstChunk = true;

  try {
    while (true) {
      const { value, done } = await reader.read();

      if (done) break;

      if (isFirstChunk) {
        isFirstChunk = false;
        onStatus("streaming");
      }

      onChunk(value);
    }

    onStatus("completed");
  } finally {
    reader.releaseLock();
  }
}
```

- **`response.body`**: 응답 본문을 `ReadableStream`으로 노출
- **`TextDecoderStream`**: 여러 바이트 청크에 걸쳐 나뉠 수 있는 UTF-8 문자열을 안전하게 디코딩
- **`reader.read()`**: 다음 데이터가 준비될 때 `{ value, done }` 형태의 결과 반환
- **`done`**: 스트림에서 더 읽을 데이터가 없는 상태
- **`finally`**: 정상 완료, 오류, 중단 여부와 관계없이 reader의 잠금 해제

> 실제 API가 SSE 형식을 반환한다면 디코딩된 문자열을 그대로 답변에 붙이지 않고 빈 줄을 기준으로 이벤트를 분리한 뒤 `data:` 필드를 파싱하는 단계 필요

#### 사용자에게 중단 권한 제공하기

`AbortController`의 `signal`을 `fetch()`에 전달하면 사용자가 요청을 중단할 수 있습니다. 중단은 실패와 다른 정상적인 사용자 행동이므로 `AbortError`를 일반 오류 메시지로 보여 주지 않고 별도의 상태로 처리하는 것이 좋습니다.

```javascript
const controller = new AbortController();

streamAnswer(question, {
  signal: controller.signal,
  onStatus: setStatus,
  onChunk: appendAnswer,
}).catch((error) => {
  if (error.name === "AbortError") {
    setStatus("aborted");
    return;
  }

  setStatus("failed");
  showRetryButton();
});

stopButton.addEventListener("click", () => {
  controller.abort();
});
```

- **중단과 실패 구분**: 사용자가 의도적으로 취소한 경우 불필요한 오류 알림 제외
- **부분 답변 표시**: 중단 시점까지 받은 내용을 유지하고 `생성이 중단된 답변`임을 표시
- **재요청 기준 명확화**: 전체 재생성, 이어서 생성, 동일 질문 재시도 가운데 가능한 동작을 구분
- **리소스 정리**: 컴포넌트가 사라지거나 새 요청이 시작될 때 이전 스트림 취소
- **서버 작업 종료 고려**: 브라우저 요청 중단만으로 서버의 모델 생성까지 반드시 중단되는 것은 아니므로 서버 측 취소 전파 설계 필요

#### 렌더링 빈도 제어

스트림의 청크마다 상태를 갱신하면 짧은 시간에 많은 렌더링과 레이아웃 계산이 발생할 수 있습니다. 도착한 문자열을 버퍼에 모았다가 프레임 단위 또는 짧은 시간 간격으로 화면에 반영하면 답변은 자연스럽게 보이면서 렌더링 부담을 줄일 수 있습니다.

```javascript
let pendingText = "";
let frameId = null;

function enqueueChunk(chunk) {
  pendingText += chunk;

  if (frameId !== null) return;

  frameId = requestAnimationFrame(() => {
    appendAnswer(pendingText);
    pendingText = "";
    frameId = null;
  });
}
```

- **버퍼링**: 짧은 시간에 도착한 여러 청크를 한 번의 화면 갱신으로 반영
- **프레임 단위 갱신**: `requestAnimationFrame()`을 이용해 브라우저의 다음 페인트 시점에 맞춰 업데이트
- **누적 문자열 비용 고려**: 매우 긴 답변은 매번 전체 문자열을 새로 만들거나 전체 Markdown을 다시 파싱하지 않도록 최적화
- **측정 우선**: 청크 빈도와 프레임 드롭을 Performance 패널과 실제 기기에서 확인한 뒤 배치 크기 결정

#### 사용자 의도를 존중하는 자동 스크롤

새 텍스트가 추가될 때 항상 맨 아래로 이동시키면 사용자가 이전 내용을 읽기 위해 위로 스크롤해도 화면이 다시 끌려 내려옵니다. 따라서 사용자가 현재 하단 근처에 있을 때만 새 내용을 따라가도록 해야 합니다.

```javascript
const BOTTOM_THRESHOLD = 48;
let shouldFollowLatest = true;

function isNearBottom(element) {
  const remaining =
    element.scrollHeight - element.scrollTop - element.clientHeight;

  return remaining <= BOTTOM_THRESHOLD;
}

chatContainer.addEventListener("scroll", () => {
  shouldFollowLatest = isNearBottom(chatContainer);
  jumpToLatestButton.hidden = shouldFollowLatest;
});

function followLatestIfNeeded() {
  if (!shouldFollowLatest) return;

  chatContainer.scrollTo({
    top: chatContainer.scrollHeight,
    behavior: "smooth",
  });
}

jumpToLatestButton.addEventListener("click", () => {
  shouldFollowLatest = true;
  followLatestIfNeeded();
});
```

- **하단 임곗값**: 스크롤 위치가 정확히 일치하지 않아도 하단에 가까우면 최신 응답 추적
- **사용자 스크롤 우선**: 사용자가 위로 이동한 순간 자동 추적 중지
- **새 응답 안내**: 자동 추적이 멈춘 동안 `최신 답변으로 이동` 버튼이나 새 내용 표시 제공
- **추적 재개**: 사용자가 다시 하단으로 이동하거나 버튼을 누르면 자동 스크롤 재활성화
- **과도한 부드러운 스크롤 방지**: 청크마다 `smooth` 애니메이션을 다시 시작하지 않도록 갱신 빈도 조절

#### 실패와 재시도 설계

- **오류 유형 구분**: 네트워크 단절, 인증 실패, 사용량 제한, 서버 오류, 파싱 오류를 가능한 범위에서 구분
- **행동 가능한 메시지**: `오류가 발생했습니다`보다 재시도 가능 여부와 사용자가 취할 행동을 함께 안내
- **부분 응답 표시**: 이미 받은 답변과 `응답이 중단됨` 상태를 함께 표시
- **재시도 버튼**: 질문을 다시 입력하지 않아도 같은 요청을 실행할 수 있는 수단
- **중복 생성 방지**: 재시도 시 이전 요청의 응답이 뒤늦게 도착해 최신 상태를 덮지 않도록 요청 ID 확인
- **입력 내용 보존**: 실패 후에도 사용자가 작성한 프롬프트와 첨부 정보 유지

#### 접근성 고려

- **상태 메시지 제공**: `role="status"`를 사용해 `답변을 준비하고 있습니다`, `답변 생성이 완료되었습니다` 같은 상태 전달
- **진행 영역 표시**: 응답을 생성하는 동안 관련 영역에 `aria-busy="true"` 적용
- **과도한 알림 방지**: 토큰이나 청크마다 라이브 리전을 갱신하여 스크린 리더가 계속 발화를 중단하지 않도록 설계
- **완료 시점 안내**: 스트리밍되는 본문과 별개로 완료 또는 실패 상태를 간결하게 알림
- **키보드 조작**: 중단, 재시도, 최신 답변 이동 기능을 키보드로 실행 가능하게 구성
- **포커스 유지**: 응답이 시작되거나 새 청크가 추가될 때 사용자의 현재 포커스를 강제로 이동하지 않음

```html
<section aria-busy="true" aria-labelledby="answer-title">
  <h2 id="answer-title">AI 답변</h2>
  <div id="answer"></div>
</section>

<p role="status">답변을 생성하고 있습니다.</p>
<button type="button">생성 중단</button>
```

> 참고: [MDN - 읽기 가능한 스트림 사용하기](https://developer.mozilla.org/ko/docs/Web/API/Streams_API/Using_readable_streams), [MDN - `AbortController`](https://developer.mozilla.org/ko/docs/Web/API/AbortController), [MDN - `Element.scrollHeight`](https://developer.mozilla.org/ko/docs/Web/API/Element/scrollHeight), [MDN - `Element.scrollTop`](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollTop), [WHATWG HTML - Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html), [W3C - 상태 메시지 이해하기](https://www.w3.org/WAI/WCAG21/Understanding/status-messages)

### 모의 면접

**1. 스트리밍 응답 중 사용자가 위로 스크롤했을 때, 자동 스크롤을 계속 유지해야 할까요? 그렇게 생각하는 이유는 무엇인가요?**

계속 유지하면 안 됩니다. 사용자가 위로 스크롤한 것은 이전 내용을 읽겠다는 명시적인 의도인데, 새 청크가 도착할 때마다 화면을 아래로 이동시키면 읽던 위치를 잃고 서비스가 사용자의 조작을 방해하게 됩니다.

스크롤 영역의 전체 높이와 현재 위치를 비교하여 사용자가 하단 근처에 있을 때만 최신 응답을 따라가도록 해야 합니다. 사용자가 위로 이동하면 자동 스크롤을 중단하고 `최신 답변으로 이동` 버튼이나 새 내용 표시를 제공합니다. 사용자가 다시 하단으로 내려오거나 버튼을 누르면 자동 추적을 재개하는 방식이 적절합니다.

**2. LLM이 첫 번째 토큰을 보내기까지 걸리는 시간(TTFT) 동안 사용자에게 아무런 피드백도 주지 않는다면 어떤 문제가 발생할 수 있을까요?**

사용자는 요청이 정상적으로 전달되었는지, 시스템이 멈췄는지 판단할 수 없어 같은 질문을 반복해서 전송하거나 페이지를 이탈할 수 있습니다. 실제 전체 응답 시간이 짧더라도 아무 변화가 없는 구간이 길면 서비스가 느리고 신뢰하기 어렵다고 느낄 수 있습니다.

따라서 요청 직후 사용자 메시지를 화면에 반영하고 `답변을 준비하고 있습니다` 같은 상태 문구나 타이핑 인디케이터를 제공해야 합니다. 동시에 중단 버튼을 노출해 사용자에게 제어권을 주고, 첫 청크가 도착하면 준비 상태를 스트리밍 상태로 전환해야 합니다. 정확한 완료 비율을 알 수 없다면 임의의 진행률 대신 불확정 상태를 정직하게 표현하는 것이 좋습니다.

## Q101. AI의 환각 현상으로 잘못 만든 UI 컴포넌트가 렌더링될 위험을 방지하는 방안은 무엇인가요?

### 면접 답변

AI가 반환한 컴포넌트 이름과 속성은 신뢰할 수 없는 외부 입력으로 취급해야 합니다. 따라서 AI가 생성한 JSX나 코드를 직접 실행하지 않고, 백엔드에서 결과를 정해진 JSON 구조로 파싱한 뒤 Zod나 JSON Schema 같은 도구로 런타임 유효성 검사를 수행합니다. 프런트엔드에서도 응답을 다시 검증하여 필수 속성, 자료형, 값의 범위가 올바른 데이터만 렌더링 계층으로 전달합니다.

검증을 통과한 데이터라도 AI가 임의의 컴포넌트를 실행할 수 있게 해서는 안 됩니다. 화면에서 사용할 수 있는 컴포넌트만 매핑 테이블에 등록하고, AI가 보낸 문자열을 이 화이트리스트의 키로만 사용합니다. 등록되지 않은 컴포넌트 이름이나 잘못된 속성이 들어오면 빈 화면 대신 안전한 폴백 UI와 재시도 방법을 보여 줍니다.

마지막으로 검증 이후 발생할 수 있는 예기치 않은 렌더링 오류는 React의 Error Boundary로 격리합니다. 이때 검증 실패와 렌더링 실패를 관측할 수 있도록 오류 유형과 스키마 경로를 기록하되, 사용자 프롬프트나 민감 정보는 로그에서 제거해야 합니다. 이처럼 파싱, 런타임 검증, 화이트리스트 매핑, 폴백 UI, Error Boundary를 여러 방어선으로 구성하면 AI의 환각이 전체 화면 장애로 이어지는 것을 막을 수 있습니다.

### 핵심 개념

#### AI 출력은 신뢰할 수 없는 외부 입력

- **확률적 출력**: 같은 요청에도 달라질 수 있으며 사전에 정의하지 않은 이름이나 형식을 생성할 가능성
- **환각**: 존재하지 않는 컴포넌트, 누락된 필수 속성, 잘못된 자료형이나 허용되지 않은 동작을 그럴듯하게 반환하는 현상
- **신뢰 경계**: LLM의 출력이 애플리케이션 내부로 들어오는 지점에서 데이터의 구조와 권한을 검증해야 한다는 기준
- **데이터와 코드의 분리**: AI는 `ART_CARD` 같은 선언적 데이터만 반환하고 실행 가능한 JSX·JavaScript는 애플리케이션이 직접 보유하는 구조
- **최소 권한**: AI가 선택할 수 있는 컴포넌트, 속성, 동작의 범위를 제품이 필요한 수준으로만 제한

다음 방식은 AI가 만든 결과를 그대로 실행하므로 사용하면 안 됩니다.

```javascript
// 금지: AI가 만든 문자열을 코드로 실행
const Component = eval(aiResponse);

// 금지: 임의의 함수 본문 생성
const render = new Function("React", aiResponse);

// 주의: 검증하지 않은 HTML을 그대로 삽입
element.innerHTML = aiResponse;
```

- **임의 코드 실행 위험**: `eval()`이나 `new Function()`을 통한 애플리케이션 권한의 코드 실행
- **XSS 위험**: 검증하지 않은 HTML에 스크립트 실행 경로가 포함될 가능성
- **의존성 노출**: 임의의 모듈 이름을 동적 `import()`에 넘길 경우 허용하지 않은 코드 로딩 가능성
- **스타일 오염**: AI가 임의의 CSS나 인라인 스타일을 결정할 경우 화면 은폐, 피싱 UI, 레이아웃 붕괴 가능성

> AI에는 실행할 코드를 작성하게 하는 대신, 애플리케이션이 정의한 제한된 UI 스키마에 맞는 데이터만 선택하게 하는 구조가 안전

#### 단계별 방어 구조

```text
LLM 원본 출력
  → 백엔드 파싱·정규화
    → 서버 스키마 검증
      → API 응답
        → 클라이언트 스키마 재검증
          → 화이트리스트 컴포넌트 매핑
            → Error Boundary 내부에서 렌더링
              → 정상 UI 또는 폴백 UI
```

- **1차 방어 — 파싱 계층**: LLM의 자유 형식 텍스트에서 허용된 JSON 데이터만 추출하고 불완전한 응답 차단
- **2차 방어 — 서버 검증**: 데이터 보완과 권한 검사를 마친 뒤 계약에 맞는 응답만 클라이언트에 전달
- **3차 방어 — 클라이언트 검증**: 네트워크 경계에서 받은 값을 `unknown`으로 취급하고 렌더링 전에 다시 검사
- **4차 방어 — 화이트리스트**: 사전에 등록한 컴포넌트와 동작만 선택 가능하도록 제한
- **5차 방어 — 오류 격리**: 검증을 통과했지만 렌더링 중 발생한 예외를 Error Boundary로 제한

> 프런트엔드 검증은 서버 검증을 대체하는 보안 장치가 아니라, 잘못된 응답이 렌더링 장애로 이어지는 것을 막는 추가 방어선

#### 백엔드 파싱·정규화 계층

- **구조화 출력 요청**: 모델이 자유로운 JSX 대신 정해진 JSON 스키마를 반환하도록 제한
- **JSON 파싱**: 코드 펜스나 설명 문장을 제거하고 유효한 JSON 객체만 추출
- **필수 데이터 보완**: 서버가 관리하는 ID, 권한, URL 등 신뢰가 필요한 값은 모델 출력 대신 데이터베이스에서 주입
- **값 정규화**: 날짜, 열거형, 식별자 등의 형식을 애플리케이션 계약에 맞게 변환
- **권한 검증**: 현재 사용자가 볼 수 없는 리소스나 실행할 수 없는 액션 제거
- **실패 응답 표준화**: 파싱과 검증 실패를 정상 UI 데이터처럼 전달하지 않고 명확한 오류 코드로 반환

LLM은 화면 구성의 의도를 제안할 수 있지만 실제 권한과 데이터의 진실성, 사용할 컴포넌트 계약은 애플리케이션이 결정해야 합니다.

#### TypeScript 타입만으로 부족한 이유

```typescript
type AIComponent = {
  type: "ART_CARD" | "LOCATION_MAP";
  props: Record<string, unknown>;
};

const response = await fetch("/api/ai-ui");

// 타입 단언은 실제 응답을 검사하지 않음
const component = (await response.json()) as AIComponent;
```

- **정적 검사**: TypeScript가 개발 중 소스 코드의 타입 오류를 찾는 기능
- **타입 제거**: 컴파일이 끝나면 타입 정보가 삭제되어 브라우저 실행 중에는 존재하지 않는 구조
- **타입 단언의 한계**: `as AIComponent`는 값의 형태를 바꾸거나 검사하지 않고 컴파일러에 개발자의 판단을 전달할 뿐인 문법
- **외부 데이터의 실제 타입**: 네트워크, 저장소, 사용자 입력, LLM 응답처럼 런타임에 들어오는 값은 우선 `unknown`으로 취급
- **런타임 검증 필요성**: 실제 값의 속성, 자료형, 길이, 범위를 실행 시점에 확인하는 별도 계층

#### 스키마 기반 런타임 검증

컴포넌트 종류마다 필요한 `props`가 다르므로, `type`을 판별자로 사용하는 유니온 스키마가 적합합니다.

```typescript
import * as z from "zod";

const TextBlockSchema = z
  .object({
    id: z.string().min(1).max(100),
    type: z.literal("TEXT_BLOCK"),
    props: z.object({
      text: z.string().max(4_000),
    }),
  })
  .strict();

const ArtCardSchema = z
  .object({
    id: z.string().min(1).max(100),
    type: z.literal("ART_CARD"),
    props: z.object({
      title: z.string().min(1).max(100),
      artist: z.string().min(1).max(100),
      imageUrl: z.url(),
    }),
  })
  .strict();

const LocationMapSchema = z
  .object({
    id: z.string().min(1).max(100),
    type: z.literal("LOCATION_MAP"),
    props: z.object({
      latitude: z.number().min(-90).max(90),
      longitude: z.number().min(-180).max(180),
    }),
  })
  .strict();

const AIComponentSchema = z.discriminatedUnion("type", [
  TextBlockSchema,
  ArtCardSchema,
  LocationMapSchema,
]);

const AIResponseSchema = z
  .object({
    version: z.literal(1),
    components: z.array(AIComponentSchema).max(20),
  })
  .strict();

type AIComponent = z.infer<typeof AIComponentSchema>;
type AIResponse = z.infer<typeof AIResponseSchema>;
```

- **리터럴 판별자**: `type`에 허용된 문자열만 입력 가능
- **컴포넌트별 속성 검사**: 카드와 지도처럼 서로 다른 `props` 계약을 각각 검증
- **범위 제한**: 문자열 길이, 배열 개수, 위도·경도 범위 등을 제한해 비정상적인 렌더링 비용 방지
- **엄격 객체**: `.strict()`로 정의하지 않은 추가 키 차단
- **버전 필드**: 서버와 클라이언트의 UI 계약 변경을 명시적으로 구분
- **타입 추론**: 런타임 스키마에서 TypeScript 타입을 생성해 검증 규칙과 정적 타입의 중복 감소

`safeParse()`는 검증 실패 시 예외를 던지는 대신 성공 여부가 포함된 결과를 반환하므로 UI 분기를 명확하게 만들 수 있습니다.

```typescript
function parseAIResponse(raw: unknown): AIResponse | null {
  const result = AIResponseSchema.safeParse(raw);

  if (!result.success) {
    reportValidationFailure({
      issues: result.error.issues.map(({ path, code }) => ({ path, code })),
    });

    return null;
  }

  return result.data;
}
```

- **성공 시**: 검증과 정규화를 통과한 타입 안전한 `result.data` 사용
- **실패 시**: 렌더링 중단 후 안전한 폴백 UI로 전환
- **경로 중심 기록**: 전체 원본 응답 대신 실패한 필드의 경로와 오류 코드 기록
- **개인정보 최소화**: 프롬프트, 사용자 입력, 모델 원문을 오류 로그에 그대로 남기지 않는 정책

#### 화이트리스트 컴포넌트 매핑

스키마를 통과한 `type`과 애플리케이션 내부의 실제 컴포넌트를 명시적인 매핑 테이블로 연결합니다.

```tsx
import type { ComponentType } from "react";

const COMPONENT_REGISTRY: Record<string, ComponentType<any>> = {
  TEXT_BLOCK: TextBlock,
  ART_CARD: ArtCard,
  LOCATION_MAP: MapView,
};

function AIComponentRenderer({ component }: { component: AIComponent }) {
  const SelectedComponent = COMPONENT_REGISTRY[component.type];

  if (!SelectedComponent) {
    return <UnsupportedComponent type={component.type} />;
  }

  return <SelectedComponent {...component.props} />;
}
```

- **문자열은 선택 키로만 사용**: AI가 보낸 이름을 직접 실행하지 않고 미리 등록한 객체에서 조회
- **허용 목록 외 차단**: 매핑 테이블에 없는 이름은 컴포넌트로 실행하지 않고 폴백 처리
- **컴포넌트 구현 소유권**: 실제 JSX와 이벤트 로직은 개발자가 작성하고 검토한 코드만 사용
- **확장 방식 단순화**: 새 UI 유형 추가 시 스키마와 매핑 테이블을 함께 변경
- **감사 가능성**: AI가 선택할 수 있는 전체 UI 목록을 코드에서 명시적으로 확인 가능

예제에서는 핵심을 보여 주기 위해 `ComponentType<any>`를 사용했지만, 실제 코드에서는 `type`별 `props`를 매핑한 제네릭 타입으로 각 컴포넌트와 속성의 대응 관계까지 검사하는 편이 좋습니다.

#### 동작과 URL도 허용 목록으로 제한

컴포넌트 이름만 제한해도 `props`가 임의의 동작을 지시할 수 있다면 안전하지 않습니다. AI가 함수 코드를 보내는 대신 `OPEN_ART_DETAIL` 같은 제한된 액션 ID를 선택하도록 설계해야 합니다.

```typescript
const ACTIONS = {
  OPEN_ART_DETAIL: ({ artId }: { artId: string }) => {
    navigate(`/arts/${encodeURIComponent(artId)}`);
  },
  OPEN_HELP: () => {
    navigate("/help");
  },
} as const;
```

- **이벤트 핸들러 제한**: 함수 본문 대신 사전에 정의한 액션 이름과 검증된 매개변수만 허용
- **URL 정책**: `javascript:` 같은 프로토콜 차단, 필요한 경우 허용된 호스트와 경로만 통과
- **스타일 정책**: 임의 CSS 문자열 대신 `variant: "primary" | "secondary"` 같은 제한된 표현 사용
- **리소스 제한**: 중첩 깊이, 컴포넌트 개수, 텍스트 길이와 이미지 개수에 상한 적용

#### 안전한 렌더링 흐름

```tsx
function AIContent({ raw }: { raw: unknown }) {

  }

  return (

```

- **검증 전 렌더링 금지**: 원본 응답을 컴포넌트에 전달하지 않고 `safeParse()` 성공 결과만 사용
- **의미 있는 폴백**: 빈 화면보다 문제 상황과 다음 행동을 설명하는 UI 제공
- **안정적인 키**: 배열 인덱스 대신 검증된 컴포넌트 ID 사용
- **오류 영역 제한**: AI 기반 UI만 Error Boundary로 감싸 나머지 페이지 기능 유지

#### 전체 거부와 부분 렌더링 전략

| 전략 | 장점 | 주의점 |
| --- | --- | --- |
| **전체 응답 거부** | 일관된 화면과 단순한 오류 처리 | 일부 정상 데이터도 표시되지 않음 |
| **컴포넌트별 검증** | 정상인 항목은 계속 표시 가능 | 항목 간 의존 관계가 있으면 의미가 깨질 수 있음 |
| **필수 영역 전체 검증 후 부가 영역 개별 검증** | 핵심 흐름 보호와 부분 복구의 균형 | 스키마와 UI 정책이 복잡해질 수 있음 |

- **거래·결제·권한 화면**: 일부 데이터만 표시하면 잘못된 판단을 유도할 수 있으므로 전체 거부 우선
- **대시보드 위젯·추천 카드**: 서로 독립적이라면 실패한 항목만 폴백으로 교체 가능
- **정책의 명시성**: 검증 라이브러리가 아니라 제품 요구 사항에 따라 원자적 실패와 부분 성공 기준 결정

#### Error Boundary의 역할과 한계

Error Boundary는 하위 컴포넌트가 렌더링되는 과정에서 예외를 던졌을 때 오류를 기록하고 대체 UI를 보여 주는 React 컴포넌트입니다. 그러나 외부 데이터의 유효성을 판단하는 도구는 아니므로 스키마 검증 뒤의 마지막 방어선으로 사용해야 합니다.

- **포착 가능**: 하위 컴포넌트의 렌더링, 생성자, 생명주기 메서드에서 발생한 오류
- **포착 불가**: 이벤트 핸들러 내부 오류
- **포착 불가**: `setTimeout`과 일반적인 비동기 콜백에서 발생한 오류
- **포착 불가**: 서버 사이드 렌더링 중 발생한 오류
- **포착 불가**: Error Boundary 자체에서 발생한 오류
- **격리 범위**: 전체 앱보다 AI UI 영역 가까이에 배치하여 장애 전파 최소화

```tsx
import React from "react";

class AIContentErrorBoundary extends React.Component<
  React.PropsWithChildren,
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: unknown, info: React.ErrorInfo) {
    reportRenderFailure({ error, componentStack: info.componentStack });
  }

  render() {
    if (this.state.hasError) {
      return <p>일부 화면을 표시하지 못했습니다. 다시 시도해 주세요.</p>;
    }

    return this.props.children;
  }
}
```

#### 폴백 UI 설계

- **빈 화면 방지**: 데이터가 없어진 것처럼 보이지 않도록 명확한 실패 상태 표시
- **사용자 언어**: 내부 스키마나 컴포넌트 이름 대신 이해할 수 있는 문제 설명
- **복구 동작**: 다시 생성, 기본 화면으로 전환, 이전 단계로 이동 등의 행동 제공
- **부분 응답 구분**: 일부 컴포넌트만 실패했다면 실패한 위치와 전체 실패를 구별
- **레이아웃 안정성**: 오류가 발생해도 주변 화면이 크게 움직이지 않도록 예상 크기의 폴백 제공
- **접근성**: 오류 메시지를 `role="status"` 또는 상황에 따라 `role="alert"`로 전달하고 재시도 버튼에 명확한 이름 제공

#### 관측성과 운영 대응

- **검증 실패율**: 전체 AI UI 응답 중 스키마 검증에 실패한 비율
- **컴포넌트별 실패율**: 특정 `type`이나 스키마 버전에서 집중되는 문제 탐지
- **실패 경로**: `components[2].props.imageUrl`처럼 문제가 발생한 필드 위치
- **모델·프롬프트 버전**: 오류가 증가한 배포나 모델 변경점을 추적할 수 있는 식별자
- **폴백 노출률과 재시도율**: 기술 오류가 실제 사용자 경험에 미치는 영향 측정
- **민감 정보 제거**: 전체 프롬프트, 모델 원문, 사용자 개인정보를 그대로 수집하지 않는 로그 정책
- **알림 기준**: 일정 비율 이상의 검증 실패나 특정 컴포넌트 장애가 발생했을 때 운영 경보 발송

### 모의 면접

**1. LLM이 반환한 데이터를 Zod로 검사했을 때 유효성 검사에 실패했다면, 프런트엔드에서 어떻게 처리하는 것이 올바른 방식일까요?**

검증에 실패한 원본 데이터를 타입 단언으로 강제로 통과시키거나 일부 속성을 임의로 추측하여 렌더링하면 안 됩니다. 렌더링을 중단하고 사용자에게 `화면 정보를 불러오지 못했습니다`와 같은 안전한 폴백 UI와 재시도 수단을 제공해야 합니다. 이미 표시할 수 있는 기본 화면이 있다면 AI 기반 UI 대신 그 화면으로 전환할 수도 있습니다.

운영 측면에서는 실패한 스키마 경로와 오류 코드, 스키마·모델 버전을 기록하여 원인을 추적해야 합니다. 다만 사용자 프롬프트나 AI 원문에는 민감 정보가 포함될 수 있으므로 필요한 진단 정보만 수집해야 합니다. 일부 데이터의 표시 여부는 임의로 결정하지 않고, 독립적인 위젯인지 거래처럼 일관성이 중요한 화면인지에 따라 사전에 정의한 실패 정책을 따라야 합니다.

**2. AI가 화이트리스트에 없는 컴포넌트 이름을 반환했을 때, 화면을 아예 비워 두는 것과 기본 폴백 UI를 보여 주는 것 중 어느 쪽이 더 나은 UX일까요?**

기본 폴백 UI를 보여 주는 것이 더 낫습니다. 화면을 비워 두면 사용자는 정보가 원래 없는 것인지, 로딩 중인지, 오류가 발생한 것인지 판단할 수 없습니다. 폴백 UI는 해당 콘텐츠를 표시하지 못했다는 사실을 알리고 다시 시도하거나 기본 화면으로 이동할 방법을 제공할 수 있습니다.

다만 존재하지 않는 컴포넌트를 비슷한 이름의 다른 컴포넌트로 임의 대체해서는 안 됩니다. 이는 잘못된 의미나 동작을 제공할 수 있기 때문입니다. 허용 목록에 없는 이름은 실행하지 않고 명시적인 폴백으로 처리하며, 동시에 오류를 기록해 모델 출력이나 스키마 계약을 개선하는 것이 안전합니다.

## Q104. RAG 구조에서 프런트엔드 개발자의 역할은 무엇이라고 생각하나요?

### 면접 답변

RAG 구조에서 프런트엔드 개발자의 역할은 생성된 답변을 단순히 화면에 출력하는 데 그치지 않습니다. 사용자가 답변의 근거를 확인하고, 검색 과정을 이해하며, 결과를 신뢰할 수 있도록 백엔드의 검색·생성 결과를 투명한 사용자 경험으로 바꾸는 역할을 담당합니다.

먼저 답변의 주장과 검색된 원문을 연결해 문장별 출처를 표시하고, 사용자가 원문의 정확한 페이지나 문단으로 이동할 수 있게 해야 합니다. 또한 `검색 중`, `근거 문서 발견`, `답변 생성 중`, `관련 문서 없음`과 같은 상태를 구분하여 시스템이 무엇을 하고 있는지 정직하게 알려야 합니다. 검색 근거가 없다면 일반적인 모델 답변을 근거가 있는 답변처럼 표시하지 않고, 사용자의 동의를 받아 다른 방식으로 전환해야 합니다.

답변 이후에는 좋아요·싫어요뿐 아니라 부정확한 답변, 관련 없는 출처, 오래된 정보처럼 구체적인 피드백을 수집해야 합니다. 이 피드백을 해당 질문, 검색 결과, 모델·인덱스 버전과 연결하면 검색 및 생성 품질을 개선할 수 있습니다. 결국 프런트엔드는 RAG의 마지막 출력 계층이면서 사용자 신뢰, 제어권, 품질 개선 데이터를 연결하는 접점이라고 생각합니다.

### 핵심 개념

#### RAG와 프런트엔드의 접점

RAG(Retrieval-Augmented Generation)는 사용자의 질문과 관련된 외부 지식을 먼저 검색하고, 검색된 근거를 바탕으로 답변을 생성하는 방식입니다. 모델 내부의 지식만 사용하는 방식과 달리 검색 가능한 외부 지식을 결합하므로 최신 정보나 조직 내부 문서를 답변에 활용할 수 있습니다.

```text
사용자 질문
  → 검색 질의 생성
  → 관련 문서 검색·순위화
  → 검색 문서를 근거로 답변 생성
  → 답변·출처·검색 상태를 프런트엔드에 전달
  → 사용자의 확인·피드백
```

프런트엔드는 마지막 결과만 받는 수동적인 계층이 아닙니다. 사용자가 RAG의 동작을 이해하고 검증할 수 있도록 다음 정보를 연결하는 계층입니다.

- **답변**: 사용자의 질문에 대한 생성 결과
- **근거**: 답변 생성에 사용된 문서와 구간
- **검색 상태**: 검색 성공, 결과 없음, 일부 실패 등의 처리 과정
- **출처 탐색**: 원문 미리 보기와 정확한 위치로의 이동
- **사용자 제어**: 중단, 재시도, 일반 모델 전환 여부 선택
- **품질 신호**: 답변과 출처에 대한 구조화된 피드백

> 프런트엔드는 답변이 사실인지 새로 판정하는 계층이 아니라, 백엔드가 제공한 근거와 상태를 왜곡 없이 표현하고 사용자가 직접 검증할 수 있게 만드는 계층

#### RAG 응답 계약 설계

답변 문자열 하나만 반환하면 어느 문장이 어떤 문서를 근거로 하는지 안정적으로 표현하기 어렵습니다. 프런트엔드가 완성된 문자열에서 `[1]`, `[2]` 같은 기호를 정규식으로 추출하기보다, 백엔드가 답변 구간과 출처의 관계를 구조화하여 전달하는 것이 안전합니다.

```typescript
type RetrievalStatus =
  | "searching"
  | "retrieved"
  | "no_evidence"
  | "generating"
  | "completed"
  | "failed";

type Citation = {
  id: string;
  sourceId: string;
  title: string;
  url: string;
  page?: number;
  excerpt?: string;
  updatedAt?: string;
};

type AnswerSegment = {
  id: string;
  text: string;
  citationIds: string[];
};

type RagResponse = {
  traceId: string;
  status: RetrievalStatus;
  resultCount: number;
  segments: AnswerSegment[];
  citations: Citation[];
};
```

- **`traceId`**: 질문, 검색 결과, 생성 결과, 피드백을 같은 요청으로 연결하는 식별자
- **`segments`**: 답변을 의미 있는 구간으로 나누고 근거 출처의 ID를 연결
- **`citations`**: 화면에 표시할 제목, 원문 위치, 미리 보기 정보
- **`status`**: 현재 검색·생성 단계 또는 실패 상태
- **`resultCount`**: 발견한 관련 문서의 수를 사용자에게 알릴 때 사용할 정보

구조화된 응답에도 런타임 검증이 필요합니다. 필수 필드가 없거나 `citationIds`에 존재하지 않는 출처 ID가 포함되었다면 그대로 표시하지 않고, 근거 표시를 생략하거나 명시적인 오류 상태로 전환해야 합니다. 존재하지 않는 출처를 프런트엔드가 임의로 만들어 연결해서는 안 됩니다.

#### 답변과 출처 표시

출처는 답변 아래에 참고 자료 목록만 추가하는 장식이 아닙니다. 사용자가 답변의 주장을 검증할 수 있게 하는 핵심 인터페이스입니다.

- **인라인 인용**: 답변의 특정 문장 바로 뒤에 해당 근거 번호 표시
- **출처 칩**: 문서 제목, 페이지, 업데이트 날짜 등 식별 가능한 정보 제공
- **원문 미리 보기**: 출처를 열기 전에 답변의 근거로 사용된 문장 확인
- **딥 링크**: 문서의 첫 페이지가 아니라 실제 근거가 있는 페이지·문단으로 이동
- **중복 정리**: 여러 문장이 같은 문서를 참조할 때 하나의 출처로 일관되게 표현
- **근거 범위 표시**: 답변 전체가 아니라 어느 주장에 어떤 출처가 연결되는지 구분

```text
RAG는 검색된 외부 지식을 답변 생성에 결합합니다.[1]
검색 결과에는 답변의 근거와 출처 메타데이터가 포함될 수 있습니다.[2]

[1] Retrieval-Augmented Generation 논문
[2] Azure AI Search의 RAG 구조 문서
```

답변과 출처 목록이 모두 존재하더라도 둘 사이의 연결이 없다면 사용자는 어떤 문서가 어떤 주장을 뒷받침하는지 알기 어렵습니다. 따라서 출처 개수보다 **주장과 근거의 연결성**이 더 중요합니다.

#### 구조화된 출처 렌더링

다음 예제는 서버가 전달한 `citationIds`를 이용해 답변 구간과 출처를 연결합니다. 답변 문자열 안에 HTML을 삽입하거나 출처 번호를 추측하지 않으므로 렌더링 오류와 보안 위험을 줄일 수 있습니다.

```tsx
type RagAnswerProps = {
  response: RagResponse;
};

function RagAnswer({ response }: RagAnswerProps) {
  const citationById = new Map(
    response.citations.map((citation) => [citation.id, citation]),
  );

  return (
    <article aria-labelledby="rag-answer-title">
      <h2 id="rag-answer-title">AI 답변</h2>

      <div>
        {response.segments.map((segment) => (
          <span key={segment.id}>
            {segment.text}
            {segment.citationIds.map((citationId) => {
              const citation = citationById.get(citationId);

              if (!citation) return null;

              return (
                <a
                  key={citation.id}
                  href={`#source-${citation.id}`}
                  aria-label={`${citation.title} 출처로 이동`}
                >
                  [{citation.id}]
                </a>
              );
            })}
          </span>
        ))}
      </div>

      <section aria-labelledby="source-title">
        <h3 id="source-title">출처</h3>
        <ol>
          {response.citations.map((citation) => (
            <li id={`source-${citation.id}`} key={citation.id}>
              <a
                href={citation.url}
                target="_blank"
                rel="noopener noreferrer"
              >
                {citation.title}
                {citation.page ? ` (${citation.page}쪽)` : ""}
              </a>
              {citation.excerpt && <blockquote>{citation.excerpt}</blockquote>}
            </li>
          ))}
        </ol>
      </section>
    </article>
  );
}
```

- **구조화된 매핑**: `citationIds`와 출처 사전을 이용해 주장과 근거 연결
- **원문과 생성 답변 구분**: 인용문은 별도의 `blockquote`로 표시
- **내부 이동 제공**: 인라인 인용을 누르면 해당 출처 항목으로 이동
- **명확한 링크 이름**: 스크린 리더 사용자가 이동 목적을 알 수 있는 레이블 제공
- **새 탭 보안**: 외부 링크에 `rel="noopener noreferrer"` 적용

#### 출처 URL과 콘텐츠의 안전성

RAG의 검색 대상에는 사내 문서, 사용자가 업로드한 파일, 외부 웹 페이지가 포함될 수 있습니다. 검색 결과의 URL이나 원문 조각을 신뢰할 수 있는 UI 코드처럼 다루면 안 됩니다.

- **허용 프로토콜**: 일반적인 출처 링크는 `https:`처럼 허용한 프로토콜만 사용
- **출처 도메인 정책**: 사내 서비스라면 허용된 문서 저장소와 도메인인지 확인
- **권한 확인**: 현재 사용자가 접근할 수 없는 문서의 제목이나 본문이 노출되지 않도록 서버에서 필터링
- **HTML 직접 삽입 금지**: 원문 조각을 `dangerouslySetInnerHTML`로 그대로 렌더링하지 않고 텍스트로 표시
- **민감 정보 방지**: 검색 결과에 포함된 개인정보나 내부 식별자가 화면과 로그에 노출되지 않도록 처리
- **끊어진 링크 대응**: 삭제되거나 권한이 변경된 문서에는 접근 불가 상태와 다음 행동 안내

```typescript
const ALLOWED_SOURCE_ORIGINS = new Set([
  "https://docs.example.com",
  "https://knowledge.example.com",
]);

function getSafeSourceUrl(rawUrl: string) {
  try {
    const url = new URL(rawUrl);

    if (!ALLOWED_SOURCE_ORIGINS.has(url.origin)) {
      return null;
    }

    return url.toString();
  } catch {
    return null;
  }
}
```

클라이언트의 검사는 사용자 경험을 위한 추가 방어선일 뿐, 접근 권한과 데이터 노출 여부는 반드시 서버에서도 검증해야 합니다.

#### 검색 상태 공유

사용자는 최종 답변만 보는 것보다 시스템이 어떤 근거를 찾았는지 알 때 결과를 더 적절히 판단할 수 있습니다. 다만 내부 추론 과정이나 확정되지 않은 내용을 그대로 공개하는 것이 아니라, 검증 가능한 처리 상태만 간결하게 전달해야 합니다.

| 상태 | 사용자에게 보여 줄 수 있는 메시지 | 주요 동작 |
| --- | --- | --- |
| **검색 중** | 관련 문서를 찾고 있습니다 | 중단 가능 |
| **검색 완료** | 관련 문서 3건을 찾았습니다 | 출처 요약 표시 |
| **생성 중** | 검색된 문서를 바탕으로 답변을 작성하고 있습니다 | 점진적 답변 표시 |
| **근거 없음** | 지식 베이스에서 관련 문서를 찾지 못했습니다 | 질문 수정 또는 일반 답변 전환 선택 |
| **일부 실패** | 일부 문서를 확인하지 못했습니다 | 표시된 출처 범위 안내 |
| **실패** | 검색 중 문제가 발생했습니다 | 재시도 제공 |

- **검색과 생성을 구분**: 검색 결과가 없다는 상태와 답변 생성 자체가 실패한 상태를 분리
- **정직한 표현**: 근거가 없는데도 `관련 정보를 찾았습니다`라고 표시하지 않음
- **결과 수의 의미 명시**: 검색된 문서 수가 곧 정확도나 신뢰도 점수인 것처럼 표현하지 않음
- **폴백 선택권**: 지식 베이스 밖의 일반 답변으로 전환할 때 근거 수준이 달라짐을 알리고 동의 확인
- **접근성**: 상태 변화는 `role="status"`를 이용해 포커스를 강제로 옮기지 않고 전달

```tsx
function RetrievalStatus({ response }: RagAnswerProps) {
  const message = {
    searching: "관련 문서를 찾고 있습니다.",
    retrieved: `관련 문서 ${response.resultCount}건을 찾았습니다.`,
    no_evidence: "지식 베이스에서 관련 문서를 찾지 못했습니다.",
    generating: "검색된 문서를 바탕으로 답변을 작성하고 있습니다.",
    completed: "답변 생성이 완료되었습니다.",
    failed: "관련 문서를 검색하지 못했습니다. 다시 시도해 주세요.",
  }[response.status];

  return <p role="status">{message}</p>;
}
```

`role="status"` 영역을 토큰마다 갱신하면 보조 기술의 안내가 지나치게 반복될 수 있습니다. `검색 완료`, `생성 완료`, `오류`처럼 의미 있는 단계가 바뀔 때만 알리는 것이 좋습니다.

#### 근거가 없는 답변의 처리

RAG 시스템이 관련 문서를 찾지 못해도 모델은 일반 지식을 이용해 자연스러운 답변을 생성할 수 있습니다. 그러나 이를 검색 근거가 있는 답변과 동일하게 표현하면 사용자는 존재하지 않는 출처가 답변을 뒷받침한다고 오해할 수 있습니다.

- **근거 없음 명시**: 지식 베이스에서 관련 문서를 찾지 못했다는 상태 표시
- **임의 인용 금지**: 비슷해 보이는 문서를 출처로 연결하거나 존재하지 않는 출처 생성 금지
- **답변 모드 구분**: 검색 근거 기반 답변과 일반 모델 답변을 시각적·문구상으로 구별
- **사용자 동의**: 일반 모델 답변으로 전환하기 전에 한계와 출처 부재를 안내
- **질문 수정 지원**: 검색 가능한 용어 또는 범위를 사용해 다시 질문할 수 있는 방법 제공

> 답변을 보여 주는 것보다 어떤 근거 수준의 답변인지 정확히 알리는 것이 우선

#### 피드백 루프

`좋아요`와 `싫어요`만 수집하면 만족도의 방향은 알 수 있지만 무엇을 개선해야 하는지 판단하기 어렵습니다. 부정적인 피드백에는 선택 가능한 사유와 선택적 설명을 함께 제공하는 것이 좋습니다.

- **답변 문제**: 사실과 다름, 질문에 답하지 않음, 설명이 불명확함
- **검색 문제**: 관련 문서를 찾지 못함, 중요 문서 누락
- **출처 문제**: 출처가 주장을 뒷받침하지 않음, 링크에 접근할 수 없음, 오래된 문서
- **표현 문제**: 지나치게 길거나 짧음, 이해하기 어려움
- **기타 의견**: 미리 정한 범주에 속하지 않는 선택적 설명

```typescript
type FeedbackReason =
  | "incorrect_answer"
  | "irrelevant_answer"
  | "missing_source"
  | "unsupported_citation"
  | "outdated_source"
  | "inaccessible_source"
  | "other";

type RagFeedback = {
  traceId: string;
  rating: "up" | "down";
  reasons: FeedbackReason[];
  citationId?: string;
  comment?: string;
};

async function submitFeedback(feedback: RagFeedback) {
  const response = await fetch("/api/rag/feedback", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(feedback),
  });

  if (!response.ok) {
    throw new Error("피드백을 저장하지 못했습니다.");
  }
}
```

`traceId`를 이용하면 피드백 요청에 질문과 답변 전체를 다시 실어 보내지 않고도 서버에서 해당 검색 결과와 생성 기록을 찾을 수 있습니다. 다만 추적 데이터의 보관 기간과 접근 권한을 정하고, 민감 정보는 저장하지 않거나 제거해야 합니다.

#### 피드백을 시스템 개선에 활용하는 과정

```text
사용자 피드백 수집
  → 요청·검색 결과·출처와 연결
  → 중복·오용·개인정보 정제
  → 실패 유형별 분류
  → 검색·순위화·생성 단계의 원인 분석
  → 오프라인 평가와 검토
  → 변경 사항 배포
  → 실제 지표 재측정
```

- **검색 품질 개선**: `중요 문서 누락` 사례를 질의 변환, 검색 필터, 임베딩, 재순위화 평가 데이터로 사용
- **출처 품질 개선**: 접근 불가·오래된 문서 비율을 분석하여 인덱스 갱신과 권한 정책 점검
- **생성 품질 개선**: 검색 근거는 적절하지만 답변이 틀린 사례를 프롬프트와 생성 모델 평가에 활용
- **UX 개선**: 출처를 찾기 어렵거나 피드백 과정에서 이탈하는 흐름 개선
- **회귀 테스트**: 자주 실패한 실제 질문을 익명화하여 변경 전후의 품질 비교

사용자 피드백은 유용한 신호지만 곧바로 정답 데이터가 되는 것은 아닙니다. 사용자가 잘못 이해했거나 악의적으로 평가할 수 있고, 만족스러운 문체와 사실 정확성이 서로 다를 수도 있습니다. 따라서 피드백을 정제하고 전문가 검토나 자동 평가와 교차 확인한 뒤 학습·검색 개선에 사용해야 합니다.

#### 프런트엔드가 함께 측정할 지표

- **검색 성공률**: 전체 요청 가운데 하나 이상의 유효한 근거 문서를 찾은 비율
- **근거 없음 비율**: 지식 베이스 범위 밖의 질문이나 검색 실패가 발생한 비율
- **출처 클릭률**: 사용자가 답변의 근거를 확인하기 위해 출처를 연 비율
- **인용 미지원 비율**: 출처가 연결되지 않은 답변 구간의 비율
- **접근 불가 출처 비율**: 권한, 삭제, 링크 오류로 원문을 열 수 없는 비율
- **답변 만족도**: 좋아요·싫어요와 세부 사유의 분포
- **재질문·이탈률**: 답변 이후 질문을 고쳐 다시 검색하거나 세션을 떠나는 비율
- **피드백 제출 실패율**: 사용자가 남긴 평가가 네트워크 오류 등으로 저장되지 못한 비율

출처 클릭률이 높다고 반드시 답변 품질이 좋은 것은 아닙니다. 답변을 믿지 못해 출처를 반복해서 확인했을 수도 있으므로 만족도, 검색 성공률, 인용 정확성 같은 지표와 함께 해석해야 합니다.

#### 역할의 경계

프런트엔드는 사용자와 가장 가까운 계층이지만 RAG의 모든 품질 문제를 혼자 해결할 수는 없습니다.

| 영역 | 주된 책임 |
| --- | --- |
| **백엔드·검색 계층** | 접근 권한 확인, 검색, 재순위화, 출처와 답변 구간의 연결, 추적 정보 생성 |
| **생성 계층** | 제공된 근거를 사용한 답변 생성, 근거 밖 주장 최소화 |
| **프런트엔드** | 검색 상태·답변·출처의 정확한 표현, 검증 가능한 탐색 경험, 피드백과 사용자 제어 제공 |
| **운영·평가 계층** | 피드백 정제, 품질 평가, 인덱스·모델·프롬프트 개선 및 회귀 검증 |

프런트엔드가 임의로 출처를 매핑하거나 검색 결과를 신뢰도 점수로 해석하면 시스템의 의미를 왜곡할 수 있습니다. 반대로 백엔드가 출처와 상태를 구조화하지 않고 답변 문자열만 전달하면 프런트엔드는 신뢰할 수 있는 출처 경험을 만들기 어렵습니다. 따라서 RAG 응답 계약을 여러 계층이 함께 설계해야 합니다.

#### 접근성과 오류 처리

- **의미 있는 요소**: 출처는 링크, 평가 동작은 버튼으로 구현
- **키보드 접근**: 인라인 인용, 출처 미리 보기, 피드백을 키보드로 조작 가능하게 구성
- **상태 알림**: 검색·생성 상태는 의미가 바뀔 때 `role="status"`로 전달
- **포커스 유지**: 검색 결과가 추가될 때 사용자의 포커스를 강제로 이동하지 않음
- **오류의 구분**: 답변 생성 실패, 출처 로드 실패, 피드백 저장 실패를 서로 다른 상태로 표시
- **피드백 복구**: 제출 실패 시 선택 내용을 유지하고 재시도 방법 제공
- **부분 실패 허용**: 출처 미리 보기를 불러오지 못해도 이미 검증된 답변과 출처 제목까지 모두 제거하지 않음

### 모의 면접

**1. RAG 시스템에서 사용자가 답변에 피드백을 주었을 때 이 데이터가 단순한 ‘불만 접수’를 넘어 시스템 개선에 어떻게 활용될 수 있을까요?**

피드백을 해당 요청의 질문, 검색된 문서, 문서의 순위, 선택된 출처, 모델·프롬프트·인덱스 버전과 연결하면 어느 단계에서 문제가 발생했는지 분석할 수 있습니다. 예를 들어 `관련 문서를 찾지 못함`이 반복되면 검색 질의 변환이나 임베딩, 재순위화 과정을 점검할 수 있고, 검색 문서는 적절하지만 답변이 부정확하다면 생성 프롬프트나 모델의 근거 사용 방식을 개선할 수 있습니다. 출처가 오래되었거나 접근할 수 없다는 피드백은 인덱스 갱신과 권한 정책을 수정하는 데 활용할 수 있습니다.

다만 사용자의 평가는 주관적이거나 잘못될 수 있으므로 곧바로 정답으로 학습시키면 안 됩니다. 중복과 악성 데이터를 제거하고 개인정보를 정제한 뒤, 전문가 검토와 오프라인 평가를 거쳐 검색·생성 시스템을 변경해야 합니다. 이후 같은 실패 사례를 회귀 테스트에 포함하고 실제 만족도와 검색 품질 지표를 다시 측정해야 개선 루프가 완성됩니다.

**2. RAG 답변에서 출처를 표시하는 것이 왜 단순한 ‘부가 기능’이 아니라 서비스의 신뢰도를 결정짓는 핵심 요소가 될까요?**

생성된 답변은 자연스럽게 보여도 사실과 다르거나 검색 문서의 의미를 잘못 해석할 수 있습니다. 출처를 표시하면 사용자는 답변이 어떤 문서에 근거했는지 확인하고 중요한 판단 전에 원문과 비교할 수 있습니다. 특히 답변의 각 주장과 해당 문서의 페이지·문단을 직접 연결하면 단순히 참고 자료 목록을 보여 주는 것보다 검증 비용을 크게 줄일 수 있습니다.

출처는 시스템의 한계도 드러냅니다. 관련 문서를 찾지 못했거나 일부 주장에 근거가 없다면 그 사실을 숨기지 않고 표시할 수 있기 때문입니다. 따라서 정확한 출처 표시는 답변을 무조건 믿게 만드는 장치가 아니라 사용자가 근거 수준을 스스로 판단하도록 돕는 장치이며, 이 투명성이 서비스의 신뢰도를 결정합니다.
