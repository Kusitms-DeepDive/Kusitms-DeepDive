# Q100. LLM의 응답 지연 문제를 사용자 경험 측면에서 어떻게 해결할 수 있나요?

## 1. 스트리밍과 인디케이터 UI

### 스트리밍

스트리밍은 데이터를 한 번에 다 받는 게 아니라, 조금씩 받아오면서 바로 보여주는 방식이다.

LLM 답변을 전부 생성할 때까지 기다리게 하는 것보다, 생성되는 답변부터 바로 보여주는 게 사용자 경험 측면에서 좋다고 생각한다.

사용자 입장에서는 답변이 끝나는 순간보다 **답변이 시작되는 순간**에 "아, 지금 제대로 돌아가고 있구나"라고 느끼기 때문이다.

실제 처리 속도가 빨라지는 건 아니지만, 그냥 기다리는 시간이 아니라 답변을 읽는 시간으로 바뀌기 때문에 체감되는 대기 시간이 줄어드는 효과가 있다.

구현 방법은 크게 두 가지가 있다.

- **SSE (Server-Sent Events)**
  - 서버에서 클라이언트 방향으로 데이터를 계속 보내주는 방식이다.
  - 브라우저의 `EventSource`로 사용할 수 있고 연결이 끊겼을 때 자동으로 재연결해 주는 기능도 있다.
  - 대신 기본적으로 GET 요청만 가능하고 인증 헤더를 직접 넣기 어렵다는 단점이 있다.

- **Fetch API + ReadableStream**
  - `fetch`를 사용하기 때문에 POST 요청도 가능하고, 헤더도 자유롭게 설정할 수 있다.

LLM 채팅은 보통 프롬프트를 POST로 보내야 하고 인증도 필요한 경우가 많기 때문에, 실제 프론트에서는 `fetch`로 요청을 보내고 `ReadableStream`으로 응답을 조금씩 읽는 방식을 많이 사용한다.

응답 자체는 SSE 형식으로 오는 경우도 있다.

### TTFT (Time To First Token)

스트리밍을 사용한다고 해서 바로 답변이 나오는 건 아니다.

첫 번째 토큰이 나오기 전까지는 어쨌든 기다리는 시간이 생기는데, 이 시간을 **TTFT(Time To First Token)**라고 한다.

이 구간은 아직 스트리밍 데이터가 오기 전이기 때문에, 스트리밍만으로는 해결하기 어렵다. 그래서 이때는 인디케이터 UI를 보여주는 게 좋다.

- **스켈레톤 UI**: 실제 데이터가 들어올 자리에 흐릿한 박스를 먼저 보여주는 방식
- **타이핑 인디케이터**: 점 3개가 움직이는 것처럼 보여서 현재 답변을 준비하고 있다는 걸 알려주는 방식

결국 이런 UI는 단순히 화면을 예쁘게 꾸미는 게 아니라, **"지금 멈춘 게 아니라 처리하고 있어요"라고 사용자에게 알려주는 역할**이라고 생각한다.

## 2. Fetch API의 ReadableStream

`fetch()`는 응답 본문 전체가 다 도착해야 끝나는 게 아니다.

응답 헤더가 먼저 도착하면 `fetch()`의 `Response`를 받을 수 있고, 그 이후에도 응답 본문은 계속 들어올 수 있다.

그런데 우리가 평소에 사용하는 `response.json()`이나 `response.text()`는 본문을 전부 받은 다음에 결과를 반환한다.

그래서 스트리밍을 사용하려면 `response.body`에 있는 `ReadableStream`에서 `reader`를 가져와서 직접 조금씩 읽어야 한다.

```js
const res = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ prompt }),
});

const reader = res.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();

  if (done) break;

  const text = decoder.decode(value, { stream: true });

  appendToScreen(text);
}
```

`reader.read()`를 호출하면 현재 들어온 데이터 조각을 받아오고, 아직 데이터가 더 있으면 계속 읽는다.

더 이상 받을 데이터가 없으면 `done`이 `true`가 된다.

여기서 주의할 점이 두 가지 있다.

### 1. 한글이 중간에 잘릴 수 있음

네트워크로 들어오는 데이터는 바이트 단위로 나뉘어 올 수 있다.

UTF-8에서는 한글 한 글자가 여러 바이트로 이루어져 있기 때문에, 데이터가 들어오는 과정에서 한글 한 글자가 두 조각으로 나뉘어 올 수도 있다.

그래서 단순히 `decoder.decode(value)`만 사용하는 게 아니라,

```js
decoder.decode(value, { stream: true })
```

처럼 `stream: true`를 사용한다.

이렇게 하면 아직 글자가 완성되지 않은 바이트를 기억해뒀다가 다음 데이터가 들어오면 이어서 처리할 수 있다.

### 2. 데이터 조각이 메시지 단위라는 보장이 없음

`read()` 한 번에 메시지 하나가 오는 게 아니다.

예를 들어 메시지 하나가 반만 들어올 수도 있고, 반대로 여러 개의 메시지가 한 번에 들어올 수도 있다.

그래서 받은 데이터를 바로 하나의 메시지라고 생각하면 안 된다.

보통은 데이터를 **버퍼에 쌓아두고**, `\n\n` 같은 구분자를 기준으로 잘라서 하나씩 처리하는 방식으로 구현한다.

## 3. 낙관적 UI와 중단 권한

### 낙관적 UI

낙관적 UI는 서버의 응답을 기다리지 않고, 성공할 것이라고 가정해서 화면을 먼저 변경하는 방식이다.

예를 들어 채팅에서 질문을 보내면 서버의 응답을 기다리지 않고 **내가 보낸 질문을 채팅창에 먼저 보여주는 것**이 낙관적 UI의 예시다.

물론 실제 요청이 실패할 수도 있기 때문에, 실패했을 때는 "전송 실패"나 "다시 시도" 같은 처리가 필요하다.

진행률을 보여주는 UI에서도 비슷한 방식으로 사용자 체감 속도를 개선할 수 있다.

예를 들어 0%에서 90%까지는 빠르게 올라가고 마지막 10%에서 천천히 올라가게 하면, 실제 처리 시간과 별개로 사용자가 더 빠르게 처리되고 있다고 느낄 수 있다.

### AbortController

LLM 답변을 기다리다 보면 답변이 너무 길거나, 사용자가 원하는 방향이 아니어서 중간에 멈추고 싶은 경우도 있다.

이럴 때 웹에서는 `AbortController`를 사용할 수 있다.

```js
const controller = new AbortController();

stopButton.onclick = () => controller.abort();

try {
  await fetch('/api/chat', {
    method: 'POST',
    signal: controller.signal,
  });
} catch (err) {
  if (err.name === 'AbortError') {
    // 사용자가 직접 중단한 경우
  }
}
```

`fetch`는 요청을 시작했다고 해서 그냥 알아서 멈출 수 있는 건 아니다.

그래서 요청을 보낼 때 `signal`을 같이 넘겨주고, 나중에 `controller.abort()`를 호출하면 해당 요청을 중단할 수 있다.

이때 사용자가 직접 중단한 경우에는 일반적인 에러처럼 보여주기보다는 **"답변이 중단됐어요" 정도로 처리하는 게 자연스럽다.**

같이 알아두면 좋은 부분은 다음과 같다.

- 답변이 생성되는 동안에는 전송 버튼을 정지 버튼으로 바꿔줄 수 있다.
- 새로운 질문을 보낼 때 이전 요청을 `abort`하면 이전 답변과 새로운 답변이 섞이는 것을 막을 수 있다.
- 컴포넌트가 unmount될 때 `abort`해서 더 이상 필요 없는 요청을 정리할 수 있다.
- `AbortSignal.timeout(30000)`을 사용하면 30초가 지나면 자동으로 요청을 중단할 수도 있다.
- 한 번 `abort`한 `AbortController`는 다시 사용할 수 없기 때문에 요청마다 새로 만들어야 한다.

## 4. 자동 스크롤과 가독성

LLM 답변이 길어지면 스트리밍으로 텍스트가 계속 추가되면서 화면이 아래로 내려가게 된다.

그래서 새로운 텍스트가 추가될 때마다 자동으로 가장 아래까지 스크롤해주는 기능을 사용할 수 있다.

그런데 여기서 중요한 건 **무조건 자동 스크롤을 하면 안 된다는 것**이다.

사용자가 답변을 읽다가 위로 스크롤해서 이전 내용을 보고 있을 수도 있기 때문이다.

이때 새로운 텍스트가 들어올 때마다 강제로 아래로 내려가면 사용자가 읽고 있던 위치가 계속 바뀌어서 오히려 불편해진다.

그래서 나는 **사용자가 맨 아래 근처에 있을 때만 자동 스크롤을 유지하는 방식**이 좋다고 생각한다.

```js
const isNearBottom = (el) =>
  el.scrollHeight - el.scrollTop - el.clientHeight < 80;
```

위 코드처럼 바닥에서 80px 이내에 있으면 사용자가 거의 맨 아래에 있다고 판단해서 자동 스크롤을 유지할 수 있다.

반대로 사용자가 위로 많이 올라갔다면 자동 스크롤을 멈추고, 필요하다면 **"새 응답 보기"** 같은 버튼을 보여줄 수도 있다.

결국 자동 스크롤은 항상 화면을 움직이는 게 아니라, **사용자가 읽는 걸 방해하지 않는 선에서 필요한 경우에만 따라가게 만드는 게 중요하다.**

## 5. 모의 면접

### 1. 스트리밍 응답 중 사용자가 위로 스크롤했을 때, 자동 스크롤을 계속 유지해야 할까요? 그렇게 생각하는 이유는 무엇인가요?

저는 **사용자가 위로 스크롤했다면 자동 스크롤을 잠시 멈추는 게 좋다고 생각합니다.**

사용자가 직접 위로 올라갔다는 건 이전 내용을 읽고 싶다는 의미일 수 있기 때문입니다.

그래서 **맨 아래에 있을 때만 자동 스크롤을 유지하고**, 위로 올라가면 멈추도록 구현할 것 같습니다.

대신 새로운 답변이 생성되고 있다는 걸 알 수 있도록 **"새 응답 보기" 버튼을 보여주고**, 사용자가 다시 아래로 내려오면 자동 스크롤을 활성화하면 좋을 것 같습니다.

### 2. LLM이 첫 번째 토큰을 보내기까지 걸리는 시간(TTFT) 동안 사용자에게 아무런 피드백도 주지 않는다면 어떤 문제가 발생할 수 있을까요?

TTFT 동안 화면에 아무 변화가 없다면 사용자는 **요청이 제대로 들어갔는지 알기 어려울 것 같습니다.**

그래서 질문을 보내자마자 **낙관적 UI로 질문을 먼저 보여주고**, 답변이 시작되기 전에는 타이핑 인디케이터나 스켈레톤 UI를 보여주는 게 좋다고 생각합니다.

또한 답변 생성 중에는 전송 버튼을 정지 버튼으로 바꿔서 **중복 전송을 막고, 사용자가 원하면 답변을 중단할 수 있도록 하는 것**도 필요하다고 생각합니다.


# Q101. AI의 환각 현상으로 잘못 만든 UI 컴포넌트가 렌더링될 위험을 방지하는 방안은 무엇인가요?

LLM은 가끔 실제로 존재하지 않는 컴포넌트 이름을 만들어내거나, 필요한 데이터를 빼먹는 경우가 있다.

이런 데이터를 그대로 프론트에서 렌더링하면 잘못된 컴포넌트를 실행하거나, 필요한 props가 없어서 화면이 깨질 수도 있다.

전체적인 흐름은 다음과 같다.

```text
LLM 응답 → ① 백엔드 파싱 → ② 스키마 검사 → ③ 화이트리스트 매핑 → ④ ErrorBoundary
```

---

## 1단계: 백엔드 출력 파싱 레이어

LLM이 만들어낸 데이터를 그대로 프론트로 넘기지는 않는 게 좋다고 생각한다.

백엔드에서 먼저 JSON 형태로 파싱하고, 필요한 정보가 빠져 있다면 DB에 있는 데이터를 채워주거나 잘못된 값은 수정한다.

즉, **LLM은 어떤 데이터를 만들지 제안하는 역할을 하고, 실제로 사용할 데이터인지는 백엔드에서 확정하는 방식**이다.

이렇게 하면 프론트에서는 어느 정도 정리되고 검증된 데이터만 받을 수 있다.

---

## 2단계: 스키마 기반 유효성 검사

그다음에는 Zod나 JSON Schema를 사용해서 데이터가 우리가 정해둔 형태에 맞는지 **런타임에서 검사**한다.

TypeScript의 타입은 실제 실행할 때는 사라지기 때문에, API를 통해 들어오는 AI 응답까지 자동으로 검증해 주지는 않는다.

그래서 AI처럼 외부에서 들어오는 데이터를 사용할 때는 별도의 런타임 검증이 필요하다.

---

## 3단계: 화이트리스트 컴포넌트 매핑

### 개념

AI가 컴포넌트 이름을 직접 코드처럼 만들어서 실행하게 하면 위험할 수 있다.

그래서 AI에게는 실제 컴포넌트가 아니라 `'ART_CARD'` 같은 **문자열만 보내도록 한다.**

그리고 프론트에서는

> "이 문자열이면 이 컴포넌트를 사용한다."

라는 매핑 테이블을 만들어 두고, **등록된 컴포넌트만 렌더링한다.**

```tsx
const COMPONENT_REGISTRY: Record<string, React.ComponentType<any>> = {
  ART_CARD: ArtCard,
  LOCATION_MAP: MapView,
};

function ChatMessage({ aiData }) {
  const Component = COMPONENT_REGISTRY[aiData.type];

  if (!Component) return <FallbackCard />;

  return <Component {...aiData.props} />;
}
```

여기서 `Record<K, V>`는 **K 타입의 키와 V 타입의 값을 가지는 객체**를 의미한다.

여기서는 AI가 보내는 컴포넌트 이름이 키가 되고, 실제 React 컴포넌트가 값이 된다.

이렇게 하면 등록되지 않은 컴포넌트는 렌더링하지 않고 바로 폴백 UI를 보여줄 수 있다.

### 장점

- **안전성**: 등록되지 않은 컴포넌트는 렌더링하지 않는다.
- **유연성**: 새로운 컴포넌트를 추가할 때 매핑 테이블에 추가하면 된다.
- **가독성**: 컴포넌트가 많아져도 `if / else if`를 계속 작성하지 않아도 된다.

### 주의 1. 객체 장부의 함정

여기서 하나 주의할 점이 있다.

JavaScript의 객체는 기본적으로 프로토타입을 가지고 있기 때문에, 내가 직접 등록하지 않은 키인데도 값이 나올 수 있다.

예를 들어,

```js
COMPONENT_REGISTRY['constructor'];
```

이렇게 접근하면 `undefined`가 아니라 `Object` 함수가 나올 수 있다.

그러면 단순히

```js
if (!Component)
```

으로 검사했을 때 통과할 가능성이 있다.

그래서 **내가 직접 등록한 키인지 확인하는 방식**으로 검사하는 게 더 안전하다.

```ts
const Component = Object.hasOwn(COMPONENT_REGISTRY, aiData.type)
  ? COMPONENT_REGISTRY[aiData.type]
  : null;
```

또는 `Map`을 사용하면 이런 프로토타입 상속 문제를 피할 수 있다.

### 주의 2. 장부에 스키마도 같이 넣기

컴포넌트 이름이 맞다고 해서 항상 안전한 건 아니다.

예를 들어 `ART_CARD`라는 이름은 맞는데 `title`이나 `artist` 같은 필수 props가 빠져 있을 수도 있다.

그래서 컴포넌트와 해당 컴포넌트가 필요한 props 스키마를 하나의 장부에 같이 넣어두는 방법도 있다.

```tsx
const REGISTRY = {
  ART_CARD: {
    component: ArtCard,
    schema: z.object({
      title: z.string(),
      artist: z.string(),
    }),
  },
};
```

이렇게 하면

```text
컴포넌트 이름 확인
→ props schema 검사
→ 둘 다 통과하면 렌더링
```

하는 식으로 한 곳에서 관리할 수 있다.

---

## 4단계: 우아한 폴백 처리

여기까지 검증했는데도 예상하지 못한 에러가 발생할 수 있다.

그래서 마지막으로 `ErrorBoundary`를 사용해서 **특정 컴포넌트에서 발생한 렌더링 에러가 앱 전체로 퍼지지 않도록 격리**할 수 있다.

예를 들어 하나의 AI 카드가 잘못 렌더링되더라도 전체 채팅 화면이 하얗게 날아가는 대신, 해당 카드 부분만

> "정보를 표시할 수 없습니다."

같은 폴백 UI를 보여주는 방식이다.

여기에 다시 시도 버튼을 추가할 수도 있다.

다만 `ErrorBoundary`는 **렌더링 과정에서 발생하는 에러를 잡는 역할**이고, 이벤트 핸들러나 비동기 코드에서 발생한 에러까지 자동으로 잡아주는 것은 아니라는 점은 알아둬야 한다.

## 모의 면접

### 1. LLM이 반환한 데이터를 Zod로 검사했을 때 유효성 검사에 실패했다면, 프론트엔드에서 어떻게 처리하는 것이 올바른 방식일까요?

검증에 실패한 데이터는 **렌더링하지 않고 폴백 UI를 보여주는 게 먼저라고 생각합니다.**

`parse()`로 바로 에러를 발생시키기보다는 `safeParse()`로 성공 여부를 확인하고, 실패했다면 **"정보를 표시할 수 없습니다." 같은 폴백 UI와 다시 시도 버튼**을 보여줄 것 같습니다.

그리고 실패한 데이터와 오류 내용을 로그로 남겨서, 자주 발생하는 문제를 확인하고 이후 프롬프트나 백엔드 로직을 개선하는 데 활용할 것 같습니다.

### 2. AI가 화이트리스트에 없는 컴포넌트 이름을 반환했을 때, 화면을 아예 비워 두는 것과 기본 폴백 UI를 보여 주는 것 중 어느 쪽이 더 나은 UX일까요?

저는 **기본 폴백 UI를 보여주는 게 좋다고 생각합니다.**

화면이 비어 있으면 사용자는 로딩 중인지, 오류가 발생한 건지 알기 어렵기 때문입니다.

그래서 **"이 부분은 표시할 수 없습니다." 같은 안내와 다시 시도 버튼**을 제공하는 게 좋을 것 같습니다.

다만 내부 에러나 AI가 반환한 잘못된 컴포넌트 이름은 사용자에게 보여주지 않고 로그로 남기는 게 좋다고 생각합니다.

# Q104. RAG 구조에서 프론트엔드 개발자의 역할은 무엇이라고 생각하나요?

## RAG?

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM이 답변하기 전에 관련된 문서를 먼저 찾아보고, 그 내용을 참고해서 답변하도록 하는 방식이다.

LLM은 학습한 내용만으로 답변하기 때문에 최신 정보나 회사 내부 문서처럼 학습하지 않은 내용은 알기 어렵다. 그리고 모르는 내용도 그럴듯하게 만들어서 답하는 환각이 발생할 수 있다.

그래서 우리 회사 문서나 최신 자료를 먼저 검색해서 LLM에게 같이 넘겨주면, 해당 문서를 근거로 답변하게 만들 수 있다.

사용자 질문
→ 관련 문서 검색 (벡터 DB)
→ 찾은 문서 + 사용자 질문을 LLM에 전달
→ 답변 생성

검색하고 답변을 만드는 과정은 주로 백엔드에서 처리하기 때문에 RAG는 백엔드 영역이라고 생각하기 쉽다.

그런데 실제 사용자가 답변을 보고 **“이 답변을 믿어도 되나?”**라고 판단하는 부분은 프론트엔드에서 만들어야 한다고 생각한다.

⸻

## 1. 출처 표시

RAG를 사용하는 이유 중 하나가 근거가 있는 답변을 만들기 위해서이기 때문에, 어떤 문서를 참고해서 답변했는지를 사용자에게 보여주는 게 중요하다.

예를 들어 답변 아래에 출처를 표시할 수 있다.

* 각주([1])나 출처 칩(source chips) 형태로 답변 아래에 표시
* 답변 속 문장과 원본 문서(PDF, 웹 페이지 등)를 연결해서 사용자가 직접 확인할 수 있게 함
* 출처를 클릭하면 해당 문서의 페이지나 문단으로 바로 이동할 수 있도록 함 (deep linking)

```tsx
{sources.map((src, idx) => (
  <a key={idx} href={src.url} target="_blank">
    [{idx + 1}] {src.title} (p.{src.page})
  </a>
))}
```

단순히 “이 답변은 문서를 참고했어요”라고 보여주는 것보다, 실제로 어떤 문서를 참고했는지 확인할 수 있게 만드는 게 더 중요하다고 생각한다.

⸻

## 2. 피드백 루프

RAG라고 해서 항상 정확한 답변을 만드는 건 아니다.

검색 단계에서 엉뚱한 문서를 가져올 수도 있고, 문서는 제대로 가져왔는데 LLM이 그 내용을 잘못 해석할 수도 있다.

그래서 사용자가 답변에 대해 어떻게 생각했는지를 수집하는 것도 프론트엔드에서 할 수 있는 중요한 역할이라고 생각한다.

예를 들어,

* 답변 아래에 좋아요 / 싫어요 버튼을 둔다.
* 싫어요를 누르면 왜 싫은지 이유를 고르게 한다.
    * 관련 없는 정보
    * 답변이 틀림
    * 질문을 제대로 이해하지 못함
    * 기타
* 사용자의 질문, AI의 답변, 참고한 문서와 피드백을 같이 묶어서 전달한다.

이렇게 모인 데이터는 단순히 사용자의 불만을 기록하는 데서 끝나는 게 아니라, RAG 시스템의 어느 부분에서 문제가 발생하고 있는지 확인하는 자료로 사용할 수 있다.

예를 들어 “관련 없는 정보”라는 피드백이 많다면 검색 단계에서 잘못된 문서를 가져오는 문제일 수 있고, 문서는 제대로 가져왔는데 “답변이 틀림”이 많다면 LLM이 문서를 잘못 해석하는 문제일 수도 있다.

그래서 이런 데이터를 백엔드 팀이 검색 알고리즘을 개선하거나 모델을 다시 학습시킬 때 활용할 수 있고, 이후에는 골드 데이터로도 사용할 수 있다.

⸻

## 3. 검색 상태 공유

RAG에서는 답변이 바로 나오는 게 아니라

질문
→ 관련 문서 검색
→ 문서 확인
→ LLM 답변 생성

같은 과정을 거친다.

이 과정에서 아무런 안내 없이 기다리게 하면 사용자는 지금 무슨 일이 일어나고 있는지 알기 어렵다.

그래서 검색하는 동안 현재 상태를 보여주는 게 좋다고 생각한다.

예를 들어,

“지식 베이스에서 관련 문서를 3건 찾았습니다.”

처럼 현재 어떤 작업을 하고 있는지 알려줄 수 있다.

반대로 관련 문서를 아예 찾지 못했다면 그것도 사용자에게 알려주는 게 좋다.

“관련 지식을 찾지 못했습니다.”

이렇게 알려주고 필요하다면 일반 LLM 모드로 답변할지 사용자에게 선택하게 할 수도 있다.

관련 문서를 찾지 못했는데도 아무런 안내 없이 답변을 만들어버리면, 사용자는 해당 답변이 회사 문서를 기반으로 한 답변이라고 생각할 수도 있기 때문이다.

# 모의 면접

## 1. RAG 시스템에서 사용자가 답변에 피드백을 주었을 때 이 데이터가 단순한 ‘불만 접수’를 넘어 시스템 개선에 어떻게 활용될 수 있을까요?

피드백 데이터는 **RAG 시스템의 어느 단계에서 문제가 발생했는지 파악하는 데** 활용할 수 있다고 생각합니다.

예를 들어 “관련 없는 정보”가 많다면 검색 단계에서 잘못된 문서를 가져온 문제일 수 있고, 문서는 적절한데 “답변이 틀림”이 많다면 LLM이 문서를 잘못 해석했을 가능성이 있습니다.

그래서 프론트에서는 좋아요/싫어요뿐만 아니라 **싫어요를 누른 이유까지 수집하고, 질문·답변·참고 문서와 함께 전달하는 것**이 중요하다고 생각합니다.

이렇게 쌓인 데이터는 검색 알고리즘이나 답변 품질을 개선하는 데 활용할 수 있습니다.

## 2. RAG 답변에서 출처를 표시하는 것이 왜 단순한 ‘부가 기능’이 아니라 서비스의 신뢰도를 결정짓는 핵심 요소가 될까요?

AI는 틀린 내용도 그럴듯하게 답할 수 있기 때문에, 사용자가 답변만 보고 정확성을 판단하기는 어렵습니다.

하지만 출처가 있다면 사용자가 원본 문서를 직접 확인할 수 있고, **답변이 어떤 근거를 바탕으로 만들어졌는지 확인할 수 있습니다.**

특히 RAG의 핵심이 관련 문서를 찾아 근거 있는 답변을 만드는 것이기 때문에, 그 근거를 사용자에게 보여주는 것이 중요하다고 생각합니다.

그래서 출처 표시는 단순한 부가 기능이 아니라 **RAG 답변의 신뢰성을 높이는 중요한 기능**이라고 생각합니다.
