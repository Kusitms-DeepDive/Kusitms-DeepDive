# 5장. 넥스트.js의 핵심 개념과 실전 활용

## Q70. 넥스트.js에서 검색 엔진 최적화를 어떻게 개선할 수 있나요?

### 면접 답변

Next.js에서는 렌더링 전략과 메타데이터 관리 기능을 활용해 검색 엔진이 페이지를 발견하고 콘텐츠를 이해하기 쉽게 만들 수 있습니다. SSR은 요청 시점에, SSG는 빌드 시점에 주요 콘텐츠가 담긴 HTML을 생성하므로, 브라우저에서 JavaScript를 실행한 뒤에야 본문이 나타나는 방식보다 검색 엔진의 렌더링 부담을 줄일 수 있습니다. 실시간성이 중요한 공개 페이지는 SSR을, 변경이 적고 캐시 효율이 중요한 페이지는 SSG를 우선 검토합니다.

메타데이터는 Pages Router에서 `next/head`의 `Head` 컴포넌트로 관리하고, App Router에서는 `metadata` 객체와 `generateMetadata`로 관리합니다. 페이지마다 고유한 제목과 설명을 설정하고, canonical URL로 대표 주소를 명시하며, Open Graph 정보로 공유 미리보기를 구성합니다. App Router에서는 공통 메타데이터를 layout에 두고 페이지별 정보를 확장하거나 재정의할 수 있습니다.

여기에 의미 있는 HTML과 내부 링크, sitemap, 적절한 robots 설정, 구조화된 데이터, Core Web Vitals 개선을 함께 적용합니다. 다만 Next.js를 사용하거나 SSR을 적용했다고 검색 노출과 순위가 보장되는 것은 아닙니다. 실제 응답과 렌더링 결과, 색인 가능 여부와 사용자 성능 지표를 확인하고 콘텐츠 품질까지 함께 개선해야 합니다.

### 핵심 개념

#### 검색 엔진이 페이지를 처리하는 과정

- **크롤링(Crawling)**: 내부 링크·외부 링크·사이트맵 등으로 URL을 발견하고 페이지와 필요한 리소스를 요청
- **렌더링(Rendering)**: 응답 HTML과 필요한 JavaScript 등을 처리해 페이지의 콘텐츠 파악
- **색인(Indexing)**: 수집·해석한 내용을 분석해 검색에 사용할 정보로 저장. URL을 크롤링했다고 반드시 색인되는 것은 아님
- **검색 결과 노출**: 검색어와 콘텐츠의 관련성·품질 등 여러 요인에 따라 결정. 색인과 상위 노출도 구분 필요

**CSR과 서버에서 생성한 HTML의 차이**

- 일반적인 CSR 앱은 초기 HTML에 본문이 적고, JavaScript 실행과 데이터 요청이 끝난 뒤 주요 콘텐츠가 나타나는 구조
- Google은 JavaScript를 실행할 수 있지만 실행 대기·리소스 접근·렌더링 오류 등의 영향을 받을 수 있으며, 모든 검색 엔진과 공유 봇의 실행 능력이 같지는 않음
- SSR·SSG는 주요 콘텐츠를 서버에서 HTML로 제공해 클라이언트 JavaScript 실행에 대한 의존도를 낮추는 방법
- 서버에서 페이지를 렌더링해도 핵심 본문을 클라이언트의 `useEffect`에서만 가져온다면 해당 본문이 서버 응답에 포함되지 않을 수 있음

> 참고: [Google Search Central - JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

#### SSR·SSG·ISR의 선택 기준

| 방식 | HTML 생성·갱신 시점 | SEO 측면의 이점 | 적합한 상황과 주의점 |
| --- | --- | --- | --- |
| **SSR** | 요청 시 서버에서 생성 | 요청 시점의 데이터를 HTML로 전달 가능 | 최신 정보가 중요한 공개 페이지. 느린 서버·데이터 요청은 응답 지연을 키울 수 있음 |
| **SSG** | 빌드 시 미리 생성해 재사용 | 미리 생성한 HTML을 CDN 등으로 빠르게 제공 가능 | 블로그·문서·소개 페이지. 콘텐츠 갱신 시 재빌드나 별도 재검증 전략 필요 |
| **ISR** | 생성된 결과를 재사용하면서 시간·이벤트 등의 조건으로 재생성 | 정적 제공의 효율과 콘텐츠 갱신을 함께 고려 가능 | 상품·게시물처럼 주기적으로 바뀌는 공개 콘텐츠. 허용 가능한 오래된 데이터의 범위 결정 필요 |

- **페이지별 선택**: 하나의 사이트에서도 소개 페이지와 공개 상품 페이지의 최신성 요구가 다르므로 같은 전략을 일괄 적용할 필요는 없음
- **검색 대상부터 구분**: 로그인 후에만 접근하는 개인 대시보드는 공개 검색 노출보다 인증·개인화·사용자 경험이 우선
- **정적 생성과 동적 경로의 구분**: `/posts/[slug]`처럼 동적 세그먼트를 사용해도 페이지를 미리 생성할 수 있음. URL 모양이 SSR 여부를 결정하지는 않음
- **App Router의 세부 동작**: 정적·동적 렌더링, 스트리밍과 캐시 조합은 사용하는 API와 설정에 따라 달라짐. SSR·SSG 개념과 실제 프로젝트의 빌드 결과를 함께 확인
- **Client Component에 대한 오해**: `'use client'` 선언만으로 처음부터 빈 HTML만 전달된다고 단정할 수는 없음. 실제로 어떤 콘텐츠가 서버에서 미리 렌더링되는지가 중요

> 참고: [Next.js - Server-side Rendering](https://nextjs.org/docs/pages/building-your-application/rendering/server-side-rendering), [Next.js - Static Site Generation](https://nextjs.org/docs/pages/building-your-application/rendering/static-site-generation), [Next.js - Incremental Static Regeneration](https://nextjs.org/docs/app/guides/incremental-static-regeneration), [Next.js - Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)

#### 페이지별 메타데이터의 역할

| 항목 | 역할 | 주의할 점 |
| --- | --- | --- |
| **`title`** | 페이지 주제를 전달하는 제목 | 페이지마다 고유하고 본문과 일치하는 제목 작성. 사이트 전체에 같은 제목만 반복하지 않기 |
| **`description`** | 페이지 내용을 요약하는 설명 | 검색 결과의 설명으로 사용될 수 있지만, 검색 엔진이 본문에서 다른 내용을 선택할 수도 있음 |
| **canonical URL** | 유사하거나 중복된 콘텐츠의 대표 주소 제안 | 검색 엔진이 반드시 따르는 강제 지시가 아니며 리다이렉트·사이트맵·내부 링크와 일관성 필요 |
| **Open Graph·Twitter 카드** | 링크 공유 시 제목·설명·이미지 등 미리보기 제공 | 공유 표현을 위한 정보와 검색 순위 신호를 같은 것으로 단정하지 않기 |
| **robots 메타데이터** | 해당 페이지의 색인·링크 처리 등에 대한 지시 | `robots.txt`의 크롤링 제어와 역할 구분 |
| **`keywords`** | 일부 시스템에 키워드 정보 전달 가능 | Google 웹 검색은 meta keywords를 색인·순위에 사용하지 않으므로 핵심 최적화 수단으로 취급하지 않기 |

> 참고: [Google Search Central - Meta tags](https://developers.google.com/search/docs/crawling-indexing/special-tags), [Google Search Central - Snippets](https://developers.google.com/search/docs/appearance/snippet), [Google Search Central - Canonical URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [Next.js - Metadata and OG images](https://nextjs.org/docs/app/getting-started/metadata-and-og-images)

#### Pages Router: next/head

```tsx
// pages/about.tsx
import Head from 'next/head';

export default function AboutPage() {
  return (
    <>
      <Head>
        <title>회사 소개 | Example</title>
        <meta
          name="description"
          content="Example이 만드는 서비스와 팀을 소개합니다."
          key="description"
        />
        <link rel="canonical" href="https://example.com/about" />
        <meta property="og:title" content="회사 소개 | Example" key="og:title" />
      </Head>
      <main>
        <h1>회사 소개</h1>
        <p>Example이 만드는 서비스와 팀을 소개합니다.</p>
      </main>
    </>
  );
}
```

- **페이지별 선언**: 페이지 컴포넌트에서 제목·설명·canonical·공유 정보 등을 직접 구성
- **데이터 기반 구성**: `getStaticProps`나 `getServerSideProps`에서 받은 데이터를 사용해 페이지별 메타데이터 생성 가능
- **중복 관리**: 중복될 수 있는 meta 태그에는 일관된 `key`를 사용. `title` 등 일부 태그는 Next.js가 별도로 중복 처리
- **페이지 이동 시 주의**: 이전 페이지가 넣었던 태그가 계속 남는다고 가정하지 말고 각 페이지에 필요한 정보를 정의
- **적용 범위**: Pages Router의 API이며 App Router에서는 Metadata API 사용

> 참고: [Next.js - Head](https://nextjs.org/docs/pages/api-reference/components/head)

#### App Router: 정적 metadata와 동적 generateMetadata

**공통 정보는 layout에서 선언**

```tsx
// app/layout.tsx
import type { Metadata } from 'next';
import type { ReactNode } from 'react';

export const metadata: Metadata = {
  metadataBase: new URL('https://example.com'),
  title: {
    default: 'Example',
    template: '%s | Example',
  },
  description: '프런트엔드 개발 지식을 공유하는 사이트입니다.',
};

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="ko">
      <body>{children}</body>
    </html>
  );
}
```

- **정적 `metadata`**: 요청 데이터와 관계없이 정해진 제목·설명 등을 객체로 선언
- **동적 `generateMetadata`**: 경로 매개변수나 게시물·상품 데이터에 따라 메타데이터 생성
- **서버에서 선언**: 두 export 모두 Server Component에서 지원. 상호작용이 필요하면 해당 UI를 Client Component로 분리
- **같은 세그먼트에서 택일**: 하나의 layout이나 page에서 `metadata`와 `generateMetadata`를 동시에 export할 수는 없음
- **상속과 덮어쓰기**: 상위 layout의 공통값을 하위에서 재정의. `openGraph` 같은 중첩 객체는 자동으로 깊게 병합되지 않으므로 필요한 필드를 명시적으로 확장
- **URL 기준**: `metadataBase`는 canonical·공유 이미지 등 상대 URL을 절대 URL로 해석할 기준. 각 페이지의 대표 경로는 따로 지정

**게시물 데이터로 메타데이터와 본문을 함께 구성**

아래 예시는 공개 게시물 API가 `title`, `excerpt`, `content`, `image`를 반환하는 상황을 가정합니다. `image`는 공개 이미지 URL이며, 오류 처리와 콘텐츠 데이터 검증은 실제 API 계약에 맞게 조정해야 합니다.

```tsx
// app/posts/[slug]/page.tsx
import type { Metadata } from 'next';
import { notFound } from 'next/navigation';

type Props = { params: Promise<{ slug: string }> };
type Post = {
  title: string;
  excerpt: string;
  content: string;
  image: string;
};

async function getPost(slug: string): Promise<Post> {
  const res = await fetch(
    `https://api.example.com/posts/${encodeURIComponent(slug)}`,
    { next: { revalidate: 300 } },
  );

  if (res.status === 404) notFound();
  if (!res.ok) throw new Error('게시물을 가져오지 못했습니다.');

  return res.json();
}

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params;
  const post = await getPost(slug);
  const path = `/posts/${encodeURIComponent(slug)}`;

  return {
    title: post.title,
    description: post.excerpt,
    alternates: { canonical: path },
    openGraph: {
      type: 'article',
      title: post.title,
      description: post.excerpt,
      url: path,
      images: [post.image],
    },
  };
}

export default async function PostPage({ params }: Props) {
  const { slug } = await params;
  const post = await getPost(slug);

  return (
    <main>
      <article>
        <h1>{post.title}</h1>
        <p>{post.content}</p>
      </article>
    </main>
  );
}
```

- **비동기 `params`**: 최신 App Router API에 맞춰 `params`를 기다린 뒤 사용
- **동적 메타데이터와 SSR의 구분**: `generateMetadata`를 사용했다는 이유만으로 반드시 요청마다 전체 페이지를 렌더링하는 것은 아님. 사전 렌더링·캐시 설정에 따라 결정
- **중복 요청 완화**: 렌더링 중 동일한 `fetch` 요청은 메모이제이션될 수 있음. DB 호출 등에는 React의 `cache`를 검토하며 요청 내 중복 제거와 장기 데이터 캐시를 구분
- **갱신 정책**: 예시의 `revalidate: 300`은 게시물 데이터의 시간 기반 재검증 설정. 메타데이터와 본문의 최신성 요구에 맞게 결정
- **스트리밍 메타데이터**: 동적 렌더링에서는 메타데이터가 초기 UI 뒤에 스트리밍될 수 있음. HTML의 head에서 정보를 기대하는 일부 봇에는 별도 동작이 적용되므로, 모든 응답의 초기 head에 모든 정보가 있다고 단정하지 않기

> 참고: [Next.js - generateMetadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata), [Next.js - Metadata and OG images](https://nextjs.org/docs/app/getting-started/metadata-and-og-images), [Next.js - fetch](https://nextjs.org/docs/app/api-reference/functions/fetch)

#### 사이트맵과 robots 설정

| 수단 | 목적 | 한계와 주의점 |
| --- | --- | --- |
| **sitemap.xml** | 검색 대상 URL과 갱신 정보 등을 알려 URL 발견 지원 | 포함했다고 크롤링·색인·검색 노출이 보장되지는 않음 |
| **robots.txt** | 협조적인 크롤러에게 접근할 경로 범위 안내 | 크롤링을 막아도 URL 자체가 검색 결과에 나타날 수 있으며 보안 수단도 아님 |
| **`noindex`** | 검색 엔진에 해당 페이지를 색인하지 않도록 지시 | 크롤러가 응답을 읽어야 확인 가능. robots.txt로 접근까지 막으면 지시를 읽지 못할 수 있음 |
| **인증·인가** | 비공개 콘텐츠의 실제 접근 제어 | 관리자·개인정보 페이지 보호는 robots 설정이 아니라 서버의 권한 검증으로 처리 |

```ts
// app/sitemap.ts
import type { MetadataRoute } from 'next';

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    { url: 'https://example.com' },
    { url: 'https://example.com/about' },
  ];
}
```

- **파일 기반 생성**: App Router에서 `app/sitemap.ts`와 `app/robots.ts` 등의 규칙으로 생성 가능. Pages Router에서는 정적 파일이나 별도 생성 과정으로 구성 가능
- **공개 URL 선별**: 로그인 전용 페이지, 중복 주소, 삭제된 페이지를 사이트맵에 무조건 포함하지 않기
- **정확한 갱신 시각**: `lastModified`를 넣는다면 실제 콘텐츠 변경 시점을 사용. 생성할 때마다 현재 시각으로 바꾸어 최신 정보처럼 표시하지 않기
- **배포 환경 분리**: 프로덕션에 `noindex`가 남거나 스테이징 사이트가 색인되는 실수 확인. 스테이징에 민감한 정보가 있다면 접근 제어도 적용

> 참고: [Next.js - sitemap.xml](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/sitemap), [Next.js - robots.txt](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots), [Google Search Central - Sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview), [Google Search Central - robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/intro), [Google Search Central - noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

#### 콘텐츠 구조·URL·구조화된 데이터

- **의미에 맞는 HTML**: `main`, `nav`, `article`, `section` 등으로 구조를 표현하고 제목 계층과 본문을 명확히 구성. 태그만 바꾸기보다 실제 콘텐츠와 구조의 일치가 중요
- **내부 링크**: 탐색 대상 페이지는 유효한 `href`를 가진 링크로 연결. 사용자가 버튼을 클릭해야만 발견되는 경로에만 의존하지 않기
- **일관된 URL**: 읽을 수 있는 경로를 사용하고 같은 콘텐츠의 추적 파라미터·변형 주소가 불필요하게 늘어나지 않도록 관리
- **중복 주소 처리**: 대표 URL을 canonical·사이트맵·내부 링크에 일관되게 반영. 주소가 영구 변경됐다면 적절한 리다이렉트도 검토
- **이미지와 접근성**: 의미 있는 이미지의 대체 텍스트, 적절한 링크 이름과 heading 구성으로 콘텐츠 이해와 이용 지원. ARIA 속성을 추가하는 것만으로 SEO나 접근성이 완성되지는 않음
- **구조화된 데이터**: Article·Product 등 페이지 유형에 맞는 JSON-LD로 제목·작성자·상품 정보를 명시. 화면에 실제로 제공하는 내용과 일치시켜야 함
- **리치 결과의 한계**: 지원되는 스키마와 검색 엔진의 정책을 충족해야 하며, 마크업이 유효해도 특별한 검색 결과 표시가 보장되지는 않음
- **JSON-LD 출력**: Next.js에서는 페이지·layout의 `script type="application/ld+json"` 등으로 제공 가능. 외부 데이터를 삽입할 때는 `<` 이스케이프 등 안전한 직렬화 고려

> 참고: [Google Search Central - JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics), [Google Search Central - Canonical URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [Google Search Central - Structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data), [Google Search Central - Structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [Next.js - JSON-LD](https://nextjs.org/docs/app/guides/json-ld)

#### 페이지 성능과 Core Web Vitals

| 지표 | 측정 대상 | 좋은 경험의 기준 | 개선 방향 |
| --- | --- | --- | --- |
| **LCP** | 주요 콘텐츠가 표시되는 시점 | 2.5초 이하 | 서버 응답 지연, 주요 이미지의 크기·발견 시점, 렌더링 차단 자원 개선 |

- **평가 기준**: 실제 방문의 75번째 백분위수를 기준으로 모바일과 데스크톱을 나누어 확인
- **Next.js의 지원**: 이미지·폰트 최적화, 경로별 코드 분할과 서버 렌더링 등을 활용하되, 기능을 사용했다는 사실보다 실제 사용자 지표 개선을 확인
- **SSR만으로 부족한 이유**: 서버 응답이 느리거나 하이드레이션과 클라이언트 실행이 무거우면 좋은 사용자 경험을 얻기 어려움
- **측정 도구의 구분**: Lighthouse 등 실험실 진단은 개선 지점 탐색에 활용하고, Search Console·CrUX·실사용자 측정으로 현장 성능 확인
- **순위 보장과 구분**: 좋은 Core Web Vitals는 사용자 경험과 검색 성과에 도움이 되지만 관련성·콘텐츠 품질 등 다른 요소를 대체하지는 못함

#### 배포 후 확인할 사항

- **응답과 렌더링**: 주요 본문이 서버 HTML·스트리밍 결과와 최종 렌더링에 포함되는지 확인. 개발자 도구에서 클라이언트 렌더링 후 보이는 화면만으로 판단하지 않기
- **메타데이터**: 페이지별 제목·설명·canonical·공유 이미지가 실제 배포 도메인과 콘텐츠에 맞는지 확인
- **검색 접근성**: 공개 URL이 인증·robots 설정·`noindex`에 의해 잘못 차단되지 않는지 확인
- **상태와 이동**: 삭제·없는 페이지와 영구 이전 경로를 적절히 처리하고, 빈 오류 화면을 정상 페이지처럼 계속 제공하지 않는지 확인
- **검색 엔진 관점의 검증**: Search Console URL 검사에서 수집·렌더링·색인 상태를 확인하고, Rich Results Test로 지원되는 구조화된 데이터 검증
- **공유 봇 검증**: 메타데이터 스트리밍과 봇별 처리 차이를 고려해 실제 공유 미리보기도 점검
- **지속적인 개선**: 사이트맵 제출이나 성능 점수 하나로 완료를 판단하지 말고 콘텐츠 변경·배포 후 검색 상태와 실제 성능을 관찰

### 모의 면접

#### 1. 넥스트.js에서 SSR과 SSG가 검색 엔진 최적화에 유리한 이유는 무엇이며 각각 어떤 상황에 적합한가요?

두 방식 모두 주요 콘텐츠가 포함된 HTML을 서버에서 생성하므로, 검색 엔진이 클라이언트 JavaScript 실행에 의존해 본문을 만들어야 하는 부담을 줄일 수 있습니다. Google처럼 JavaScript를 실행하는 검색 엔진에도 리소스 로딩이나 실행 오류로 콘텐츠가 누락될 가능성을 줄이는 데 도움이 됩니다.

SSR은 요청 시점에 HTML을 생성하므로 최신 정보가 중요한 공개 페이지에 적합하지만 서버와 데이터 응답 속도를 관리해야 합니다. SSG는 빌드 때 HTML을 생성해 재사용하므로 블로그·문서·소개 페이지처럼 변경이 적은 콘텐츠에 적합하고 빠르게 제공하기 좋습니다. 갱신이 필요한 콘텐츠라면 ISR도 검토하겠습니다. 다만 렌더링 방식만으로 순위를 보장할 수는 없으므로 콘텐츠 품질, 메타데이터와 실제 색인 상태도 함께 확인하겠습니다.

#### 2. 페이지 라우터의 `<Head>`와 앱 라우터의 Metadata API를 사용했을 때 SEO 최적화에서 얻을 수 있는 주요 장점은 무엇인가요?

Pages Router의 `Head`는 페이지에서 제목·설명·canonical과 공유용 메타 태그를 직접 정의할 수 있어 페이지 특성에 맞는 정보를 제공하기 좋습니다. 서버에서 가져온 데이터를 props로 전달하면 게시물이나 상품별 메타데이터도 구성할 수 있습니다.

App Router의 Metadata API는 공통 정보를 layout에서 관리하고 하위 페이지가 필요한 값을 재정의할 수 있어 일관성과 유지보수성이 좋습니다. 정적인 값은 `metadata`, 데이터에 따라 달라지는 값은 `generateMetadata`로 선언하며, TypeScript의 `Metadata` 타입과 파일 기반 메타데이터 규칙도 활용할 수 있습니다. 이를 통해 검색 엔진에는 페이지 주제와 대표 주소를, 공유 서비스에는 적절한 미리보기 정보를 제공할 수 있습니다. 실제 검색 노출을 위해서는 본문·크롤링·색인 설정도 함께 검증해야 합니다.

## Q71. 넥스트.js의 라우팅 시스템은 무엇인가요?

### 면접 답변

Next.js의 라우팅 시스템은 파일과 폴더 구조를 URL 경로에 연결하는 파일 시스템 기반 라우팅입니다. Pages Router에서는 `pages/about.tsx`가 `/about`에 대응하고, App Router에서는 `app/about/page.tsx`가 같은 경로에 대응합니다. App Router는 폴더를 경로 세그먼트로 사용하면서 `page`, `layout`, `loading` 같은 파일 규칙으로 화면과 공통 레이아웃, 로딩 UI도 함께 구성합니다.

페이지 이동에는 일반적으로 `next/link`의 `Link`를 사용합니다. 실제 링크 요소를 제공하면서 클라이언트 측 화면 전환과 프리페칭을 지원해 전체 문서를 다시 불러오는 부담을 줄입니다. App Router에서는 공유 레이아웃을 재사용하고 필요한 서버 컴포넌트 결과를 받아 변경된 부분을 반영할 수 있습니다. 클라이언트에서 이동한다고 모든 렌더링과 데이터 처리가 브라우저에서만 일어나는 것은 아닙니다.

이벤트 처리 결과나 조건에 따라 이동해야 한다면 `useRouter`를 사용합니다. Pages Router는 `next/router`, App Router는 `next/navigation`에서 가져오며, App Router의 현재 경로·검색 파라미터·동적 세그먼트는 각각 `usePathname`, `useSearchParams`, `useParams`로 읽습니다. 단순 탐색은 `Link`, 로직에 따른 이동은 라우터 메서드로 구분하고, 프리페칭 범위와 상태 유지 조건을 고려해 사용자 경험을 설계합니다.

### 핵심 개념

#### Pages Router와 App Router의 파일 규칙

| 구분 | Pages Router | App Router |
| --- | --- | --- |
| **기준 디렉터리** | `pages` 또는 `src/pages` | `app` 또는 `src/app` |
| **페이지 정의** | 경로에 대응하는 파일에서 컴포넌트 export | 경로 폴더 안의 `page.tsx` 등에서 컴포넌트 export |
| **루트 경로** | `pages/index.tsx` → `/` | `app/page.tsx` → `/` |
| **중첩 경로** | `pages/dashboard/settings.tsx` → `/dashboard/settings` | `app/dashboard/settings/page.tsx` → `/dashboard/settings` |
| **공통 UI** | `_app`과 페이지별 layout 패턴 등으로 구성 | 중첩 `layout.tsx` 규칙으로 구성 |
| **HTTP 엔드포인트** | `pages/api/hello.ts` → `/api/hello` | `app/api/hello/route.ts` → `/api/hello` |
| **라우터 훅** | `useRouter` from `next/router` | `useRouter` 등 from `next/navigation` |

- **현재도 구분이 필요한 두 방식**: Pages Router를 Next.js 12 이하에서만 쓸 수 있는 기능으로 이해하면 부정확. 버전과 별개로 프로젝트가 사용하는 라우터 확인
- **App Router의 경로 공개**: 폴더만 만들었다고 페이지가 생기는 것은 아니며, 해당 경로를 제공할 `page`나 `route` 등의 파일 필요
- **파일 배치의 차이**: App Router의 경로 폴더에는 관련 컴포넌트·유틸리티를 함께 둘 수 있음. 임의의 `.tsx` 파일이 모두 페이지가 되는 것은 아님
- **페이지와 API의 구분**: `page.tsx`는 화면, `route.ts`는 HTTP 요청 처리 담당. 같은 세그먼트에 두 파일을 함께 두어 같은 URL을 중복 정의하지 않기
- **두 라우터의 공존**: 점진적인 이전은 가능하지만 동일 URL에 서로 다른 페이지를 중복 정의하지 않도록 관리

> 참고: [Next.js - Pages and Layouts](https://nextjs.org/docs/pages/building-your-application/routing/pages-and-layouts), [Next.js - Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages), [Next.js - Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)

#### App Router의 경로와 화면 구성

```text
app/
  layout.tsx                 → 앱의 루트 레이아웃
  page.tsx                   → /
  about/
    page.tsx                 → /about
  dashboard/
    layout.tsx               → dashboard 하위의 공통 UI
    loading.tsx              → 하위 화면의 로딩 UI
    page.tsx                 → /dashboard
    settings/
      page.tsx               → /dashboard/settings
  posts/
    [slug]/
      page.tsx               → /posts/hello 등
  (marketing)/
    pricing/
      page.tsx               → /pricing
```

- **`page.tsx`**: 해당 URL에서 보여 줄 페이지 UI 정의
- **`layout.tsx`**: `children`을 감싸 공통 화면 구성. 루트 layout에는 `html`과 `body` 포함
- **`loading.tsx`**: 해당 경로의 페이지와 하위 내용을 위한 Suspense 기반 로딩 UI 구성. 느린 응답이 있을 때 즉시 피드백 제공에 도움
- **Route Group `(이름)`**: 파일을 논리적으로 묶되 폴더 이름을 URL에 포함하지 않는 규칙. 위 예시의 주소는 `/(marketing)/pricing`이 아닌 `/pricing`
- **공유 레이아웃 재사용**: `/dashboard`에서 `/dashboard/settings`로 이동할 때 같은 dashboard layout을 재사용해 내비게이션·사이드바 등의 유지에 도움
- **`template.tsx`와의 차이**: layout과 비슷하게 자식을 감싸지만 관련 세그먼트가 바뀌면 새 인스턴스로 마운트될 수 있어 내부 상태 초기화·effect 재실행이 필요한 경우 검토
- **상태 유지의 범위**: 유지되는 공유 레이아웃과 실제로 남아 있는 클라이언트 컴포넌트가 기준. 페이지를 이동해도 이전 페이지의 모든 상태가 항상 보존된다는 의미는 아님
- **전체 문서 이동의 예외**: 서로 다른 루트 layout을 사용하는 경로 사이의 이동 등은 전체 페이지 로드를 일으킬 수 있음

> 참고: [Next.js - layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout), [Next.js - loading.js](https://nextjs.org/docs/app/api-reference/file-conventions/loading), [Next.js - template.js](https://nextjs.org/docs/app/api-reference/file-conventions/template), [Next.js - Route Groups](https://nextjs.org/docs/app/api-reference/file-conventions/route-groups)

#### 동적 세그먼트와 쿼리 파라미터

| 규칙 | App Router 예시 | 대응 URL과 값 |
| --- | --- | --- |
| **`[slug]`** | `app/posts/[slug]/page.tsx` | `/posts/hello` → `slug: 'hello'` |
| **`[...slug]`** | `app/docs/[...slug]/page.tsx` | `/docs/a/b` → `slug: ['a', 'b']`. 한 개 이상의 세그먼트 |
| **`[[...slug]]`** | `app/shop/[[...slug]]/page.tsx` | `/shop`도 대응하며 이때 `slug`는 `undefined` |
| **검색 파라미터** | `/products?category=books&page=2` | 경로는 `/products`, 검색 조건은 `category`, `page`로 별도 처리 |

- **Pages Router의 대응 규칙**: `pages/posts/[slug].tsx`, `pages/docs/[...slug].tsx`처럼 파일명에 동적 세그먼트 표현
- **App Router의 서버 페이지**: `params`로 동적 세그먼트, `searchParams`로 검색 파라미터 접근. 최신 API에서는 Promise 형태이므로 `await` 등으로 값을 읽기
- **App Router의 클라이언트**: 동적 세그먼트는 `useParams`, 검색 파라미터는 `useSearchParams`로 구분
- **값의 검증**: URL에서 받은 값은 외부 입력. 페이지 번호·카테고리·허용된 ID 형식 등을 검증하고 없는 자원은 적절히 처리
- **인코딩**: 경로의 한 세그먼트에 값을 넣을 때는 `encodeURIComponent`, 검색 문자열을 만들 때는 `URLSearchParams` 등으로 특수문자 처리
- **라우팅과 렌더링의 구분**: 동적 URL이라고 매번 SSR하는 것은 아님. 동적 경로의 사전 생성·캐시 여부는 별도 결정

> 참고: [Next.js - Dynamic Route Segments](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes), [Next.js - page.js](https://nextjs.org/docs/app/api-reference/file-conventions/page), [Next.js - useParams](https://nextjs.org/docs/app/api-reference/functions/use-params)

#### Link를 이용한 선언적 이동

```tsx
// app/components/navigation.tsx
import Link from 'next/link';

export default function Navigation() {
  return (
    <nav aria-label="주요 메뉴">
      <Link href="/">홈</Link>
      <Link href="/about">소개</Link>
      <Link href="/posts/hello">게시물</Link>
      <Link href={{ pathname: '/products', query: { category: 'books' } }}>
        도서 상품
      </Link>
      <Link href="/reports" prefetch={false}>
        보고서
      </Link>
    </nav>
  );
}
```

- **선언적 탐색**: 목적지가 정해진 메뉴·게시물·상품 링크에 사용. 클릭 이벤트에서 `router.push`를 직접 호출할 필요 없이 이동 의도 표현
- **HTML 링크의 의미 유지**: `a` 요소 기반으로 링크 주소 확인, 키보드 탐색, 새 탭 열기 등 기본 브라우저 동작 활용
- **클라이언트 측 이동**: 지원되는 내부 경로에서는 전체 문서를 다시 로드하지 않고 페이지 전환 가능
- **옵션**: `replace`로 현재 방문 기록 교체, `scroll={false}`로 기본 스크롤 조정 방지, `prefetch`로 선행 로딩 정책 조절
- **서버 컴포넌트에서도 사용**: `Link`를 렌더링하려고 부모 파일에 무조건 `'use client'`를 붙일 필요는 없음
- **도구 선택**: 일반적인 외부 사이트·파일 다운로드는 목적에 맞는 `a` 요소도 활용. 내부 탐색과 외부 문서 이동을 구분

> 참고: [Next.js - Link Component](https://nextjs.org/docs/app/api-reference/components/link)

#### 클라이언트 측 화면 전환이 이루어지는 방식

```text
초기 방문
  → 서버에서 생성한 HTML과 필요한 자원 수신
  → 브라우저에 화면 표시, 상호작용할 컴포넌트 하이드레이션

App Router의 일반적인 내부 이동
  → Link 클릭 또는 router.push
  → 선행 로딩·클라이언트 캐시 확인, 필요하면 서버 결과 요청
  → 공유 레이아웃 재사용
  → 변경된 경로의 결과 반영
```

- **서버 역할 유지**: App Router의 이동에는 React Server Component Payload가 사용될 수 있음. 문서 전체를 새로 요청하지 않는 것과 서버를 전혀 사용하지 않는 것은 다름
- **부분 업데이트**: 변경된 경로에 필요한 내용을 반영해 공유 UI를 유지하고 불필요한 재로딩 감소
- **로딩 피드백**: 데이터나 서버 결과가 준비되지 않았다면 `loading.tsx`·Suspense 등으로 대기 상태 제공
- **성능의 조건**: 프리페칭·캐시가 부족하거나 서버 응답이 느리면 화면 전환도 기다림이 생길 수 있음. SPA처럼 이동한다는 사실만으로 즉시 전환이 보장되지는 않음

> 참고: [Next.js - Linking and Navigating](https://nextjs.org/docs/app/getting-started/linking-and-navigating), [Next.js - loading.js](https://nextjs.org/docs/app/api-reference/file-conventions/loading)

#### 프리페칭의 범위와 비용

- **의미**: 사용자가 이동하기 전에 다음 경로에 필요한 코드·데이터·서버 컴포넌트 결과 등을 미리 가져와 이동 시 대기 감소
- **자동 실행**: 일반적으로 프로덕션에서 `Link`가 뷰포트에 들어올 때 수행. 개발 서버에서 보이지 않는다고 기능이 고장 났다고 판단하지 않기
- **App Router의 기본 정책**: `prefetch`의 기본값은 `auto` 또는 `null`이며 경로·로딩 경계 등에 따라 범위 결정. 정적 경로는 전체, 동적 경로는 생략하거나 `loading` 경계까지 일부를 가져오는 방식 등이 적용
- **설정에 따른 차이**: Partial Prefetching 등 추가 설정에서는 기본 범위가 달라질 수 있으므로 모든 링크가 항상 전체 페이지를 미리 받는다고 설명하지 않기
- **`prefetch={true}`**: App Router에서 선행 로딩을 적극적으로 수행하도록 지정. 실제 포함 범위는 사용하는 기능과 설정 확인
- **`prefetch={false}`의 라우터 차이**: App Router에서는 뷰포트·hover 자동 프리페칭을 끄지만, Pages Router에서는 뷰포트 프리페칭을 꺼도 hover 시 로딩할 수 있음
- **명령형 이동**: `router.push`를 호출할 버튼이 있다는 이유만으로 `Link`처럼 자동 선행 로딩되지는 않음. 필요하면 `router.prefetch`로 명시적 요청
- **실무 판단**: 링크가 많은 목록이나 접근 가능성이 낮은 무거운 화면은 선행 요청 비용 검토. 체감 이동 속도와 불필요한 트래픽·서버 작업을 함께 측정

> 참고: [Next.js - Link Component: App Router](https://nextjs.org/docs/app/api-reference/components/link#prefetch), [Next.js - Link: Pages Router](https://nextjs.org/docs/pages/api-reference/components/link#prefetch), [Next.js - Linking and Navigating](https://nextjs.org/docs/app/getting-started/linking-and-navigating)

#### useRouter와 경로 조회 훅

| 목적 | Pages Router | App Router |
| --- | --- | --- |
| **이동 메서드** | `useRouter` from `next/router` | `useRouter` from `next/navigation` |
| **현재 경로** | `router.pathname`은 페이지 패턴, `router.asPath`는 표시 경로 등에 사용 | `usePathname()`으로 URL의 pathname 조회 |
| **동적 세그먼트** | `router.query`에 포함 | `useParams()` |
| **검색 파라미터** | `router.query`에 포함 | `useSearchParams()` |

예를 들어 `/posts/hello?sort=latest`에서 Pages Router의 `pathname`은 `/posts/[slug]`일 수 있지만, App Router의 `usePathname()`은 `/posts/hello`를 반환합니다. Pages Router의 `query`에는 `slug`와 `sort`가 함께 들어가고, App Router에서는 동적 세그먼트와 검색 파라미터를 다른 훅으로 읽습니다.

- **App Router의 훅 사용 위치**: Client Component에서 사용. Server Component에서는 page의 props나 서버 전용 API 등 적합한 수단 선택
- **Pages Router의 준비 상태**: 사전 렌더링 단계에서 `query`가 비어 있을 수 있음. 라우터 필드에 의존하는 effect에서는 `isReady` 등을 고려
- **App Router의 API 차이**: `router.pathname`, `router.query`, `router.events`를 그대로 사용할 수 있다고 가정하지 않기
- **경로에 따른 UI**: layout 안에서 현재 경로에 맞춰 활성 메뉴를 표시하려면 Client Component의 `usePathname` 등 활용. 유지되는 서버 layout이 매 이동마다 새 경로를 읽어 다시 실행된다고 가정하지 않기

> 참고: [Next.js - useRouter: Pages Router](https://nextjs.org/docs/pages/api-reference/functions/use-router), [Next.js - usePathname](https://nextjs.org/docs/app/api-reference/functions/use-pathname), [Next.js - useParams](https://nextjs.org/docs/app/api-reference/functions/use-params), [Next.js - layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)

#### 명령형 이동과 방문 기록

| App Router 메서드 | 역할 | 사용을 검토할 상황 |
| --- | --- | --- |
| **`push(href)`** | 새 방문 기록을 추가하면서 이동 | 사용자가 이전 단계로 돌아갈 수 있어야 하는 이동 |
| **`replace(href)`** | 현재 기록을 교체하면서 이동 | 필터의 잦은 갱신처럼 기록을 계속 쌓고 싶지 않은 경우 |
| **`back()`·`forward()`** | 브라우저 기록의 앞뒤로 이동 | 실제 방문 이력에 따른 이전·다음 이동 |
| **`prefetch(href)`** | 지정 경로를 선행 로딩 | 조건에 따라 이동할 화면을 미리 준비 |
| **`refresh()`** | 현재 경로의 서버 결과를 다시 요청·반영 | 변경 이후 서버 컴포넌트 결과를 다시 확인 |

- **`back`의 의미**: 앱에서 정한 부모 경로가 아니라 실제 브라우저 방문 이력 기준. 반드시 목록으로 돌아가야 한다면 목록 URL로 이동하도록 설계
- **`refresh`와 새로고침의 차이**: 문서 전체를 재로드하는 것과 다르며, 영향받지 않은 클라이언트 상태와 스크롤 등을 유지하면서 서버 결과 병합
- **서버 캐시와의 구분**: `refresh`가 서버의 데이터 캐시를 무조건 무효화하지는 않음. 캐시된 결과를 받을 수 있으므로 필요하면 서버에서 `revalidatePath`·`revalidateTag` 등으로 갱신 정책 적용
- **입력 URL 검증**: 외부 입력을 검증 없이 `push`·`replace`에 전달하지 않기. 의도하지 않은 외부 이동이나 `javascript:` URL 실행 등의 위험 고려
- **서버에서의 이동**: Server Component·Server Action 등에서는 상황에 맞게 `redirect`를 사용. 서버 인증 판단을 클라이언트 훅으로만 대체하지 않기

> 참고: [Next.js - useRouter: App Router](https://nextjs.org/docs/app/api-reference/functions/use-router), [Next.js - Redirecting](https://nextjs.org/docs/app/guides/redirecting)

#### App Router에서 검색 조건을 URL로 관리하는 예시

아래는 App Router만 사용하는 프로젝트에서 카테고리 버튼으로 현재 경로의 검색 파라미터를 갱신하는 예시입니다. URL에 조건을 남기면 새로고침·링크 공유에도 같은 상태를 재현하기 좋습니다.

```tsx
// app/products/category-filter.tsx
'use client';

import { usePathname, useRouter, useSearchParams } from 'next/navigation';

export default function CategoryFilter() {
  const router = useRouter();
  const pathname = usePathname();
  const searchParams = useSearchParams();

  function selectCategory(category: string) {
    const nextParams = new URLSearchParams(searchParams.toString());
    nextParams.set('category', category);
    nextParams.delete('page'); // 필터 변경 시 페이지 번호 초기화

    router.replace(`${pathname}?${nextParams.toString()}`, { scroll: false });
  }

  return (
    <div>
      <p>선택한 카테고리: {searchParams.get('category') ?? '전체'}</p>
      <button type="button" onClick={() => selectCategory('books')}>
        도서 보기
      </button>
    </div>
  );
}
```

```tsx
// app/products/page.tsx
import { Suspense } from 'react';
import CategoryFilter from './category-filter';

export default function ProductsPage() {
  return (
    <main>
      <h1>상품 목록</h1>
      <Suspense fallback={<p>필터를 준비하고 있습니다.</p>}>
        <CategoryFilter />
      </Suspense>
    </main>
  );
}
```

- **읽기 전용 검색 파라미터**: `useSearchParams` 결과를 직접 수정하지 않고 `URLSearchParams`로 복사해 변경
- **기존 조건 보존**: 수정할 항목 외의 검색 파라미터는 유지. 요구사항에 따라 페이지 번호처럼 함께 초기화할 값은 명시적으로 제거
- **방문 기록 선택**: 예시는 필터 변경마다 이력을 쌓지 않도록 `replace` 사용. 뒤로 가기로 필터 변경을 되돌려야 한다면 `push` 검토
- **정적 페이지의 Suspense**: 정적으로 사전 렌더링하는 페이지에서 `useSearchParams`를 호출하는 Client Component는 Suspense 경계로 감싸야 함. 개발 서버에서 동작했다는 사실만으로 프로덕션 빌드 성공을 판단하지 않기
- **서버 데이터와 연결**: 실제 상품 목록을 서버에서 조회한다면 page의 `searchParams`를 읽어 조건을 검증하고 조회. 위 예시는 필터 UI와 URL 갱신만 표현

> 참고: [Next.js - useSearchParams](https://nextjs.org/docs/app/api-reference/functions/use-search-params), [Next.js - usePathname](https://nextjs.org/docs/app/api-reference/functions/use-pathname)

### 모의 면접

#### 1. 넥스트.js에서 페이지 라우터와 앱 라우터의 라우팅 방식과 디렉터리 구조의 차이는 무엇인가요?

두 방식 모두 파일 시스템 기반이지만, Pages Router는 `pages` 아래의 파일이 페이지 경로에 대응하고 App Router는 `app` 아래의 폴더가 경로 세그먼트를 구성하며 그 안의 `page` 파일이 화면을 정의합니다. 예를 들어 `/about`은 각각 `pages/about.tsx`와 `app/about/page.tsx`로 구성합니다.

공통 UI도 Pages Router에서는 `_app`이나 페이지별 layout 패턴으로 구성하고, App Router에서는 중첩 `layout` 파일로 구성합니다. App Router는 `loading`과 Route Group 등으로 경로별 UI와 구조를 함께 관리할 수 있습니다. 또한 라우팅 훅도 달라 Pages Router의 `next/router`를 App Router에서 그대로 사용하지 않고, `next/navigation`의 이동·경로 조회 API로 나누어 사용합니다.

#### 2. next/link와 useRouter 훅의 역할과 장단점은 무엇이며 어떤 상황에서 각각을 사용하는 것이 적합한가요?

`next/link`의 `Link`는 목적지가 정해진 탐색을 선언적으로 표현하고, HTML 링크의 기본 동작과 Next.js의 클라이언트 측 이동·자동 프리페칭을 활용할 수 있다는 장점이 있습니다. 메뉴·게시물 제목·상품 링크처럼 사용자가 목적지를 선택하는 경우에 우선 사용하겠습니다. 다만 폼 처리 결과처럼 로직을 수행한 뒤 이동 여부와 목적지가 결정되는 상황은 별도로 처리해야 합니다.

`useRouter`는 이벤트나 조건에 따라 `push`, `replace`, `back` 등의 메서드로 이동을 제어할 때 적합합니다. 예를 들어 저장이 성공한 뒤 상세 화면으로 이동하거나 검색 조건 변경 시 방문 기록을 교체할 수 있습니다. 대신 버튼에 `push`를 연결하는 것만으로 링크의 의미와 자동 프리페칭을 얻는 것은 아니므로 단순 탐색에는 `Link`를 사용하고, 필요한 경우에만 명령형 이동과 `prefetch`를 적용하겠습니다.

## Q73. 넥스트.js에서 API 루트를 사용하는 목적은 무엇인가요?

### 면접 답변

Next.js의 API 라우트는 같은 프로젝트 안에 서버에서 실행되는 HTTP 엔드포인트를 정의하는 기능입니다. Pages Router에서는 `pages/api` 아래의 API Routes를, App Router에서는 `route.ts` 등의 Route Handlers를 사용합니다. 클라이언트는 이 엔드포인트를 호출하고, 서버는 외부 서비스 요청이나 데이터베이스 접근 등을 처리한 뒤 필요한 결과를 반환합니다.

주요 목적은 비밀 키 같은 서버 전용 정보를 브라우저에 노출하지 않고 외부 API를 중계하거나, 인증과 권한 확인을 거쳐 데이터를 조회·변경하거나, 여러 서비스의 결과를 화면에 맞게 조합하는 것입니다. 특히 프런트엔드에 필요한 데이터 형태를 제공하는 BFF 계층으로 활용하면 클라이언트의 호출과 가공 부담을 줄이고 관련 코드를 같은 프로젝트에서 관리할 수 있습니다.

다만 서버에서 실행된다고 자동으로 안전한 것은 아닙니다. 공개 HTTP 엔드포인트이므로 입력 검증, 인증·인가, 요청 제한과 오류 처리가 필요합니다. 또한 서버리스 함수로 실행되는지는 배포 환경에 따라 달라지고, 서버 컴포넌트가 데이터를 읽을 때는 자신의 API를 다시 호출하기보다 공통 서버 로직을 직접 사용하는 편이 적절합니다. 작업의 실행 시간과 확장 요구에 따라 별도 백엔드나 작업 큐와 역할을 나누겠습니다.

### 핵심 개념

#### API 라우트의 목적과 요청 흐름

```text
브라우저 또는 외부 클라이언트
  → /api/... HTTP 요청
  → Next.js API 엔드포인트
      ├─ 입력·인증·권한 확인
      ├─ 외부 서비스 호출 또는 데이터베이스 접근
      └─ 필요한 필드 선택·데이터 조합
  → 상태 코드와 응답 반환
```

| 목적 | 활용 예시 | 얻을 수 있는 이점 |
| --- | --- | --- |
| **비밀 정보 보호** | 서버 전용 API 키로 날씨·결제 서비스 호출 | 비밀 키를 클라이언트 번들에 포함하지 않고 외부 서비스 이용 |
| **BFF** | 사용자 정보와 주문 요약을 대시보드 응답 하나로 조합 | 화면에 맞는 데이터 제공, 클라이언트의 호출·가공 부담 감소 |
| **DB 접근** | 인증한 사용자의 게시물 조회·수정 | 서버에서 권한과 데이터 접근 규칙 적용 |
| **인증·세션 처리** | 로그인 요청, 세션 검증, 인증 서비스의 콜백 처리 | 서버에서 자격 증명과 세션 수명 주기 관리 |
| **폼 처리** | 문의·구독·댓글 입력 검증 후 저장 또는 외부 서비스로 전달 | 서버에서 최종 검증과 오류 응답 통일 |
| **웹훅 수신** | 결제·배포 서비스의 이벤트 수신 | 외부 시스템이 호출할 명시적인 HTTP 진입점 제공 |

- **같은 코드베이스의 장점**: 화면과 그 화면을 위한 API를 함께 개발·배포하고 계약을 맞추기 쉬움
- **공개 엔드포인트**: 구현 파일이 서버 전용이어도 URL로 호출 가능. 앱의 화면을 거치지 않은 직접 요청도 처리해야 함
- **라우팅 경로의 관례**: App Router의 `api` 폴더명은 관례이며 Route Handler는 다른 경로에도 정의 가능
- **응답 형식**: JSON뿐 아니라 텍스트·파일·스트림 등도 반환 가능. 페이지 UI를 반환하는 `page.tsx`와 역할 구분

> 참고: [Next.js - Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend), [Next.js - API Routes](https://nextjs.org/docs/pages/building-your-application/routing/api-routes), [Next.js - Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)

#### Pages Router와 App Router의 API 작성 방식

| 구분 | Pages Router의 API Routes | App Router의 Route Handlers |
| --- | --- | --- |
| **파일 예시** | `pages/api/hello.ts` | `app/api/hello/route.ts` |
| **URL** | `/api/hello` | `/api/hello` |
| **함수 정의** | 기본 export한 handler 안에서 `req.method` 분기 | `GET`, `POST` 등 메서드 이름으로 named export |
| **요청 객체** | `NextApiRequest` | 표준 `Request` 또는 이를 확장한 `NextRequest` |
| **응답 방식** | `res.status(...).json(...)` 등 | `Response` 또는 `NextResponse` 반환 |
| **검색 파라미터** | `req.query` | `new URL(request.url).searchParams` 또는 `request.nextUrl.searchParams` |
| **JSON 본문** | 기본 body parser를 통해 `req.body`로 접근 | `await request.json()` 등으로 명시적으로 읽기 |

**Pages Router: 요청 메서드를 handler에서 분기**

```ts
// pages/api/hello.ts
import type { NextApiRequest, NextApiResponse } from 'next';

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  if (req.method !== 'GET') {
    res.setHeader('Allow', 'GET');
    return res.status(405).json({ error: '지원하지 않는 메서드입니다.' });
  }

  return res.status(200).json({ message: 'Hello from API Routes' });
}
```

**App Router: 메서드별 함수를 export**

```ts
// app/api/hello/route.ts
export function GET() {
  return Response.json({ message: 'Hello from Route Handlers' });
}

export async function POST(request: Request) {
  let body: unknown;

  try {
    body = await request.json();
  } catch {
    return Response.json({ error: 'JSON 형식을 확인해 주세요.' }, { status: 400 });
  }

  if (
    typeof body !== 'object' || body === null ||
    !('name' in body) || typeof body.name !== 'string' ||
    body.name.trim().length === 0 || body.name.trim().length > 50
  ) {
    return Response.json({ error: '이름은 1~50자로 입력해 주세요.' }, { status: 400 });
  }

  return Response.json({ message: `${body.name.trim()}님, 안녕하세요.` });
}
```

- **메서드 처리의 차이**: Pages Router에서도 `GET`, `POST` 함수를 각각 export한다고 이해하면 부정확. 일반적으로 handler 내부에서 요청 메서드 분기
- **지원하지 않는 메서드**: Route Handler에서는 정의되지 않은 요청 메서드에 대해 프레임워크가 `405` 처리. Pages Router에서는 예시처럼 명시적으로 처리
- **입력 검증**: TypeScript 타입은 런타임에 JSON의 모양을 검증하지 않음. `unknown`과 타입 가드 또는 스키마 검증 도구 등으로 실제 값 확인
- **예시의 범위**: POST 예시는 입력을 검증해 인사말을 반환하며 DB 저장은 수행하지 않음. 실제 생성 작업에는 저장 성공과 실패, 적절한 상태 코드 처리 추가
- **본문 스트림**: Route Handler의 요청 본문은 스트림이므로 JSON·텍스트·폼 등 필요한 방식으로 읽고 여러 번 소비하지 않도록 설계

> 참고: [Next.js - API Routes](https://nextjs.org/docs/pages/building-your-application/routing/api-routes), [Next.js - route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route), [Next.js - Forms: Server-side validation](https://nextjs.org/docs/app/guides/forms#form-validation)

#### 서버 전용 정보 보호와 외부 API 중계

- **비밀 키의 위치**: 외부 API 키와 DB 자격 증명은 서버 전용 환경변수·시크릿으로 관리
- **`NEXT_PUBLIC_`의 의미**: 클라이언트에 공개할 값에 사용하는 접두사. 비밀 키를 이 이름으로 선언하면 브라우저 번들에 포함될 수 있음
- **서버 전용 모듈**: 비밀 정보·DB 접근 로직을 별도 모듈에 두고 `server-only`로 클라이언트에서 잘못 import하는 실수 탐지 가능
- **반환값도 노출 경계**: 서버에서 키를 읽어도 응답 JSON이나 클라이언트 props로 반환하면 공개됨. 클라이언트가 필요한 필드만 선택
- **중계 대상 제한**: 사용자가 준 임의의 URL을 그대로 서버에서 요청하지 않기. 허용할 서비스·경로·입력 범위를 정해 오픈 프록시나 내부 자원 접근으로 악용되는 상황 방지

다음은 공개 날씨 조회를 중계하는 학습 예시입니다. `OPENWEATHER_API_KEY`를 서버에 설정하고, 지원 도시를 미리 정한 좌표로 변환해 요청한 뒤 도시 이름과 기온만 반환합니다. 실제 서비스에서는 요청 제한과 외부 API의 이용 조건·오류 정책도 적용해야 합니다.

```ts
// app/api/weather/route.ts
const cities = new Map([
  ['Seoul', { lat: 37.57, lon: 126.98 }],
  ['Busan', { lat: 35.18, lon: 129.08 }],
  ['Tokyo', { lat: 35.68, lon: 139.69 }],
]);

function json(body: unknown, status = 200) {
  return Response.json(body, {
    status,
    headers: { 'Cache-Control': 'no-store' },
  });
}

export async function GET(request: Request) {
  const city = new URL(request.url).searchParams.get('city') ?? 'Seoul';
  const coordinates = cities.get(city);

  if (!coordinates) {
    return json({ error: '지원하지 않는 도시입니다.' }, 400);
  }

  const apiKey = process.env.OPENWEATHER_API_KEY;
  if (!apiKey) {
    return json({ error: '서버 설정을 확인해 주세요.' }, 500);
  }

  const url = new URL('https://api.openweathermap.org/data/2.5/weather');
  url.searchParams.set('lat', String(coordinates.lat));
  url.searchParams.set('lon', String(coordinates.lon));
  url.searchParams.set('appid', apiKey);
  url.searchParams.set('units', 'metric');

  try {
    const upstream = await fetch(url, {
      cache: 'no-store',
      signal: AbortSignal.timeout(5000),
    });

    if (!upstream.ok) {
      return json({ error: '날씨 서비스 응답에 문제가 있습니다.' }, 502);
    }

    const data = await upstream.json();
    if (typeof data?.main?.temp !== 'number') {
      return json({ error: '날씨 서비스 응답 형식이 올바르지 않습니다.' }, 502);
    }

    return json({ city, temperature: data.main.temp });
  } catch (error) {
    if (error instanceof Error && error.name === 'TimeoutError') {
      return json({ error: '날씨 서비스 응답 시간이 초과되었습니다.' }, 504);
    }
    return json({ error: '날씨 서비스를 불러오지 못했습니다.' }, 502);
  }
}
```

- **브라우저의 요청**: `/api/weather?city=Busan`만 호출하며 외부 API 키를 요청에 직접 포함하지 않음
- **서버의 책임**: 허용 입력 확인, 외부 API 요청, 시간 제한, 응답 검증·필드 선별과 오류 변환
- **키 보호와 접근 제한의 차이**: 키가 보이지 않아도 누구나 엔드포인트를 반복 호출해 외부 서비스 비용을 발생시킬 수 있음. 공개 조회에도 요청량 제어 필요
- **로그 주의**: 예외·외부 요청 URL에 API 키가 포함될 수 있으므로 원본 오류와 URL을 무분별하게 기록하거나 클라이언트에 반환하지 않기
- **캐시 정책**: 예시는 상위 요청과 클라이언트 응답 모두 저장하지 않도록 구성. 공개 날씨 정보라면 실제 요구에 맞게 짧은 캐시와 요청 제한을 조합할 수 있음

> 참고: [Next.js - Environment Variables](https://nextjs.org/docs/app/guides/environment-variables), [Next.js - Data Security](https://nextjs.org/docs/app/guides/data-security), [OpenWeather - Current Weather Data](https://openweathermap.org/api/current), [MDN - AbortSignal.timeout](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static), [MDN - Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

#### BFF와 데이터 조합

- **BFF(Backend for Frontend)**: 특정 프런트엔드의 화면·사용 흐름에 맞춰 백엔드 데이터를 제공하는 계층
- **조합 예시**: `/api/dashboard`에서 사용자 서비스와 주문 서비스를 호출하고 표시 이름·최근 주문 5개 등 필요한 정보만 반환
- **병렬화**: 서로 독립적인 요청이라면 `Promise.all` 등으로 함께 수행. 앞선 결과가 필요한 요청은 의존 관계에 맞춰 처리
- **실패 정책**: 일부 서비스가 실패하면 전체 응답을 실패시킬지, 선택 영역만 제외해 부분 결과를 제공할지 결정
- **데이터 축소**: 원본 사용자 레코드나 외부 API 응답 전체를 그대로 넘기지 말고 화면에 공개할 응답 형태를 정의
- **경계의 이점과 비용**: 브라우저 요청 수와 클라이언트 가공 부담은 줄지만, BFF와 서비스 사이의 네트워크·인증·장애 처리 책임은 서버에 남음
- **로직 재사용**: HTTP handler에 비즈니스 규칙을 모두 넣기보다 데이터 접근·서비스 함수를 분리해 테스트와 재사용 지원

> 참고: [Next.js - Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend), [Next.js - Data Security](https://nextjs.org/docs/app/guides/data-security)

#### DB 접근·인증·폼 처리

- **DB 접근 경로**: 서버의 데이터 접근 계층에서 쿼리와 공개 필드 선택 수행. 브라우저에 서버 DB 비밀번호를 전달하지 않기
- **인증(Authentication)**: 세션·토큰 등을 검증해 요청 사용자가 누구인지 확인
- **인가(Authorization)**: 로그인 여부와 별도로 해당 사용자가 요청한 자원을 조회·수정할 권한이 있는지 확인
- **소유자 식별**: 클라이언트가 보낸 `userId`를 그대로 신뢰해 주문을 조회하지 말고 검증한 세션과 자원 소유 관계로 접근 제어
- **폼 처리 순서**: 입력 파싱 → 서버 검증 → 인증·권한 확인 → 저장·외부 연동 → 결과 반환. 실제 순서는 작업 특성에 맞게 조정
- **클라이언트 검증의 역할**: 빠른 피드백과 UX 개선용이며 서버의 최종 검증을 대체하지는 못함
- **쿠키 기반 변경 요청**: 쿠키가 자동 첨부되는 특성을 고려해 CSRF 토큰·요청 출처 검증 등 적절한 방어 적용. 같은 출처의 API라는 이유만으로 방어가 완성되지는 않음
- **DB 연결 관리**: 서버리스 인스턴스가 늘면 DB 연결도 늘어날 수 있으므로 연결 풀·프록시·드라이버의 배포 환경 호환성 검토

> 참고: [Next.js - Authentication](https://nextjs.org/docs/app/guides/authentication), [Next.js - Data Security](https://nextjs.org/docs/app/guides/data-security), [Next.js - Forms](https://nextjs.org/docs/app/guides/forms)

#### CORS를 줄여 주는 구조와 한계

- **동일 출처 호출**: 브라우저가 자신의 웹 앱과 같은 출처의 `/api/...`를 호출하면 그 구간에 교차 출처 응답 읽기 문제가 생기지 않음
- **서버 간 외부 요청**: Next.js 서버가 외부 API를 호출하는 구간에는 브라우저의 CORS 정책이 적용되지 않음. 외부 서비스의 인증·접근 정책은 여전히 준수
- **출처가 다른 클라이언트**: 다른 도메인의 웹 앱이 이 API를 호출한다면 허용할 origin·메서드·헤더와 필요한 preflight 응답 구성
- **인증과 별개**: CORS는 브라우저가 다른 출처 응답을 읽을 수 있는지 제어하는 정책. 비브라우저 클라이언트의 직접 호출을 막거나 사용자의 권한을 검증하는 수단은 아님
- **범위 구분**: API를 한 프로젝트에 두었다고 모든 배포 구조에서 같은 출처가 되는 것은 아님. 실제 URL의 scheme·host·port 확인

> 참고: [MDN - CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS), [Next.js - API Routes](https://nextjs.org/docs/pages/building-your-application/routing/api-routes)

#### 응답 계약·캐시·운영 품질

| 항목 | 확인할 내용 |
| --- | --- |
| **상태 코드** | 성공·생성에는 `200`·`201`, 잘못된 입력은 `400`, 미인증은 `401`, 권한 부족은 `403`, 요청 제한은 `429` 등 상황에 맞게 사용 |
| **외부 서비스 실패** | 외부 응답 오류·시간 초과를 구분하고 필요에 따라 `502`·`504` 등으로 표현. 모든 오류를 성공 `200`으로 숨기지 않기 |
| **오류 정보** | 클라이언트용 오류 메시지와 운영 로그를 분리하고 비밀 키·스택·개인정보 노출 방지 |
| **캐시** | Next.js 내부 데이터 캐시와 브라우저·CDN의 HTTP 응답 캐시를 구분. 사용자별 응답을 공유 캐시에 섞지 않도록 정책 명시 |
| **입력·크기 제한** | 본문 스키마뿐 아니라 허용 메서드·콘텐츠 형식·요청 크기·업로드 정책도 검토 |
| **요청량과 의존성** | rate limit, 외부 요청 시간 제한, 재시도 기준과 부작용 중복 방지 정책 구성 |
| **관측 가능성** | 요청 ID, 처리 시간, 오류율과 외부 서비스 실패 지점을 추적하고 민감 데이터는 로그에서 제외 |

- **GET 캐시의 버전 차이**: Route Handler의 GET이 항상 자동으로 캐시된다고 가정하지 않기. Next.js 15부터 기본 정책이 변경됐고, 현재도 Cache Components·정적 생성 등 설정에 따라 동작 확인 필요
- **개인 데이터**: 세션·권한에 따라 달라지는 응답에는 명시적인 비공유·비저장 정책 등을 검토하고, 캐시 키와 데이터 범위를 함께 확인
- **웹훅 검증**: 서비스가 지정한 서명을 원문 본문으로 검증하고 중복 이벤트를 안전하게 처리. Pages Router에서는 자동 body parser를 끄고 원문을 읽어야 하는 경우가 있으며, Route Handler는 `request.text()` 등 활용

> 참고: [Next.js - Route Handlers: Caching](https://nextjs.org/docs/app/getting-started/route-handlers#caching), [Next.js - route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route), [Next.js - API Routes](https://nextjs.org/docs/pages/building-your-application/routing/api-routes), [MDN - HTTP Status Codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status), [MDN - Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

#### 배포 방식과 서버리스의 제약

| 배포 환경 | 실행 특성 | 고려할 점 |
| --- | --- | --- |
| **서버리스 함수** | 호스팅 환경이 요청을 처리할 함수 인스턴스 관리 | 콜드 스타트, 실행 시간·메모리·본문 크기 제한, DB 연결 증가 등 환경별 제약 |
| **Node.js 서버·컨테이너** | 직접 운영하는 Next.js 서버 프로세스에서 요청 처리 | 인스턴스 확장, 프로세스 관리, 네트워크·캐시·운영 책임 |
| **정적 export** | 요청을 처리할 Next.js 런타임 서버 없이 파일 제공 | 런타임 API 처리 불가. 사전 생성 가능한 GET 응답을 정적 파일로 만드는 제한된 활용은 가능 |

- **프레임워크와 호스팅의 구분**: API 라우트는 HTTP 처리 기능이며, 파일을 만들었다는 사실만으로 항상 서버리스 함수가 되는 것은 아님
- **비용 판단**: 서버리스는 트래픽과 실행 시간·리소스 요금에 따라 비용이 달라짐. 항상 비용이 적게 든다고 단정하지 않기
- **요청 사이의 상태**: 서버리스의 메모리·로컬 파일을 영구 저장소로 취급하지 않기. 인증 세션·중복 방지 정보 등은 적절한 공유 저장소 사용
- **긴 작업 분리**: 대용량 처리·배치·오래 걸리는 작업은 큐에 등록하고 worker에서 수행하는 구조 검토
- **실시간 연결**: 일반적인 짧은 수명의 서버리스 함수는 WebSocket 연결 유지에 맞지 않을 수 있음. 연결 유지 요구와 배포 플랫폼 지원에 따라 별도 실시간 서버·서비스 선택
- **런타임 호환성**: Node.js와 Edge Runtime은 지원 API와 라이브러리 범위가 다름. DB 드라이버·파일 시스템·네이티브 모듈 의존성을 확인

> 참고: [Next.js - Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting), [Next.js - Static Exports](https://nextjs.org/docs/app/guides/static-exports), [Next.js - Edge Runtime](https://nextjs.org/docs/app/api-reference/edge), [Next.js - Deployment environment](https://nextjs.org/docs/app/guides/backend-for-frontend#deployment-environment)

#### API 라우트·Server Component·Server Action의 선택

| 요구사항 | 우선 검토할 수단 | 이유 |
| --- | --- | --- |
| **서버에서 페이지에 필요한 데이터 조회** | Server Component와 공통 서버 함수 | 자기 앱의 HTTP API를 경유하는 추가 왕복을 줄이고 데이터 원본에 직접 접근 |
| **브라우저·모바일·외부 시스템의 HTTP 호출** | API Route 또는 Route Handler | 명시적인 URL·메서드·상태 코드·응답 계약 제공 |
| **Next.js UI에서 폼 제출·데이터 변경** | Server Action 또는 Route Handler | UI 결합도와 외부 소비자 필요 여부를 기준으로 선택 |
| **여러 클라이언트가 공유하는 핵심 도메인 API** | 독립 백엔드 또는 분리한 서비스 계층 | 별도 배포·확장·버전 관리와 다른 앱에서의 재사용 요구 고려 |
| **긴 비동기 작업·지속 연결** | 작업 큐·worker·실시간 서버 등 | HTTP 요청 수명과 플랫폼 제한에 맞춰 실행 책임 분리 |

- **자기 API 우회 호출 방지**: Server Component에서 같은 앱의 `/api/...`를 다시 HTTP로 호출하면 추가 지연이 생기고, 빌드 시 서버가 없어 실패할 수도 있음
- **서버 로직 재사용**: Server Component와 Route Handler가 인증·권한 확인을 포함한 공통 데이터 접근 함수를 공유하도록 구성 가능
- **Server Action의 보안**: 서버에서 실행하는 UI 연동 수단도 외부 호출 가능한 진입점으로 보고 입력·인증·권한 검증 적용
- **프레임워크 종속성 완화**: HTTP 요청·응답 처리와 핵심 규칙을 분리하면 별도 백엔드 이전과 테스트가 쉬워짐

> 참고: [Next.js - Server Components caveat](https://nextjs.org/docs/app/guides/backend-for-frontend#server-components), [Next.js - Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components), [Next.js - Forms](https://nextjs.org/docs/app/guides/forms), [Next.js - Data Security](https://nextjs.org/docs/app/guides/data-security)

### 모의 면접

#### 1. 넥스트.js의 API 루트를 사용하는 주요 목적과 장점을 3가지 이상 설명할 수 있나요?

첫째, 외부 서비스의 비밀 키나 DB 자격 증명을 서버에 두고 브라우저에는 필요한 결과만 전달할 수 있습니다. 둘째, 여러 API 응답을 화면에 맞게 조합하는 BFF 역할로 클라이언트의 호출과 데이터 가공 부담을 줄일 수 있습니다. 셋째, 인증과 권한 검증, 폼 데이터 검증과 저장을 같은 프로젝트에서 처리해 개발 흐름과 배포 관리를 단순하게 만들 수 있습니다. 또한 웹훅처럼 외부 시스템이 호출할 HTTP 진입점으로도 활용할 수 있습니다.

다만 보안은 서버에서 실행된다는 사실만으로 보장되지 않으므로 각 엔드포인트에 입력 검증·인증·인가·요청 제한을 적용해야 합니다. 서버리스 배포가 가능한 환경에서는 인프라 관리 부담을 줄일 수 있지만, 실행 방식과 비용·제약은 실제 호스팅 환경을 확인하겠습니다.

#### 2. 페이지 라우터와 앱 라우터의 차이점 및 각각의 사용 예시를 설명할 수 있나요?

API 작성 관점에서 Pages Router는 `pages/api/hello.ts`처럼 파일을 만들고 기본 export한 handler에서 `req.method`를 확인해 GET·POST 등을 분기합니다. 요청은 `NextApiRequest`, 응답은 `NextApiResponse`를 사용하며 `res.status(200).json(...)` 형태로 반환합니다. 예를 들어 GET 요청이면 안내 데이터를 반환하고, POST 요청이면 `req.body`를 검증해 저장하는 방식입니다.

App Router는 `app/api/hello/route.ts`에서 `GET`, `POST` 같은 함수를 named export하는 Route Handler를 사용합니다. 표준 Request·Response API를 기반으로 `await request.json()`으로 본문을 읽고 `Response.json(...)` 등으로 반환합니다. 외부 API 중계나 웹훅 수신에도 사용할 수 있으며, 요청 객체와 export 방식이 다르므로 Pages Router의 코드를 그대로 옮기기보다 새 API에 맞춰 작성하겠습니다.
