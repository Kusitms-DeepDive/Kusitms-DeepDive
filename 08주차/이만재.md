### Q70 넥스트.js에서 검색 엔진 최적화를 어떻게 개선할 수 있나요?

---

#### **책을 읽기 전 혼자 답해보기**

> 검색 엔진 최적화를 하기 위해서는 적절한 HTML 태그 사용은 물론 메타데이터를 꼼꼼히 작성하는 것이 중요하다. CSR과 달리 SSR은 미리 서버에서 HTML을 구워서 내려주기에 크롤러가 읽고 정보를 파악할 수 있다.

---

#### 책 정리

**SSR과 SSG를 활용한 검색 엔진 최적화**

Next.js의 가장 본질적인 검색 엔진 최적화는 렌더링 방식에 있다.  
일반적으로 CSR 리액트 앱은 초기 HTML이 비어있고 모든 콘텐츠가 자바스크립트가 실행된 후에 동적으로 생성된다. 이 방식은 자바스크립트 실행 능력이 제한적인 크롤러가 콘텐츠를 제대로 수집하지 못하게 되어 검색 엔진 최적화에 불리하다. 

**SSR의 검색 엔진 최적화**

SSR은 사용자가 페이지를 요청하는 시점에 서버에서 데이터를 가져와 리액트 컴포넌트를 미리 렌더링하고 콘텐츠가 모두 포함된 HTML 문서를 생성하여 브라우저로 전송한다. 이로 인해 검색 엔진 크롤러는 자바스크립트를 실행하지 않아도 완전한 콘텐츠가 채워진 HTML을 즉시 읽고 인덱싱할 수 있어 검색 엔진 최적화에 유리하다. 특히 뉴스 페이지나 상품 상세 페이지처럼 데이터가 자주 변경되는 경우에 적합하다.

**SSG의 검색 엔진 최적화**

SSG는 빌드 시점에 모든 페이지의 HTML 파일을 미리 생성해두는 방식이다. 이렇게 생성된 HTML 파일은 CDN을 통해 사용자에게 즉시 전달되므로 로딩 속도가 매우 빠르고 크롤러가 접근하기에 가장 이상적인 형태를 제공한다. 특히 콘텐츠 변화가 적은 블로그, 문서 페이지, 마케팅 페이지 등에 효과적이다. (흔히 정적 페이지 렌더링이라고 하는 게 SSG이다.)

**메타데이터 관리**

검색 엔진은 HTML 문서의 `<head>` 태그 내에 있는 메타데이터를 사용하여 페이지의 내용과 관련된 중요한 정보를 얻는다. Next.js는 이 메타데이터를 효율적으로 관리하는 방법을 제공한다.

**페이지 라우터**

페이지 라우터에서는 `next/head` 모듈의 `<Head>` 컴포넌트를 사용하여 페이지의 `<head>` 태그 내용을 동적으로 관리한다. 각 페이지 컴포넌트 내에서 `<Head>` 컴포넌트를 임포트해 사용한다. 

**페이지 라우터의 장점**

1. 페이지별 메타데이터 관리: 각 페이지의 특성에 맞는 고유한 제목, 설명, 키워드 등을 설정할 수 있다.
2. 동적 메타데이터: `getServerSideProps`나 `getStaticProps`로 가져온 데이터를 기반으로 동적인 메타데이터를 생성할 수 있다.
3. 오픈그래프와 트위터 카드 설정: 소셜 미디어에 공유할 때 미리보기를 최적화하여 클릭률을 높인다.
4. 표준 URL 설정: 여러 URL로 접근 가능한 동일한 콘텐츠가 있을 경우, 검색 엔진에 어떤 URL이 원본인지 알려주어 중복 콘텐츠 페널티를 방지한다.

**앱 라우터**

앱 라우터에서는 Metadata API를 사용하여 `<head>` 태그를 관리하는 방식이 훨씬 더 강력하고 유연해졌다. `layout.js` 또는 `page.js` 파일에서 `metadata` 객체를 익스포트하면 정적 메타데이터를 설정할 수 있고, 페이지별로 달라지는 정보가 필요할 때는 `generateMetadata` 비동기 함수를 사용해 동적 메타데이터를 생성할 수 있다. 

**앱 라우터의 장점**

1. 향상된 관리: `layout.js`에서 공통 메타데이터를 정의하고 하위 `layout.js`나 `page.js`에서 이를 오버라이드하거나 확장할 수 있다.
2. 강력한 타입 안정성: 타입스크립트와 함께 사용 시 타입 안정성이 보장된다.
3. 데이터 페칭 통합: `generateMetadata` 함수는 서버 컴포넌트와 동일하게 `async`로 데이터를 페칭하여 동적으로 메타데이터를 생성할 수 있다.
4. 다양한 메타데이터 타입 지원: `title`, `description`, `keywords`뿐만 아니라 `openGraph`, `twitter`, `robots`, `alternates`, `icons` 등 훨씬 더 많은 메타데이터 속성을 지원한다.

> Next.js에서 SSR은 사용자가 페이지를 요청하는 시점에 서버에서 데이터를 받아 리액트 컴포넌트에 값을 채워 넣기 때문에 크롤러는 완성된 HTML을 읽게 되고 이는 곧 검색 엔진 최적화까지 이어진다.

> 
> 두 방식 다 CSR처럼 빈 HTML에 자바스크립트가 로딩된 후 정보를 채워 넣는 방식이 아니라 이미 HTML에 정보가 채워져 있다는 점에서 검색 엔진 최적화에 도움이 된다.

> 각 페이지별로 알맞은 메타데이터를 생성, 설정할 수 있는 것이 장점인 것 같다.

### Q71 넥스트.js의 라우팅 시스템은 무엇인가요?

---

#### **책을 읽기 전 혼자 답해보기**

> 폴더 기반 라우팅 시스템으로 라우터를 하나하나 지정해 줘야 하는 리액트와 다르게 넥스트는 폴더 기반으로 라우터를 생성해 준다.

---

#### 책 정리

리액트와 같은 SPA 라이브러리에서 라우팅을 구현하려면 일반적으로 `react-router-dom`과 같은 별도의 라이브러리를 설치하고 복잡한 설정을 해야 한다. 하지만 넥스트.js는 자체적인 파일 시스템 기반 라우팅 시스템을 내장하고 있어 개발자가 별도로 설정하지 않아도 쉽게 라우팅을 구현하고 관리할 수 있다.

**파일 시스템 기반 라우팅**

넥스트.js의 라우팅은 프로젝트 안의 `pages`나 `app` 같은 특정 디렉터리에 파일을 생성하기만 하면 자동으로 설정된다.

**pages 디렉터리**

넥스트.js 12 버전 이하 또는 페이지 라우터를 사용하는 경우에는 `pages` 디렉터리 내의 각 `.js`, `.jsx`, `.ts`, `.tsx` 파일이 하나의 라우트가 되어 파일 구조가 곧 URL 구조로 연결된다.

```text
pages/index.js -> / (루트 경로)
pages/about.js -> /about
pages/posts/index.js -> /posts
pages/posts/[id].js -> /posts/:id (동적 라우팅)
pages/api/hello.js -> /api/hello (API Route)
```

**app 디렉터리**

넥스트.js 13 버전 이상에서는 `app` 디렉터리의 폴더 구조와 각 폴더 안의 `page.js` 파일이 곧 라우트가 된다.  
폴더가 URL 경로를 결정하고 그 안의 `page.js`가 실제 페이지를 담당하는 방식으로 파일 구조만 봐도 전체 라우팅 구조를 파악할 수 있다.

```text
app/page.js -> / (루트 경로)
app/about/page.js -> /about
app/dashboard/page.js -> /dashboard
app/products/[slug]/page.js -> /products/:slug (동적 라우팅)
app/api/route.js -> /api (Route Handlers)
```

**next/link 컴포넌트**

넥스트.js의 라우터는 단순히 URL과 페이지를 연결하는 역할에 그치지 않고 페이지 전환 방식과 성능 최적화까지 함께 담당한다. 페이지 단위로 코드를 나누어 관리하고 전체 페이지를 새로 고치지 않고도 빠른 화면 전환, 사전 로딩과 같은 기능을 구현할 때 사용하는 도구가 `next/link` 컴포넌트이다.

**클라이언트 사이드 내비게이션**

넥스트.js는 `next/link` 컴포넌트를 사용하여 페이지 간의 클라이언트 사이드 내비게이션을 지원한다.  
이는 브라우저의 전체 새로 고침 없이 자바스크립트를 통해 DOM만 부분적으로 업데이트하는 방식으로 페이지를 전환한다.

**링크 프리페칭**

`next/link` 컴포넌트의 또 다른 강력한 기능은 바로 링크 프리페칭이다. 사용자가 특정 `Link` 컴포넌트가 포함된 영역을 스크롤하여 뷰포트에 진입하거나 마우스를 링크 위에 올리면 넥스트.js는 해당 링크가 가리키는 페이지의 자바스크립트 번들을 미리 내려받아 캐시에 저장한다.  
`Link` 컴포넌트는 기본적으로 `prefetch={true}`로 설정되어 있어 별도의 설정 없이도 이 동작이 자동으로 수행된다. 그 결과 실제 사용자가 링크를 클릭하는 순간에는 이미 필요한 코드가 준비된 상태이다.

**Link 컴포넌트와 useRouter 훅의 사용법**

페이지 라우팅을 처리하는 주요 방법은 선언적인 방식인 `next/link`의 `Link` 컴포넌트와 프로그래밍 방식의 `useRouter` 훅이다.

**Link 컴포넌트**

선언적으로 페이지 간에 이동할 때 사용한다. HTML `<a>` 태그와 유사하지만 넥스트.js의 클라이언트 사이드 라우팅 및 프리페칭 기능을 활성화한다.

`Link` 컴포넌트는 사용법이 간단하고 직관적이어서 링크를 만들 때 가장 많이 사용하는 방식이다. 링크 프리페칭이 활성화되어 있어 성능 최적화에 기여하며 HTML `<a>` 태그로 렌더링되므로 스크린 리더 같은 보조 기술에도 친화적이다. 또한 검색 엔진 크롤러가 링크 구조를 명확하게 인식할 수 있어 검색 엔진 최적화 측면에도 유리하다.

다만 폼 제출 후 이동, 조건부 라우팅처럼 사용자 행동이나 특정 조건에 따라 자바스크립트 코드로 페이지 이동을 제어해야 하는 경우에는 적합하지 않다는 한계가 있다.

**useRouter 훅**

`useRouter` 훅은 프로그래밍 방식으로 페이지 이동을 제어하거나 현재 라우트 경로를 가져올 때 사용한다.

`useRouter` 훅의 장점은 자바스크립트 로직 안에서 페이지 이동을 제어할 수 있다는 것이다. 특정 조건에 따라 다른 페이지로 이동시키거나 폼 제출 후 결과에 따라 리다이렉션하는 등 프로그래밍 방식으로 라우팅할 수 있다.  
현재 경로, 쿼리 파라미터, 동적 라우트 매개변수 같은 라우트 정보를 가져와 페이지 로직에 활용할 수 있다.

하지만 `Link` 컴포넌트와 달리 자동으로 프리페칭되지 않아 필요하다면 `router.prefetch()`로 직접 처리해야 한다.

#### 모의 면접

**Q1: 넥스트.js에서 페이지 라우터와 앱 라우터의 라우팅 방식과 디렉터리 구조의 차이는 무엇인가요?**

> 페이지 라우터의 경우 `pages` 디렉터리 내에 `.js`, `.ts`, `.tsx` 등의 파일이 하나의 라우트가 되는 방식이고 앱 라우터의 경우 폴더 구조와 각 폴더 내의 `page.js` 파일이 라우트가 된다.

<br>

**Q2: next/link, useRouter 훅의 역할과 장단점은 무엇이며 어떤 상황에서 각각을 사용하는 것이 적합한가요?**

> `Link` 컴포넌트의 경우 링크 프리페칭이 기본값이기 때문에 단순한 페이지 이동의 경우 사용자가 버튼을 클릭했을 때 이미 페이지에 필요한 정보가 거의 다 완성되어 있다. 그렇기 때문에 단순 페이지 이동에는 링크 버튼을 사용하는 것이 좋다.  
> 
> `useRouter` 훅의 경우 현재 경로나 쿼리 파라미터 값 등 라우트 정보가 필요할 때 사용하며 자바스크립트 로직 안에서 페이지 이동을 제어할 수 있다. 특정 조건에 따라 다른 페이지로 이동시키거나 폼 제출 후 결과에 따라 리다이렉션하는 등 프로그래밍 방식으로 라우팅할 수 있다. 하지만 `Link` 컴포넌트처럼 프리페칭을 기본값으로 지원하지 않아 필요시 `router.prefetch()`를 호출해서 직접 처리해야 한다.

### Q73 넥스트.js에서 API 루트를 사용하는 목적은 무엇인가요?

---

#### **책을 읽기 전 혼자 답해보기**

> 프론트엔드와 동시에 백엔드 개발도 할 수 있으며 외부에 유출되면 안 되는 인증키 값 등을 BFF로 우회할 수 있다. (이때 CORS도 안 걸림)

---

#### 책 정리

**API 루트의 의미와 목적**

API 루트는 넥스트.js 프로젝트의 특정 디렉터리 내에 자바스크립트 또는 타입스크립트 파일을 생성하는 것만으로 해당 파일이 HTTP API 엔드포인트 역할을 하도록 만드는 기능이다.

**API 루트의 주요 목적 3가지**

1. 프론트엔드와 백엔드 로직의 통합: 프론트엔드 코드베이스 내에서 간단한 백엔드 로직을 직접 구현할 수 있게 하여 개발 워크플로를 간소화한다.
2. 서버리스 함수 지원: 배포 환경에서 API 루트는 자동으로 서버리스 함수로 변환되어 실행된다. 이는 요청이 있을 때만 서버 자원을 사용하므로 비용 효율적이다.
3. 클라이언트-서버 간의 ‘미들웨어’ 역할: CORS, 보안 문제 등으로 클라이언트에서 직접 외부 API를 호출하기 어려운 상황에서 중간 다리, 즉 프록시 역할을 수행한다.

**API 루트가 유용하게 사용되는 상황**

**민감한 정보 숨기고 보안 강화하기**

클라이언트 측 코드에 데이터베이스 접근 정보나 외부 서비스의 API 키를 포함하면 브라우저의 개발자 도구를 통해 누구나 해당 정보를 확인할 수 있어 보안상 매우 취약해진다. API 루트는 서버 환경에서 실행되므로 이곳에서 민감한 정보를 안전하게 다룰 수 있다. 외부 API 호출 시 API 키를 API 루트 내부에서 사용하여 클라이언트에 노출시키지 않는다. 

**경량 백엔드 수행하기**

API 루트는 서버 환경에서 실행되므로, 여러 외부 API를 호출해 데이터를 조합하고 프론트엔드가 바로 사용할 수 있는 형태로 변환하는 경량 백엔드 역할을 수행할 수 있다. 

**서버리스 DB 연동하기**

클라이언트에서 직접 데이터베이스에 연결하는 것은 보안상 매우 위험하다. API 루트는 서버 환경에서 실행되므로 프리즈마(Prisma), 몽구스(Mongoose) 같은 데이터베이스 클라이언트 라이브러리를 사용하여 안전하게 데이터베이스에 접근하고 쿼리를 실행할 수 있다.

**사용자 인증과 세션 관리하기**

로그인 처리나 세션 관리, JWT 검증 등은 서버 측에서 안전하게 이루어져야 한다. API 루트는 로그인이나 회원가입 요청을 처리하고 세션을 생성하거나 JWT를 발급하고 검증하는 로직을 구현하는 데 사용될 수 있다. `next-auth` 같은 인증 라이브러리도 내부적으로 API 루트를 활용한다.

**폼 제출 처리하기**

리액트 컴포넌트에서 직접 폼 데이터를 서버로 전송할 때 CORS 문제나 복잡한 전송 로직이 필요할 수 있다. API 루트는 프론트엔드 폼의 제출 데이터를 받아 처리하고 데이터베이스에 저장하거나 외부 서비스로 전달하는 중간 지점 역할을 할 수 있다.

**API 루트의 장점과 단점**

**장점**

1. 풀스택 개발 용이성: 프론트엔드 프로젝트 내에서 간단한 백엔드 로직을 함께 관리할 수 있어 개발 워크플로를 간소화한다.
2. 서버리스 배포: 대부분의 호스팅 서비스에서 자동으로 서버리스 함수로 배포되어 비용 효율적이다.
3. 보안 강화: 민감한 정보를 클라이언트에 노출하지 않고 서버에서 처리할 수 있다.
4. CORS 문제 해결: 프론트엔드와 백엔드가 같은 도메인에 있는 것처럼 동작하므로 CORS 문제를 피할 수 있다.
5. 타입 안정성: 타입스크립트와 함께 사용 시 API 요청 및 응답에 대한 타입 안정성을 확보할 수 있다.

**단점**

1. 복잡한 백엔드 로직에는 부적합: 대규모, 고도로 복잡한 비즈니스 로직이나 실시간 처리가 필요한 경우에는 전통적인 독립형 백엔드 서버가 더 적합할 수 있다.
2. 콜드 스타트: 서버리스 함수의 특성상 오랜 시간 호출되지 않았다가 다시 호출될 때 초기 시작 지연(콜드 스타트)이 발생할 수 있다.
3. 넥스트.js에 종속적: 넥스트.js 프레임워크에 종속적인 API이므로 API 루트 코드를 다른 프레임워크나 환경에서 재사용하기 어렵다.

**Q1: 넥스트.js의 API 루트를 사용하는 주요 목적과 장점을 3가지 이상 설명할 수 있나요?**

> 1. 경량 백엔드 역할을 할 수 있다: 인증/인가, DB 저장 등 간단한 백엔드 역할은 가능하지만 실시간 처리나 고도화된 로직은 독립형 백엔드가 필요하다.  
> 2. 보안 강화: 외부 브라우저로 민감한 정보(API 키, 인증 정보) 등이 노출되지 않고, 내부 API 루트를 통해 처리되기 때문에 안전하다.  
> 3. 서버리스 배포: 대부분의 호스팅 서비스에서 자동으로 서버리스 함수로 배포되어 비용 효율적이다.

**Q2: 페이지 라우터와 앱 라우터의 차이점 및 각각의 사용 예시를 설명할 수 있나요?**

> 페이지 라우터에서는 `pages/api` 디렉터리 내에 파일을 만들면 해당 파일이 API 엔드포인트가 된다. `pages/api/hello.js` 파일을 생성하면 `/api/hello` 경로로 요청이 가능하다.  
> 
> 앱 라우터에서는 `app/api` 디렉터리 안에 `route.js` 또는 `route.ts` 파일을 만들어 API 엔드포인트를 정의한다. `app/api/users/route.js` 파일을 만들면 `/api/users` 경로가 생성된다.  
> 
> 클라이언트 측에서는 일반적인 `fetch` API 등을 사용하여 API 루트 엔드포인트를 호출할 수 있다.
