# 10주차 정리
# Q24. `display:none`, `visibility:hidden`, `opacity:0`의 차이점

세 속성은 모두 요소를 숨기지만 브라우저가 요소를 처리하는 방식이 다릅니다.

## 한눈에 비교

| 구분 | `display: none` | `visibility: hidden` | `opacity: 0` |
|---|---|---|---|
| DOM 트리 | 있음 | 있음 | 있음 |
| 레이아웃(공간 차지) | ❌ | ✅ | ✅ |
| 화면에 그려짐(Paint) | ❌ | ❌ | ✅ (투명하게 그려짐) |
| 이벤트(클릭, 호버) | ❌ | ❌ | ✅ |
| 스크린 리더 | ❌ 읽지 않음 | ❌ 읽지 않음 | ✅ 읽음 |
| 토글할 때 비용 | 리플로우 + 리페인트 | 리페인트 | 컴포지팅만 일어날 수 있음 |
| 자식 요소만 보이게 하기 | 불가 | `visibility: visible`로 가능 | 불가 |

## display: none
- 처음부터 없었던 것처럼 취급합니다. **DOM 트리에는 있지만 렌더 트리에서는 빠집니다.**
- 요소가 차지하던 공간이 사라지므로, 적용하거나 해제할 때 주변 요소의 위치가 바뀌는 **리플로우**가 일어납니다.
- 화면 표시, 이벤트, 접근성이 모두 막힙니다.

## visibility: hidden
- 요소를 보이지 않게 하지만 **공간은 그대로 둡니다.** 그래서 리플로우가 일어나지 않습니다.
- ⚠️ **수정**: "화면에는 그려지지만 투명하게 처리된다"는 정확하지 않습니다. 레이아웃 계산에는 포함되지만 **페인트 단계에서 그리지 않습니다.** 값을 바꿀 때 리페인트가 일어납니다.
- 클릭이나 호버 같은 이벤트에 반응하지 않습니다.
- ➕ **보충**: 스크린 리더도 읽지 않습니다. 접근성 트리에서 빠집니다.
- 자식 요소에 `visibility: visible`을 주면 자식만 보이게 할 수 있습니다.

## opacity: 0
- 요소를 시각적으로만 투명하게 만듭니다.
- 레이아웃에 포함되고 화면에도 그려집니다.
- 투명할 뿐이므로 호버, 클릭, 포커스 같은 이벤트에 반응합니다.
- 스크린 리더도 읽습니다.
- ➕ **보충**: `opacity`는 `transform`과 함께 **컴포지팅 단계만으로 처리할 수 있는 속성**입니다. 그래서 페이드 애니메이션에 유리합니다.

```css
.a { display: none; }      /* 공간 X, 그려지지 않음, 이벤트 X */
.b { visibility: hidden; } /* 공간 O, 그려지지 않음, 이벤트 X */
.c { opacity: 0; }         /* 공간 O, 투명하게 그려짐, 이벤트 O */
```

> ➕ **보충**: 투명하지만 클릭되는 요소는 사용자를 헷갈리게 할 수 있습니다. 클릭을 막으려면 `pointer-events: none`을 함께 씁니다.

## 렌더링 과정과 리플로우, 리페인트

```
DOM + CSSOM → 렌더 트리 → Layout(리플로우) → Paint(리페인트) → Composite(합성)
```

앞 단계가 다시 실행되면 뒤의 단계도 모두 다시 실행됩니다. 그래서 **리플로우가 가장 비싸고, 컴포지팅만 일어나는 경우가 가장 저렴합니다.**

### 리플로우 (Reflow)
- 요소의 위치와 크기를 다시 계산하는 과정, 즉 레이아웃을 다시 하는 것입니다.
- 레이아웃: 브라우저가 HTML과 CSS를 바탕으로 각 요소를 화면의 어디에 얼마나 크게 배치할지 계산하는 단계입니다.
- 주변 요소의 레이아웃에도 영향을 줄 수 있고, 보통 리페인트까지 이어져 비용이 큽니다.

**언제 발생하나요?**
- 요소의 너비, 높이, 위치가 바뀔 때
- 브라우저 창 크기가 바뀔 때
- `display: none`을 적용하거나 해제할 때
- ➕ 폰트 크기나 텍스트 내용이 바뀔 때, 요소를 추가하거나 삭제할 때
- ➕ JS에서 `offsetWidth`, `getBoundingClientRect()` 같은 레이아웃 값을 읽을 때 (강제 동기 레이아웃)

### 리페인트 (Repaint)
- 위치와 크기는 그대로 두고, 보이는 모양만 다시 그리는 과정입니다. 리플로우보다 부담이 적습니다.
- **언제 발생하나요?** `color`, `background-color`, `visibility`, `box-shadow`, `outline` 등이 바뀔 때

### 컴포지팅 (Compositing, 합성)
- 브라우저는 화면을 여러 레이어로 나누어 관리하고, 이 레이어들을 합쳐 최종 화면을 만듭니다.
- `transform`과 `opacity`의 변화는 **레이아웃과 페인트를 건너뛰고 합성 단계에서만 처리될 수 있습니다.** 그래서 애니메이션에는 `top`/`left`보다 `transform`이 유리합니다.

```css
/* ❌ 프레임마다 리플로우 발생 */
.box { position: relative; transition: left 0.3s; }
.box:hover { left: 100px; }

/* ✅ 합성 단계에서 처리 */
.box { transition: transform 0.3s; }
.box:hover { transform: translateX(100px); }
```

> ➕ **보충**: `will-change: transform`으로 브라우저에 미리 레이어 분리를 알려줄 수 있습니다. 다만 남용하면 메모리를 많이 씁니다.

## 모의 면접

**1. display:none, visibility:hidden, opacity:0의 차이점은 무엇인가요?**

> `display: none`은 요소를 렌더 트리에서 제외해 레이아웃에서 공간이 사라집니다. 그래서 적용하거나 해제할 때 전체 배치를 다시 계산하는 리플로우가 일어나고, 화면 표시, 이벤트, 접근성이 모두 막힙니다.
> `visibility: hidden`은 레이아웃에서 공간은 유지하지만 페인트 단계에서 요소를 그리지 않습니다. 그래서 값을 바꿀 때 리플로우 없이 리페인트만 일어나고, 클릭 같은 이벤트에 반응하지 않으며 스크린 리더도 읽지 않습니다.
> `opacity: 0`은 레이아웃과 페인트 모두 정상적으로 처리되고 투명도만 0인 상태입니다. 그래서 이벤트에 반응하고 스크린 리더도 읽을 수 있습니다.

**2. 요소를 숨기면서도 클릭이나 호버 같은 이벤트가 동작하게 하려면 어떤 속성을 써야 하나요?**

> 세 속성 중 이벤트 상호작용이 유지되는 것은 `opacity: 0`이므로 이 속성을 사용합니다. 다만 보이지 않는 요소가 클릭되면 사용자가 혼란스러울 수 있어서, 의도적인 경우에만 쓰는 것이 좋습니다.

# Q32. BEM은 무엇이며, 사용하는 이유는?

## CSS 설계 방법론
CSS 코드를 구조화하고, 예측 가능하고 재사용할 수 있게 만드는 규칙과 지침입니다. BEM은 그중 하나입니다.

## BEM (Block, Element, Modifier)
클래스 이름을 명확한 규칙으로 정해 CSS의 예측 가능성과 재사용성을 높이는 방법론입니다.

| 구분 | 의미 | 예시 | 클래스명 규칙 |
|---|---|---|---|
| **Block** | 독립적이고 재사용할 수 있는 컴포넌트 단위 | 헤더, 버튼, 카드 | `.block-name` |
| **Element** | 블록의 일부. 블록 없이는 의미가 없어 블록에 종속됨 | 카드 이미지, 카드 제목 | `.block-name__element-name` (언더스코어 2개) |
| **Modifier** | 블록이나 요소의 모양, 상태, 동작을 바꾸는 변형 | 기본 버튼, 비활성 버튼 | `.block-name--modifier-name` (하이픈 2개) |

⚠️ **수정**: Modifier는 대시(—)가 아니라 **하이픈 2개(`--`)**를 씁니다. 예: `button--primary`

```html
<div class="card card--featured">
  <img class="card__image" src="thumb.png" alt="">
  <h2 class="card__title">제목</h2>
  <button class="button button--primary">구매</button>
  <button class="button button--disabled">품절</button>
</div>
```

```css
.card { padding: 16px; border: 1px solid #ddd; }
.card--featured { border-color: gold; }
.card__title { font-size: 18px; }
.button--primary { background: blue; color: white; }
```

➕ **보충: 주의할 점**
- Modifier는 **기본 클래스와 함께** 씁니다. 예: `class="button button--primary"`
- 요소 안의 요소라도 `card__body__title`처럼 중첩하지 않고 **`card__title`처럼 평평하게** 씁니다.
- 클래스 선택자 하나만 쓰기 때문에 명시도(specificity)가 낮고 균일해서 스타일 충돌이 적습니다.

## 장점과 단점
- **장점**: 예측 가능성, 재사용성, 유지보수 용이성, 명확한 구조, 낮고 일정한 명시도
- **단점**: 긴 클래스명, HTML 코드 증가, 초기 학습 곡선

## 언제 사용하면 좋을까?
- 여러 개발자가 협업하는 대규모 웹 앱
- React, Vue, Angular 같은 컴포넌트 기반 개발
- 재사용 가능한 UI 라이브러리 개발

> ➕ **보충**: React 등에서는 CSS Modules나 CSS-in-JS가 스타일 범위(scope)를 자동으로 분리해 줍니다. 그래서 BEM이 꼭 필요하지는 않지만, 일반 CSS나 Sass를 쓰는 환경에서는 여전히 많이 쓰입니다.

## 그 밖의 CSS 설계 방법론

### 1. OOCSS (Object Oriented CSS)
DRY(Don't Repeat Yourself) 원칙을 바탕으로 CSS를 객체처럼 설계합니다.

➕ **보충**: 원칙은 두 가지입니다.
1. **구조와 스킨 분리**: 크기나 여백 같은 구조와 색상이나 테두리 같은 스킨을 별도 클래스로 나눕니다.
2. **컨테이너와 콘텐츠 분리**: 요소가 어느 위치에 있든 같은 모양을 갖도록, 부모에 의존하는 선택자를 피합니다.

```css
/* 구조 */
.btn { padding: 8px 16px; border-radius: 4px; }
/* 스킨 */
.skin-primary { background: blue; color: white; }
.skin-danger  { background: red;  color: white; }

/* ❌ 컨테이너에 의존 */
.sidebar h3 { font-size: 20px; }
/* ✅ 위치와 무관 */
.heading-md { font-size: 20px; }
```

```html
<button class="btn skin-primary">확인</button>
<button class="btn skin-danger">삭제</button>
```

### 2. SMACSS (Scalable and Modular Architecture for CSS)
스타일을 5가지 범주로 나누어 관리합니다.

| 범주 | 설명 | 예시 |
|---|---|---|
| Base | HTML 요소의 기본 스타일 | `body`, `a` |
| Layout | 페이지의 주요 구역 레이아웃 (`l-` 접두사) | `.l-header` |
| Module | 재사용 가능한 독립 컴포넌트 | `.card` |
| State | 요소의 특정 상태 (`is-` 접두사) | `.is-active` |
| Theme | 시각적인 테마 | `.theme-dark` |

```css
/* Base */   body { margin: 0; font-family: sans-serif; }
/* Layout */ .l-header { display: flex; height: 60px; }
/* Module */ .card { padding: 16px; }
/* State */  .is-hidden { display: none; }
/* Theme */  .theme-dark .card { background: #222; color: #fff; }
```

### 3. Utility-First CSS
미리 정의된 작은 단위의 유틸리티 클래스를 HTML에서 조합해 스타일을 적용하는 방식입니다. Tailwind CSS가 대표적입니다.

```html
<button class="px-4 py-2 bg-blue-500 text-white rounded hover:bg-blue-600">
  버튼
</button>
```

- **장점**: 개발 속도가 빠르고, 클래스 이름을 고민할 필요가 없고, CSS 파일 관리 부담과 **캐스케이드(계단식) 문제**에서 벗어날 수 있습니다. 정해진 값(디자인 토큰)을 쓰므로 디자인 일관성도 유지됩니다.
- ➕ **단점**: HTML에 클래스가 많아져 가독성이 떨어지고, 유틸리티 클래스 이름을 익혀야 합니다.

### ⚠️ 수정: 계단식(Cascade) 문제란
"크기나 간격을 직접 계산하는 번거로움"이 **아닙니다.**
CSS(Cascading Style Sheets)의 캐스케이드 특성 때문에 생기는 문제입니다.

- CSS는 **전역 범위**라서, 한 곳에서 작성한 스타일이 의도하지 않은 다른 요소에 영향을 줄 수 있습니다.
- 명시도(specificity)와 선언 순서에 따라 스타일이 덮어써지기 때문에, 어떤 스타일이 왜 적용됐는지 추적하기 어렵습니다.
- 이를 이기려고 선택자를 점점 구체적으로 쓰거나 `!important`를 남발하게 됩니다.

```css
.title { color: black; }
.sidebar .title { color: gray; }   /* 명시도가 더 높아 덮어씀 */
.title { color: blue !important; } /* 결국 !important 경쟁 */
```

Utility-First 방식은 각 클래스가 하나의 스타일만 담당하고 HTML에 직접 붙이기 때문에, 이런 덮어쓰기 충돌이 거의 생기지 않습니다.

## 모의 면접

**1. BEM 방법론에서 Block, Element, Modifier의 역할과 클래스명 규칙은 무엇인가요?**

> Block은 독립적으로 재사용할 수 있는 컴포넌트 단위입니다. 버튼이나 헤더가 예시이고, `.button`처럼 작성합니다.
> Element는 블록을 이루는 일부분으로, 블록 없이는 의미가 없어 블록에 종속됩니다. 카드의 이미지나 제목이 예시이고, 블록 이름과 언더스코어 2개(`__`)로 연결해 `.card__image`처럼 작성합니다.
> Modifier는 블록이나 요소의 모양, 상태, 동작이 달라진 변형을 나타냅니다. 기본(primary), 비활성(disabled) 상태 등이 예시이고, 하이픈 2개(`--`)로 연결해 `.button--primary`처럼 작성합니다. 보통 `class="button button--primary"`처럼 기본 클래스와 함께 씁니다.

**2. 프로젝트 특성과 팀 상황에 따라 CSS 설계 방법론을 고를 때 핵심 기준은 무엇인가요?**

> 정답이 정해져 있지는 않지만, 팀 규모, 개발 속도, 유지보수성, 사용하는 기술 스택을 고려해 선택하는 것이 중요합니다. 예를 들어 여러 명이 협업하는 대규모 프로젝트라면 구조가 명확한 BEM, 빠른 개발이 중요하다면 Tailwind 같은 Utility-First 방식이 적합할 수 있습니다. 어떤 방법론을 고르든 팀 전체가 일관되게 적용하는 것이 가장 중요합니다.

# Q33. `@supports` 규칙은 언제 사용하나요?

웹을 개발하다 보면 "이 CSS 속성이 모든 브라우저에서 동작할까?"라는 고민이 생깁니다. 이때 쓰는 규칙이 `@supports`입니다.

## @supports
CSS 조건부 규칙 중 하나로, **CSS 속성-값 쌍**이나 선택자가 현재 브라우저에서 지원되는지 확인하고, 그 결과에 따라 다른 스타일을 적용합니다. 점진적 향상 전략을 구현할 때 중요한 역할을 합니다.

## 점진적 향상 (Progressive Enhancement)
기본 콘텐츠와 기능은 모든 사용자에게 제공하고, 최신 브라우저를 쓰는 사용자에게는 추가 기능을 제공하는 철학입니다.
- **장점**: 접근성 보장, 유연한 개발, 미래 지향적

## 언제 사용하나요?

### 1. 새로운 CSS 속성이나 값의 지원 여부 확인

```css
/* 기본(폴백): 모든 브라우저 */
.container { display: flex; flex-wrap: wrap; }
.box { width: 33.33%; }

/* grid를 지원하는 브라우저에만 적용 */
@supports (display: grid) {
  .container {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: 16px;
  }
  .box { width: auto; }
}
```

### 2. 특정 CSS 함수의 지원 여부 확인

```css
h1 { font-size: 24px; } /* 폴백 */

@supports (font-size: clamp(1rem, 5vw, 3rem)) {
  h1 { font-size: clamp(1.5rem, 5vw, 3rem); }
}
```

#### clamp()
- 최솟값과 최댓값을 정하고, 그 범위 안에서 값이 유동적으로 변하게 하는 함수입니다.
- 문법: `clamp(최솟값, 선호값, 최댓값)`
- 반응형 웹에 유용합니다. 예전에는 미디어 쿼리로 화면 크기마다 값을 따로 지정해야 했지만, `clamp()`는 선언 하나로 대응할 수 있습니다.

### 3. 벤더 프리픽스 대응
⚠️ **수정**: "벤더 프리픽스 없이"보다 "벤더 프리픽스 대응"이 정확합니다. `@supports`로 **접두사 버전과 표준 버전을 함께 확인**할 수 있기 때문입니다.

```css
.modal { background: rgba(255, 255, 255, 0.9); } /* 폴백 */

@supports (backdrop-filter: blur(10px)) or (-webkit-backdrop-filter: blur(10px)) {
  .modal {
    background: rgba(255, 255, 255, 0.5);
    -webkit-backdrop-filter: blur(10px);
    backdrop-filter: blur(10px);
  }
}
```

#### 벤더 프리픽스란
브라우저마다 CSS 기능을 지원하는 방식이나 시점이 다를 때, 표준화 전 기능을 특정 브라우저에서 쓰기 위해 속성 앞에 붙이는 접두사입니다.

| 접두사 | 브라우저 |
|---|---|
| `-webkit-` | Chrome, Safari, 최신 Edge, 최신 Opera |
| `-moz-` | Firefox |
| `-ms-` | Internet Explorer, 구형 Edge |
| `-o-` | 구형 Opera (현재 Opera는 `-webkit-` 사용) |

- 요즘은 Autoprefixer 같은 도구가 접두사를 자동으로 붙여 줍니다. `@supports`는 **지원 여부에 따라 아예 다른 스타일(폴백)을 적용**하는 세밀한 제어가 필요할 때 씁니다.
- ➕ **보충**: 최근 브라우저들은 새 기능을 접두사 대신 실험 플래그로 제공하는 추세라 접두사가 점점 줄고 있습니다.

## 문법
`and`, `or`, `not` 키워드로 여러 조건을 조합할 수 있습니다.

```css
@supports (display: grid) and (gap: 1rem) { ... }
@supports (position: sticky) or (position: -webkit-sticky) { ... }
@supports not (display: grid) { ... }

/* 선택자 지원 여부 확인 */
@supports selector(:has(img)) { ... }
```

➕ **보충**
- `and`와 `or`를 섞어 쓸 때는 반드시 괄호로 묶어야 합니다.
- JS에서는 `CSS.supports('display', 'grid')`로 같은 확인을 할 수 있습니다.

## 장점과 단점
- **장점**
  - 점진적 향상 구현
  - 미래 지향적인 코드
  - 유지보수 용이성
  - 성능 이점: Modernizr 같은 JS 기능 감지 없이 CSS만으로 분기하므로 JS 실행 비용이 없습니다.
- **단점**
  - 폴백 스타일과 최신 스타일을 모두 작성해야 해서 코드가 복잡해집니다.
  - CSS 문법(속성, 값, 선택자)의 지원 여부만 확인할 수 있고, JS API 등은 확인할 수 없습니다.
  - ➕ 브라우저가 **문법을 해석할 수 있는지만** 확인합니다. 실제로 버그 없이 동작하는지는 보장하지 않습니다.
  - ➕ IE처럼 `@supports` 자체를 지원하지 않는 브라우저도 있습니다. 그래서 **폴백 스타일은 `@supports` 바깥에 작성해야 합니다.**

## 모의 면접

**1. @supports 규칙은 어떤 문제를 해결하기 위해 쓰이며, 점진적 향상과 어떤 관련이 있나요?**

> 브라우저마다 지원하는 CSS 기능이 달라서, 최신 기능을 쓰면 일부 브라우저에서 레이아웃이 깨질 수 있습니다. `@supports`는 현재 브라우저가 특정 CSS 속성이나 값을 지원하는지 확인하고, 조건에 따라 스타일을 적용할 수 있게 해 이 문제를 해결합니다.
> 이를 통해 모든 사용자에게는 기본 스타일을 제공하고, 최신 브라우저 사용자에게만 추가 기능을 제공할 수 있습니다. 이것이 점진적 향상 철학과 맞닿아 있습니다.

**2. @supports를 쓸 때의 장점과 단점은 무엇이며, 실제로 어떤 경우에 유용한가요?**

> 장점은 점진적 향상을 구현할 수 있고, JS 없이 CSS만으로 기능 지원 여부를 분기할 수 있다는 점입니다.
> 단점은 폴백 스타일과 최신 스타일을 함께 작성해야 해서 코드가 복잡해지고, CSS 문법의 지원 여부만 확인할 수 있다는 점입니다.
> 실제로는 `grid`나 `gap` 같은 새 레이아웃 속성, `clamp()` 같은 CSS 함수, `backdrop-filter`처럼 브라우저마다 접두사가 필요한 속성을 적용할 때 유용합니다.
