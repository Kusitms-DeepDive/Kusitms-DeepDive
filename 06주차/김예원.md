# 6주차 정리
# Q90. 프로젝트 빌드와 배포가 무엇인가요?

## 한 줄 요약
빌드와 배포는 코드를 서버에 올리는 일이 아니라, **코드 작성부터 사용자 전달까지 전 과정을 자동화하는 "개발 조립 라인"**을 만드는 일이다.

---

## 1. CI / CD

| 구분 | 역할 | 프론트엔드에서 하는 일 |
|---|---|---|
| **CI** (지속적 통합) | 코드가 합쳐질 때마다 자동으로 품질 검사 | ESLint로 컨벤션 검사, Jest/Vitest로 컴포넌트 테스트 → 버그 있는 코드가 통합되는 것을 조기 차단 |
| **CD** (지속적 배포) | 통과한 코드를 자동으로 빌드해 실제 서버에 배포 | 최적화된 build/dist 폴더를 만들어 서버로 업로드 |

### 왜 필요한가?
- **번들링과 최적화**: 리액트/뷰 코드는 브라우저가 바로 읽을 수 없으므로 Vite/Webpack으로 합치고, 압축하고, 불필요한 코드를 제거해야 한다.
- **품질 일관성**: 린트, 포맷(Prettier), 테스트를 자동으로 검사하지 않으면 협업 시 품질이 들쑥날쑥해진다.
- **빠른 피드백과 배포**: 수동으로 5~10분 걸리는 과정을 `git push` 한 번으로 해결한다.
- 결국 반복 작업을 자동화해 생산성을 높이고 **휴먼 에러를 방지**하는 것이 목적이다.

---

## 2. CI/CD 도구 비교

| 구분 | 깃허브 액션 | 버셀 / 네트리파이 |
|---|---|---|
| 성격 | 범용 CI/CD 도구 | 프론트엔드 특화 배포 플랫폼 |
| 설정 | `.yml`로 스크립트를 직접 상세 작성 | 저장소 연결 시 프레임워크를 자동 감지해 설정 |
| 장점 | 커스터마이징 자유도 높음, AWS S3/EC2 등 특정 인프라에 유연 | 설정 거의 없음, PR마다 미리보기 URL 자동 생성, 글로벌 CDN 내장 |
| 단점 | 배포 스크립트와 인프라 학습 필요 | 복잡한 커스터마이징 어려움 |

**선택 기준**
- Next.js, Nuxt.js, Astro 같은 최신 프레임워크 → 버셀/네트리파이 추천
- 회사 자체 클라우드 인프라에 배포해야 함 → 깃허브 액션으로 직접 파이프라인 구축

### 💡 Q. 버셀을 깃허브에 연결하면 CI/CD가 자동으로 챙겨지는 건가?
**연결만으로 자동인 것은 사실상 CD(빌드·배포)이고, 린트/타입/테스트 같은 CI는 별도 워크플로우를 작성해야 한다.** 책의 "깃 저장소 연결만으로 CI/CD가 거의 완성"이라는 표현은 배포 쪽 이야기로 읽는 게 정확하다.

- **버셀이 자동으로 해주는 것**
  - push마다 `build` 실행 후 배포
  - PR마다 프리뷰 URL 생성
  - main 머지 시 프로덕션 배포
- **자동이 아닌 것**: 린트, 타입 체크, 테스트
  - 버셀은 빌드 커맨드만 실행하므로, 빌드만 성공하면 린트 에러가 있어도 배포될 수 있다.
  - Next.js는 `next build` 중 타입 체크를 하지만 린트 실행 여부는 버전·설정에 따라 다르다.
  - Vite는 build 스크립트에 `tsc`를 넣지 않으면 타입 체크를 건너뛴다.

따라서 **PR 프리체크 워크플로우(lint, type-check, test)를 직접 작성하는 것도 CI/CD를 챙기는 것에 포함**된다. 실무 조합은 보통 아래와 같다.

| 역할 | 도구 | 하는 일 |
|---|---|---|
| CI | GitHub Actions | PR 시 lint, `tsc --noEmit`, test 실행 |
| 머지 게이트 | 브랜치 보호 규칙 | 위 체크를 Required status checks로 지정해 통과해야만 머지 가능 |
| CD | Vercel | main 머지 시 자동 빌드·배포 |

이렇게 하면 검증을 통과한 코드만 main에 들어가고, 그 main이 자동 배포되는 완전한 파이프라인이 된다.
(참고: PR 단계의 프리뷰 배포는 체크 결과와 무관하게 생성된다.)

## 3. 정적 웹 사이트 호스팅 파이프라인 (깃허브 액션 + AWS S3)

1. **코드 푸시**: main 브랜치에 `git push`하면 파이프라인 시작
2. **의존성 설치 + 린트**: `npm install` → `npm run lint` (실패 시 파이프라인 중단)
3. **단위 테스트**: `npm test`
4. **프로덕션 빌드**: `npm run build` → build 또는 dist 폴더 생성
5. **배포**: `jakejarvis/s3-sync-action`으로 S3 버킷에 동기화

```yaml
- name: Deploy to AWS S3
  uses: jakejarvis/s3-sync-action@v2.0
  with:
    args: --acl public-read --delete   # 공개 읽기 권한으로 올리고, 이전 파일은 삭제
  env:
    AWS_S3_BUCKET: ${{ secrets.AWS_S3_BUCKET }}
    AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
    AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    AWS_REGION: 'ap-northeast-2'
    SOURCE_DIR: 'build'
```

- AWS 액세스 키 같은 민감 정보는 코드에 절대 직접 넣지 않는다.
- 깃허브 저장소의 **Settings → Secrets and variables → Actions**에 등록하고 `${{ secrets.XXX }}`로 사용한다.

## 4. S3와 CDN이란?

### S3 (Simple Storage Service)
- HTML, CSS, JavaScript 등 빌드한 프론트엔드 파일을 저장하는 클라우드 저장소
- 빌드한 파일을 S3에 올려두면 웹사이트를 제공할 수 있음

**보충**
- AWS가 제공하는 오브젝트 스토리지로, 버킷(폴더)을 만들어 파일을 넣어두는 클라우드 하드디스크로 이해하면 쉽다.
- 프론트엔드 빌드 결과물은 서버 로직 없이 **파일 그 자체**로 동작하므로, S3에 올려두고 브라우저가 가져가게 하면 배포가 끝난다.
- 서버를 직접 띄우고 관리할 필요가 없고, 저렴하며, 용량 걱정이 없다.

### CDN (Content Delivery Network)
- 사용자와 가까운 서버에서 파일을 전달해 웹사이트 로딩 속도를 높이는 네트워크
- 원본 파일을 여러 지역의 서버에 캐싱해 사용자에게 빠르게 전달함

**보충**
- 비유: 본사 창고(S3, 서울) 하나에서 전 세계에 배송하면 느리므로, 나라별 지역 물류센터(CDN)에 미리 재고를 깔아두는 것.
- 효과: 로딩 속도 향상, 원본 서버 부하 감소, 트래픽 폭주 대응.

### 실무에서의 조합
- 보통 **S3(원본 저장) + CloudFront(AWS의 CDN)** 로 사용한다.
- S3 정적 웹사이트 엔드포인트는 HTTPS를 지원하지 않으므로, HTTPS와 커스텀 도메인을 쓰려면 CloudFront가 사실상 필요하다.
- 책 예제의 `--acl public-read`는 단순화한 예시다. 실무에서는 버킷을 비공개로 두고 CloudFront를 통해서만 접근시키는 구성을 많이 쓴다.
- 버셀/네트리파이가 "글로벌 CDN 내장"이라는 건 이 구성을 플랫폼이 알아서 해준다는 뜻이다.

## 5. 도커를 이용한 CI/CD

정적 파일은 S3에 올리면 끝나는 경우가 많지만, **Next.js SSR처럼 복잡한 서버 환경이 필요하면 도커가 강력**하다.

### 도커란?
- 앱 실행에 필요한 모든 것(코드, 라이브러리, 설정)을 **컨테이너**라는 표준화된 공간에 담아 어디서든 똑같이 실행하는 기술.
- 바다의 선적 컨테이너처럼, 내용물이 무엇이든 규격화된 상자에 담으면 어떤 배나 트럭으로도 옮길 수 있다.
- 개발 → 테스트 → 운영 환경을 통일하고, 가상머신보다 훨씬 가볍고 빠르다.
- 한 서버에서 여러 앱을 서로 영향 없이 독립적으로 실행할 수 있다.

### 💡 Q. 도커가 SSR에서 강력한 이유는?
핵심은 **SSR은 정적 파일이 아니라 "계속 실행되는 서버 프로세스"를 배포해야 하기 때문**이다.

| 구분 | 배포 대상 | 필요한 것 |
|---|---|---|
| 정적 사이트 | build 결과물(HTML/JS/CSS) | S3/CDN에 올리면 끝, 실행 환경 불필요 |
| SSR | 요청마다 렌더링하는 Node 서버 | Node 런타임, 특정 Node 버전, 환경변수, 포트, 네이티브 의존성 → S3로는 불가능 |

도커가 맞는 이유
1. **환경 통일**: 런타임과 앱을 이미지로 묶어 로컬/스테이징/프로덕션이 동일하게 동작한다. ("내 PC에선 되는데" 방지)
2. **어디든 배포 가능**: AWS ECS/EC2, GCP, 온프레미스 등 도커만 돌아가면 되므로 특정 플랫폼(버셀)에 종속되지 않는다.
3. **확장성**: 컨테이너를 복제해 수평 확장하기 쉽다.
4. **멀티 스테이지 빌드**로 SSR 이미지도 가볍게 유지할 수 있다.

### 멀티 스테이지 빌드
빌드에만 필요한 무거운 도구까지 최종 이미지에 들어가면 용량이 불필요하게 커진다. 이를 해결하기 위해 Dockerfile 안에서 스테이지를 나누고, 최종 단계에는 꼭 필요한 결과물만 담는다.

**① 빌드 스테이지** – 앱을 빌드하는 전용 스테이지

```dockerfile
FROM node:18-alpine as builder      # 'builder'라는 별칭의 스테이지 시작
WORKDIR /app                        # 작업 디렉터리 설정
COPY package*.json ./               # package.json만 먼저 복사 → 의존성 캐싱 활용
RUN npm install
COPY . .                            # 전체 소스 코드 복사
RUN npm run build                   # 프로덕션 빌드 실행
```

**② 실행 스테이지** – 실제 서비스에 필요한 최소 환경만 포함

```dockerfile
FROM nginx:stable-alpine                              # 경량 웹 서버 이미지로 최종 스테이지 시작
COPY --from=builder /app/build /usr/share/nginx/html  # builder에서 만든 결과물만 복사
EXPOSE 80                                             # 80번 포트 노출
CMD ["nginx", "-g", "daemon off;"]                    # 엔진엑스 서버 실행
```

**효과**: 최종 이미지에는 엔진엑스와 빌드 완료된 정적 파일만 포함되므로 용량이 작고, 배포가 빠르고, 보안 면에서도 더 안전하다.

**배포 흐름**: CI/CD 배포 단계에서 이미지 빌드 → Docker Hub / AWS ECR 같은 레지스트리에 푸시 → 서버에서 해당 이미지를 받아 실행하도록 스크립트 작성

## 6. 모의 면접 답변 가이드

**Q1. 프론트엔드 개발에서 CI와 CD가 각각 담당하는 역할은 무엇이며, 자동화했을 때 얻을 수 있는 이점은?**
> CI는 코드가 통합될 때마다 린트와 테스트로 품질을 자동 검증하고, CD는 검증된 코드를 자동으로 빌드해 서버에 배포합니다. 자동화하면 반복 작업이 줄어 생산성이 오르고, 휴먼 에러가 방지되며, 결과물의 품질이 일관되게 유지됩니다.

**Q2. 도커 멀티 스테이지 빌드를 활용하면 어떤 문제를 해결할 수 있으며, 최종 배포 이미지가 어떻게 개선되나요?**
> 빌드에만 필요한 무거운 도구가 최종 이미지에 포함되어 용량이 커지는 문제를 해결합니다. 빌드 스테이지와 실행 스테이지를 분리해 결과물만 담으므로 이미지 용량이 작아지고, 배포 속도가 빨라지며, 불필요한 도구가 빠져 보안도 좋아집니다.

## 7. 핵심 정리
- 프론트엔드 CI/CD는 이제 **선택이 아닌 필수**다.
- 버셀/네트리파이는 **CD(배포)를 간편하게** 해주고, 린트·타입·테스트 같은 **CI는 GitHub Actions로 직접 구성**하는 것이 실무 조합이다.
- 정적 사이트는 **S3 + CDN**, SSR 같은 서버 환경은 **도커**가 적합하다.
- 도커 멀티 스테이지 빌드로 환경을 통일하고 경량 이미지를 만들어 더 안정적이고 효율적으로 배포한다.

# Q92. 번들러를 사용하는 이유는 무엇인가요?

## 한 줄 요약
번들러는 단순히 흩어진 파일을 묶는 도구가 아니라, **의존성을 체계적으로 관리하고 다양한 최적화 기법으로 웹 앱의 성능을 끌어올리는 현대 프론트엔드 개발의 심장** 같은 존재다.

---

## 1. 과거 방식의 한계

과거에는 `<script>` 태그로 자바스크립트 파일을 하나씩 불러왔다.

```html
<html>
<head>
  <title>My Awesome App</title>
</head>
<body>
  ...
  <script src="js/library1.js"></script>
  <script src="js/library2.js"></script>
  <script src="js/utils.js"></script>
  <script src="js/api.js"></script>
  <script src="js/ui.js"></script>
  <script src="js/main.js"></script>
</body>
</html>
```

간단해 보이지만 심각한 문제가 숨어 있다.

| 문제 | 설명 |
|---|---|
| **네트워크 병목 현상** | 브라우저는 `<script>` 태그를 만날 때마다 서버에 파일을 요청한다. 파일이 10개면 10번, 100개면 100번의 HTTP 요청이 발생하고, 각 요청에는 보이지 않는 지연 시간(latency)이 존재한다. 여러 심부름을 한 번에 처리하지 않고 하나씩 따로따로 다녀오는 것과 같다. |
| **복잡한 의존성 관리** | main.js가 api.js의 함수를 쓰고, api.js가 utils.js의 함수를 쓴다고 하자. 이때 스크립트 로딩 순서가 꼬이면 즉시 오류가 발생한다. 프로젝트가 커질수록 이런 의존성을 수동으로 관리하기 어려워진다. |
| **불필요한 코드 로딩** | library1.js의 수많은 기능 중 함수 하나만 필요해도 파일 전체를 내려받아야 한다. 성능 측면에서 매우 비효율적이다. |

---

## 2. 번들러와 의존성 그래프

- 번들러는 **여러 개로 나뉜 코드 조각을 분석해서 브라우저가 가장 효율적으로 처리할 수 있는 몇 개의 파일로 합치는 역할**을 한다.
- 이 과정을 **번들링(bundling)** 이라고 한다.

### 번들링 과정에서 이루어지는 최적화

| 최적화 | 설명 |
|---|---|
| **번들링** (bundling) | 여러 개의 JS와 CSS 파일을 하나 또는 소수의 파일로 병합한다. HTTP 요청 수가 줄어 네트워크 병목이 완화되고 초기 로딩 속도가 크게 향상된다. |
| **트랜스파일링** (transpiling) | 최신 JS 문법이나 JSX를 구형 브라우저도 이해할 수 있는 ES5 문법으로 변환한다. Babel 같은 도구를 활용하며, 직접적인 속도 향상보다는 **안정성(호환성)** 에 기여한다. 더 많은 사용자가 문제없이 서비스를 이용하게 만드는 과정이다. |
| **코드 최소화** (minification) | 동작에 영향을 주지 않는 공백, 주석, 줄 바꿈을 제거하고 변수명을 짧게 바꿔 파일 크기를 줄인다. 내려받는 시간이 줄어 사용자가 더 빠르게 콘텐츠를 볼 수 있다. |
| **코드 분할** (code splitting) | 거대한 번들 파일 하나 대신 당장 필요한 코드와 나중에 필요한 코드를 분리한다. 초기 화면에 필요한 최소한의 코드만 먼저 불러오고, 사용자가 특정 페이지로 이동하거나 기능을 실행할 때 나머지를 동적으로 불러온다. 이를 **지연 로딩(lazy loading)** 이라고 한다. |

> 💡 **보충: 번들러가 필요한 근본적인 이유**
> 브라우저는 예전에 파일 간 `import`를 지원하지 않았고, 지금도 `import` 하는 파일마다 요청이 발생한다. 번들러는 이런 제약을 개발 단계에서 미리 정리해서 브라우저가 가장 처리하기 좋은 형태로 만들어 주는 도구다.

### 번들러의 의존성 그래프 (dependency graph)

번들러의 핵심은 **의존성 그래프를 만드는 것**이다.

```
메인 자바스크립트(진입점) → 모듈 A, B → C, D → E, F ...
                    ↓
              웹팩(모듈 번들러)
                    ↓
            자바스크립트 번들
```

1. **진입점(entry point) 설정**: 번들러에 프로젝트의 시작점이 되는 파일을 알려준다.
2. **의존성 분석**: 번들러가 해당 파일을 읽고 `import`나 `require` 같은 키워드를 통해 어떤 모듈이 필요한지 파악한다.
3. **그래프 완성**: 연결된 모든 모듈을 연쇄적으로 따라가며 프로젝트 전체의 코드 관계도를 완성한다. 마치 가족 관계도를 그리듯 말이다. 이렇게 완성된 그래프를 바탕으로 번들러는 최종 결과물을 만들어 낸다.

> 💡 **보충: 의존성 그래프의 장점**
> - 파일 간 의존 관계를 번들러가 알고 있으므로 **로딩 순서를 자동으로 보장**한다. (수동으로 `<script>` 순서를 맞출 필요가 없다.)
> - 어디서도 `import` 되지 않는 코드는 결과물에서 제외할 수 있다. 이를 **트리 쉐이킹(tree shaking)** 이라고 하며, 불필요한 코드 로딩 문제를 줄이는 데 쓰인다.

---

## 3. 웹팩과 비트

두 번들러는 **같은 목표**를 가지고 있지만 **내부 동작 방식**에 차이가 있다.

### 웹팩 (Webpack): 강력하고 성숙한 표준 번들러

- 모든 짐을 꼼꼼하게 챙겨 출발하는 **캠핑카**에 비유할 수 있다.
- 수많은 **로더(loader)** 와 **플러그인(plugin)** 을 통해 이미지, 글꼴, CSS 등 거의 모든 종류의 자원을 처리할 수 있다.
- 오랜 시간 다양한 환경에서 검증되어 복잡하고 규모가 큰 프로젝트에서도 안정적으로 사용할 수 있다.
- **단점**
  - 코드를 수정할 때마다 전체 의존성 그래프를 다시 분석하고 번들링하는 과정을 거치므로, 프로젝트가 커질수록 **개발 서버 실행 속도와 코드 수정 반영 속도가 느려질 수 있다.**
  - 다양한 기능을 지원하는 만큼 초기 설정이 다소 복잡하게 느껴질 수 있다.

> 💡 **보충: 로더(loader)와 플러그인(plugin)이란?**
>
> 웹팩은 기본적으로 **JavaScript 파일만 이해**한다. CSS, 이미지, TypeScript 같은 다른 형식은 로더와 플러그인이 있어야 처리할 수 있다.
>
> | 구분 | 역할 | 비유 | 예시 |
> |---|---|---|---|
> | **로더 (loader)** | **개별 파일을 변환**해서 웹팩이 이해할 수 있는 모듈로 바꿔 준다. 파일 단위로 동작한다. | 번역가 (다른 언어 → 웹팩이 아는 언어) | `babel-loader` (최신 JS/JSX → ES5), `css-loader`, `style-loader` (CSS를 JS에서 import), `ts-loader` (TypeScript → JS), `file-loader` (이미지·폰트 처리) |
> | **플러그인 (plugin)** | 번들링 **전체 과정에 개입**해서 결과물 최적화, 파일 생성, 환경 변수 주입 같은 **부가 기능**을 수행한다. | 공장의 후처리 공정 | `HtmlWebpackPlugin` (HTML 파일 자동 생성 및 번들 연결), `MiniCssExtractPlugin` (CSS를 별도 파일로 분리), `DefinePlugin` (환경 변수 주입) |
>
> 쉽게 말해 **로더는 "파일을 어떻게 읽을까"**, **플러그인은 "번들 결과를 어떻게 가공할까"** 를 담당한다.
>
> ```js
> // webpack.config.js 예시
> module.exports = {
>   entry: './src/index.js',          // 진입점
>   module: {
>     rules: [
>       { test: /\.css$/, use: ['style-loader', 'css-loader'] },  // 로더
>       { test: /\.jsx?$/, use: 'babel-loader' },
>     ],
>   },
>   plugins: [new HtmlWebpackPlugin()],  // 플러그인
> };
> ```

### 비트 (Vite): 빠르고 현대적인 차세대 번들러

- 가볍게 출발하고 필요한 물건은 현지에서 바로 조달하는 **스포츠카**에 비유할 수 있다.
- 개발 환경에서 모든 파일을 미리 번들링하지 않고, 브라우저가 기본적으로 지원하는 **ES 모듈**을 활용해 **요청된 파일만 즉시 변환**해서 전달한다.
- 덕분에 개발 서버 구동과 코드 수정 반영이 거의 즉각적이다.
- 대부분의 설정이 기본으로 내장되어 있어 비교적 간단하게 시작할 수 있다.
- 프로덕션 빌드 단계에서는 내부적으로 최적화된 번들링 과정을 거쳐 웹팩에 못지않은 훌륭한 결과물을 만든다.
- **단점**: 생태계가 상대적으로 작아서 아주 특수한 요구 사항을 처리하기 위한 플러그인이 부족할 수 있다. (다만 빠르게 성장하고 있다.)

> 💡 **보충: ES 모듈(ESM)이란?**
>
> **ES 모듈은 자바스크립트 공식 표준 모듈 시스템**이다. `import`와 `export` 문법으로 파일 간에 코드를 주고받는다.
>
> ```js
> // utils.js
> export function add(a, b) {
>   return a + b;
> }
>
> // main.js
> import { add } from './utils.js';
> console.log(add(1, 2));
> ```
>
> ```html
> <!-- 브라우저에서 직접 사용 -->
> <script type="module" src="main.js"></script>
> ```
>
> - 과거 JS에는 모듈 개념이 없어서 `<script>` 순서에 의존하거나, Node.js의 `require`(CommonJS) 같은 방식을 썼다.
> - 이제는 **최신 브라우저가 ES 모듈을 기본으로 지원**한다. 브라우저가 `import` 구문을 만나면 해당 파일을 직접 요청한다.
> - Vite는 이 점을 이용해 개발 중에는 **번들링을 생략**한다. 브라우저가 `import`로 필요한 파일을 요청하면 그때 그 파일만 변환해서 응답하는 것이다.
> - 웹팩은 전체를 먼저 번들링한 뒤 서버를 띄우므로 프로젝트가 클수록 시작이 느려지고, Vite는 요청된 파일만 처리하므로 프로젝트 크기와 관계없이 시작이 빠르다.
>
> 정적 분석이 가능한 `import`/`export` 구조 덕분에 앞서 말한 **트리 쉐이킹**도 가능해진다.

### 웹팩 vs 비트 비교

| 구분 | 웹팩 | 비트 |
|---|---|---|
| 비유 | 캠핑카 (다 챙겨서 출발) | 스포츠카 (가볍게 출발, 현지 조달) |
| 개발 환경 방식 | 전체를 먼저 번들링한 뒤 서버 실행 | 번들링 없이 ES 모듈로 요청된 파일만 변환 |
| 개발 서버 속도 | 프로젝트가 클수록 느려짐 | 빠름 (거의 즉각적) |
| 설정 | 다소 복잡 | 기본 설정이 내장되어 간단 |
| 생태계 | 오래 검증된 방대한 로더/플러그인 | 상대적으로 작지만 빠르게 성장 중 |
| 프로덕션 빌드 | 안정적 | 내부적으로 최적화된 번들링 수행 |
| 적합한 상황 | 복잡하고 규모가 큰 프로젝트, 특수한 요구 사항이 많은 레거시/대형 프로젝트 | 새 프로젝트, 빠른 개발 경험이 중요한 경우, 비교적 표준적인 구성 |

## 4. 모의 면접 답변 가이드

**Q1. 번들러가 없던 시절에는 네트워크 병목, 의존성 관리, 불필요한 코드 로딩 문제를 각각 어떻게 해결했나요?**
> 책에서는 번들러가 없던 시절의 해결 방법을 직접 다루지 않고 "문제가 있었다"는 점만 설명합니다. 아래는 일반적으로 쓰이던 방식을 정리한 답변입니다.
>
> - **네트워크 병목**: 여러 파일을 수동으로 하나로 이어 붙이거나(concat), CSS 스프라이트처럼 요청 수를 줄이는 방식으로 대응했습니다. 또한 파일을 합치고 압축하는 Grunt, Gulp 같은 태스크 러너를 사용했습니다.
> - **의존성 관리**: `<script>` 태그의 로딩 순서를 개발자가 직접 맞췄고, 전역 변수 충돌을 막기 위해 즉시 실행 함수(IIFE) 패턴을 쓰거나 RequireJS 같은 모듈 로더(AMD)를 사용했습니다.
> - **불필요한 코드 로딩**: 필요한 기능만 골라 담은 커스텀 빌드를 만들거나, 직접 파일을 분리해 필요한 페이지에서만 `<script>`를 넣는 식으로 대응했습니다. 다만 모두 수작업이라 한계가 컸고, 이 문제를 체계적으로 해결하려고 번들러가 등장했습니다.

**Q2. 웹팩과 비트의 개발 환경과 설정 방식의 차이는 무엇이며 각각 어떤 상황에 더 적합할까요?**
> 웹팩은 개발 서버를 띄우기 전에 전체 의존성 그래프를 분석해 번들링하기 때문에 프로젝트가 커질수록 서버 실행과 수정 반영이 느려질 수 있고, 로더와 플러그인을 직접 설정해야 해서 초기 설정이 다소 복잡합니다. 대신 오랜 기간 검증된 방대한 생태계 덕분에 복잡하고 규모가 큰 프로젝트나 특수한 요구 사항이 있는 경우에 적합합니다.
>
> 비트는 개발 환경에서 번들링 없이 브라우저의 ES 모듈을 활용해 요청된 파일만 즉시 변환하므로 서버 구동과 코드 반영이 매우 빠르고, 대부분의 설정이 기본으로 내장되어 있어 시작이 간단합니다. 프로덕션 빌드에서는 내부적으로 최적화된 번들링을 수행합니다. 그래서 빠른 개발 경험이 중요한 새 프로젝트에 적합하고, 특수한 플러그인이 필요한 경우에는 생태계가 아직 작다는 점을 고려해야 합니다.

## 5. 이렇게 답변할 수 있어요 (요약)
번들러는 여러 자바스크립트, CSS 파일을 분석·통합해 의존성을 관리하고 네트워크 병목과 불필요한 코드 로딩 문제를 해결하는 핵심 도구다. 또한 트랜스파일링, 코드 최소화, 코드 분할 등 다양한 최적화를 통해 성능과 호환성을 보장한다. **웹팩은 강력한 생태계와 안정성**을, **비트는 빠른 개발 환경과 간결함**을 강점으로 가지며 현대 프론트엔드 개발에서 필수적인 요소다.

# Q97. 프론트엔드에서 사용하는 TDD 기법을 설명할 수 있나요?

## 한 줄 요약
TDD는 단순히 버그를 잡는 테스트 행위가 아니라, **테스트가 개발 과정을 이끌어 가는 설계 방법론**이다. 실패하는 테스트를 먼저 작성하고, 최소한의 코드로 통과시킨 뒤, 리팩터링하는 사이클을 반복한다.

---

## 1. TDD의 핵심 주기

**TDD(Test-Driven Development)** 란 **실제 프로덕션 코드를 작성하기 전에 실패하는 테스트 케이스를 먼저 작성하는** 개발 방식이다.
3단계의 짧은 주기를 반복하며, 이를 **Red-Green-Refactor 사이클**이라고 부른다.

```
   RED (실패하는 테스트를 작성하라)
    ↓
   GREEN (코드를 동작하게 하라)
    ↓
   REFACTOR (코드를 개선하라)
    ↓
   다시 RED로 ...
```

| 단계 | 의미 | 핵심 포인트 |
|---|---|---|
| **1. RED** | 실패하는 테스트를 작성하라 | 기능 구현 코드가 아직 없으므로 테스트는 **반드시 실패해야 한다.** 실패(Red)를 확인하는 것이 첫 단계의 목표 |
| **2. GREEN** | 코드를 동작하게 하라 | 테스트를 통과시키기 위한 **가장 최소한의 프로덕션 코드**만 작성한다. 비효율적이거나 지저분해도 괜찮다. |
| **3. REFACTOR** | 코드를 개선하라 | 중복 제거, 가독성 향상, 구조 개선. 이 과정에서 **기존 테스트는 계속 통과**해야 한다. |

### 단계별 예시 (로그인 버튼)
요구사항: *"사용자가 로그인 버튼을 클릭했을 때 환영 메시지가 화면에 나타나야 한다."*

1. **RED**: 로그인 버튼을 클릭했을 때 `'환영합니다'` 텍스트를 가진 요소가 존재하는지 검증하는 테스트를 먼저 작성한다. (구현이 없으므로 실패)
2. **GREEN**: 로그인 버튼에 클릭 이벤트를 추가하고, 클릭 시 `'환영합니다'` 텍스트를 가진 `div`를 렌더링하는 코드를 작성한다. (테스트 성공)
3. **REFACTOR**: 로그인 로직을 별도 함수로 분리하거나 컴포넌트 구조를 더 효율적으로 변경한다. 변경 후에도 테스트를 실행해 여전히 Green인지 확인한다.

> 💡 **보충: 예시 코드 (React Testing Library + Jest/Vitest)**
> ```jsx
> // Login.test.jsx  ← 1) RED: 먼저 작성 (Login 컴포넌트가 없거나 기능이 없어 실패)
> import { render, screen } from '@testing-library/react';
> import userEvent from '@testing-library/user-event';
> import Login from './Login';
>
> test('로그인 버튼을 클릭하면 환영 메시지가 나타난다', async () => {
>   render(<Login />);
>   await userEvent.click(screen.getByRole('button', { name: '로그인' }));
>   expect(screen.getByText('환영합니다')).toBeInTheDocument();
> });
> ```
> ```jsx
> // Login.jsx  ← 2) GREEN: 테스트를 통과시키는 최소한의 코드
> import { useState } from 'react';
>
> export default function Login() {
>   const [loggedIn, setLoggedIn] = useState(false);
>   return (
>     <div>
>       <button onClick={() => setLoggedIn(true)}>로그인</button>
>       {loggedIn && <div>환영합니다</div>}
>     </div>
>   );
> }
> // 3) REFACTOR: 구조 개선 후에도 위 테스트는 계속 통과해야 함
> ```

### 왜 이 순서로 진행할까?
- **실패를 먼저 확인**해야 테스트가 제대로 동작하는지 믿을 수 있다. (처음부터 통과하는 테스트는 아무것도 검증하지 못할 수 있다.)
- **최소한의 코드**로 통과시키면 불필요한 과잉 구현을 막고 작은 단위로 빠르게 진행할 수 있다.
- **테스트가 안전망**이 되므로 리팩터링 중에도 기존 기능을 망가뜨리지 않았음을 보장받는다.
- 이 사이클을 **아주 작은 단위로 빠르게 반복**하며 소프트웨어 기능을 점진적으로 완성해 나가는 것이 TDD의 핵심이다.

## 2. TDD의 주요 기법 (프론트엔드)

프론트엔드에서 TDD는 주로 **UI 컴포넌트와 사용자 상호작용**을 중심으로 이루어진다.
화면에 무엇이 보이고, 사용자의 행동에 따라 어떤 변화가 일어나는지를 검증하는 것이 핵심이다.

| 기법 | 설명 |
|---|---|
| **컴포넌트 렌더링 테스트** | 특정 컴포넌트가 주어진 props에 따라 의도한 대로 화면에 잘 그려지는지 테스트 |
| **사용자 이벤트 시뮬레이션** | 사용자가 버튼을 클릭하거나 폼에 텍스트를 입력하는 등의 행동을 코드로 시뮬레이션하고, 그 결과로 상태(state)나 UI가 예상대로 변경되는지 검증 |
| **상태 관리 로직 테스트** | 리덕스, 주스탠드 등 상태 관리 라이브러리의 로직을 검증. 특히 Reducer, Action 같은 **순수 함수**가 입력값에 따라 예측할 수 있게 동작하는지 테스트 |

> 💡 **보충: 순수 함수가 테스트하기 쉬운 이유**
> 순수 함수는 같은 입력이면 항상 같은 출력을 내고 외부 상태에 영향을 주지 않는다. 그래서 별도 환경 설정 없이 `입력 → 기대 출력`만 비교하면 되어 TDD와 궁합이 좋다.
> ```js
> // reducer 테스트 예시
> test('INCREMENT 액션이면 count가 1 증가한다', () => {
>   expect(counterReducer({ count: 0 }, { type: 'INCREMENT' })).toEqual({ count: 1 });
> });
> ```

## 3. TDD의 테스트 도구

TDD를 실천하려면 테스트 코드를 작성하는 것만으로는 부족하다. **테스트를 실행하고, 사용자 행동을 시뮬레이션하며, 전체 흐름을 검증할 수 있는 도구**가 함께 갖춰져야 한다.

프론트엔드 테스트 도구는 크게 세 가지로 구분할 수 있다.

1. 테스트를 **실행**하는 도구 (러너/프레임워크)
2. 컴포넌트를 **사용자 관점에서 검증**하는 도구 (테스팅 라이브러리)
3. 실제 사용자 **시나리오 전체를 점검**하는 도구 (E2E)

각각 목적과 사용 범위가 다르므로 상황에 맞게 적절히 조합해 사용하는 것이 중요하다.

### 3-1. 테스트 러너와 프레임워크
테스트를 실행하고 결과를 관리해 주는 도구.

| 도구 | 설명 |
|---|---|
| **제스트 (Jest)** | 페이스북에서 만들었으며, 별도 설정 없이 바로 쓸 수 있는 **올인원(All-in-one)** 테스트 프레임워크. 테스트 실행, 단언(assertion), 모의(mocking) 객체 생성 기능을 모두 내장하고 있어 가장 널리 쓰인다. |
| **비테스트 (Vitest)** | 비트 기반 프로젝트에서 매우 빠른 속도를 자랑하는 최신 테스트 프레임워크. 제스트와 유사한 API를 제공해 마이그레이션이 쉽다. |

> 💡 **보충: 용어 설명**
> - **테스트 러너(test runner)**: 테스트 파일을 찾아 실행하고 통과/실패 결과를 보여 주는 도구
> - **단언(assertion)**: "이 값은 이래야 한다"를 검증하는 구문. 예) `expect(result).toBe(3)`
> - **모의(mocking)**: API 호출 같은 외부 의존성을 가짜 객체로 대체해 테스트를 독립적으로 만드는 것

### 3-2. 테스팅 라이브러리
UI 컴포넌트를 **실제 사용자 관점**에서 테스트하도록 도와주는 도구.

| 도구 | 설명 |
|---|---|
| **리액트 테스팅 라이브러리 (React Testing Library)** | **"사용자의 관점에서 테스트하라"** 는 철학을 가진 라이브러리. 컴포넌트 내부 구현보다는 실제 사용자가 경험하는 방식을 테스트하도록 유도하여 **리팩터링에 더 강건한 테스트**를 작성하게 도와준다. 제스트 같은 러너와 함께 사용한다. |
| **뷰 테스트 유틸 (Vue Test Utils)** | 뷰 공식 테스트 유틸리티 라이브러리. 뷰 컴포넌트를 분리하여 테스트할 수 있는 메서드를 제공한다. |

> 💡 **보충: 왜 "사용자 관점"이 리팩터링에 강할까?**
> - 내부 구현에 의존한 테스트(예: state 변수명, 내부 함수 호출 여부 확인)는 리팩터링 때 **동작이 같아도 테스트가 깨진다.**
> - 사용자 관점 테스트(예: "버튼을 누르면 '환영합니다'가 보인다")는 내부 구조를 바꿔도 **사용자에게 보이는 결과가 같다면 통과**한다.
> - 이는 TDD의 REFACTOR 단계("기존 테스트는 계속 통과해야 한다")와 잘 맞는다.

### 3-3. E2E 테스트 도구
**E2E(End-to-End)** 테스트는 단위 테스트보다 더 큰 범위의 **사용자 시나리오**를 검증하는 도구다. TDD의 작은 단위 테스트와는 성격이 조금 다르지만, **전체 흐름을 보장하는 데 매우 중요**하다.

| 도구 | 설명 |
|---|---|
| **사이프레스 (Cypress)** | 개발자가 **실제 브라우저에서 사용자의 시나리오 전체**(회원가입부터 상품 구매까지 등)를 자동화하여 테스트할 수 있게 해주는 도구. TDD의 개별 단위 테스트보다는 더 큰 흐름의 통합 테스트에 가깝다. |
| **플레이라이트 (Playwright)** | 마이크로소프트에서 개발했으며 사이프레스와 유사하게 E2E 테스트를 자동화하는 도구. **크로미움, 파이어폭스, 웹킷 등 다양한 브라우저를 지원**하는 것이 강점. |

### 한눈에 비교

| 구분 | 대표 도구 | 테스트 범위 | 역할 |
|---|---|---|---|
| 러너/프레임워크 | Jest, Vitest | 전체 (실행 환경) | 테스트 실행, 단언, 모킹, 결과 관리 |
| 테스팅 라이브러리 | React Testing Library, Vue Test Utils | 컴포넌트 단위 | 사용자 관점에서 UI 렌더링·이벤트 검증 |
| E2E 도구 | Cypress, Playwright | 사용자 시나리오 전체 | 실제 브라우저에서 전체 흐름 자동화 검증 |

> 💡 **보충: 함께 쓰는 모습**
> 실무에서는 보통 **Jest/Vitest(러너) + React Testing Library(컴포넌트 검증)** 를 묶어서 쓰고, 중요한 핵심 사용자 흐름만 **Cypress/Playwright**로 추가 검증한다. 도구끼리 경쟁 관계가 아니라 **역할이 다른 보완 관계**다.

## 4. 모의 면접 답변 가이드

**Q1. TDD의 핵심 주기인 Red-Green-Refactor는 각각 어떤 의미를 가지며 왜 이 순서로 진행될까요?**
> RED는 구현 전에 실패하는 테스트를 먼저 작성해 기능의 요구사항을 정의하는 단계이고, GREEN은 그 테스트를 통과시킬 최소한의 코드를 작성하는 단계이며, REFACTOR는 테스트가 통과하는 안전망 아래에서 중복을 제거하고 가독성과 구조를 개선하는 단계입니다.
> 이 순서로 진행하는 이유는, 먼저 실패를 확인해야 테스트가 제대로 동작함을 보장할 수 있고, 최소한의 코드로 통과시켜 과잉 구현을 막으며, 테스트가 통과하는 상태에서 리팩터링해야 기존 기능이 망가지지 않았음을 확신할 수 있기 때문입니다. 이 사이클을 작은 단위로 빠르게 반복하며 기능을 점진적으로 완성합니다.

**Q2. 프론트엔드에서 TDD를 적용할 때 자주 활용되는 테스트 도구(제스트, 테스팅 라이브러리, 사이프레스 등)의 역할 차이는 무엇인가요?**
> 제스트·비테스트는 테스트를 실행하고 단언, 모킹, 결과 관리를 담당하는 러너/프레임워크입니다. 리액트 테스팅 라이브러리나 뷰 테스트 유틸은 컴포넌트를 실제 사용자 관점에서 렌더링하고 이벤트를 시뮬레이션해 검증하는 도구입니다. 사이프레스·플레이라이트는 실제 브라우저에서 회원가입부터 구매까지 같은 사용자 시나리오 전체를 자동화해 검증하는 E2E 도구입니다. 즉 범위와 목적이 다르므로 상황에 맞게 조합해서 사용합니다.

## 5. 이렇게 답변할 수 있어요 (요약)
TDD는 실패하는 테스트를 먼저 작성한 뒤 최소한의 코드로 통과시키고, 이후 리팩터링하는 사이클을 반복하는 개발 방법론이다. 이를 Red-Green-Refactor 사이클이라고 한다. 프론트엔드에서는 컴포넌트 렌더링, 사용자 이벤트, 상태 관리 로직을 중심으로 테스트하며, 제스트·비테스트, 리액트 테스팅 라이브러리, 사이프레스·플레이라이트 같은 도구가 활용된다. 이 방식은 단순한 버그 탐지가 아니라 **설계 품질 향상과 유지보수성 강화**를 목표로 하며, 안정적이고 확신 있는 개발을 가능하게 한다.

---

## 6. 핵심 정리
- TDD = **테스트가 개발을 이끄는** 방법론 (Red → Green → Refactor 반복)
- 프론트엔드 TDD의 중심은 **UI 컴포넌트 + 사용자 상호작용**
- 도구는 역할별로 구분해서 조합: **러너(Jest/Vitest) / 테스팅 라이브러리(RTL) / E2E(Cypress/Playwright)**
- 사용자 관점 테스트는 **리팩터링에 강하다**
