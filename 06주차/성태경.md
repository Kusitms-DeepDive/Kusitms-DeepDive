# 7장. 실무에서 필요한 프로젝트 지식

## Q90. 프로젝트 빌드와 배포가 무엇인가요?

### 면접 답변

빌드는 개발자가 작성한 소스 코드와 의존성을 브라우저나 실행 환경이 사용할 수 있는 배포 가능한 결과물로 변환하는 과정입니다. 프런트엔드에서는 타입스크립트나 JSX 변환, 모듈 번들링, 코드 분할, 압축, 정적 자산 처리 등이 이루어지며, 그 결과 `dist`와 같은 디렉터리에 HTML, 자바스크립트, CSS 등의 아티팩트가 생성됩니다.

배포는 검증된 빌드 아티팩트를 실제 사용자가 접근할 수 있는 환경에 전달하고 서비스하는 과정입니다. 정적 사이트라면 결과물을 오브젝트 스토리지와 CDN에 게시하고, SSR 애플리케이션이라면 서버나 컨테이너에 배치해 프로세스를 실행합니다. 배포에는 단순 파일 업로드뿐 아니라 환경 설정, 캐시 무효화, 상태 확인, 트래픽 전환과 롤백도 포함됩니다.

실무에서는 이 과정을 CI/CD 파이프라인으로 자동화합니다. CI에서 코드 스타일, 타입, 테스트와 빌드를 검증하고, CD에서 검증된 아티팩트를 스테이징이나 프로덕션 환경으로 전달합니다. 이를 통해 반복 작업과 휴먼 에러를 줄이고, 같은 절차로 재현 가능한 배포와 빠른 피드백, 문제 발생 시 신속한 롤백이 가능해집니다.

### 핵심 개념

#### 빌드와 배포

| 구분 | 빌드 | 배포 |
| --- | --- | --- |
| **입력** | 소스 코드, 의존성, 빌드 설정 | 검증된 빌드 아티팩트, 배포 설정 |
| **핵심 작업** | 변환, 번들링, 최적화, 정적 자산 처리 | 업로드·배치, 설정 적용, 트래픽 연결 |
| **출력** | 실행 가능한 아티팩트 | 사용자가 접근할 수 있는 서비스 |
| **대표 실패** | 컴파일 오류, 타입 오류, 테스트 실패 | 권한 오류, 설정 누락, 헬스 체크 실패 |
| **완료 기준** | 배포 가능한 결과물 생성 | 대상 환경에서 새 버전이 정상 제공됨 |

- **소스 코드**: 개발과 유지보수를 위해 작성한 원본 코드
- **아티팩트**: 빌드 과정을 통과해 배포 대상으로 고정된 결과물
- **릴리스**: 특정 버전의 기능을 사용자에게 제공하기로 결정하는 행위
- **배포**: 아티팩트를 실행 환경에 설치하고 실제 트래픽을 받을 수 있게 만드는 행위

> 배포했다고 반드시 모든 사용자에게 기능이 공개되는 것은 아님. 배포 후 기능 플래그로 노출 시점을 별도로 제어할 수 있으므로 배포와 릴리스는 구분할 필요가 있음

#### 프런트엔드 빌드 과정

```text
소스 코드와 의존성
  → 린트·타입 검사·테스트
  → 트랜스파일링
  → 모듈 분석과 번들링
  → 코드 분할·트리 셰이킹·최소화
  → 파일명 해시와 정적 자산 처리
  → 배포 아티팩트 생성
```

- **트랜스파일링**: 타입스크립트, JSX, 최신 자바스크립트 문법을 목표 환경이 이해할 수 있는 코드로 변환
- **번들링**: 모듈의 의존성 그래프를 분석해 배포에 적합한 파일 묶음 생성
- **트리 셰이킹**: 실제로 사용되지 않는 내보내기 제거
- **코드 분할**: 초기 실행에 필요한 코드와 나중에 불러올 코드를 청크 단위로 분리
- **최소화**: 공백, 주석, 긴 식별자 등 실행에 불필요한 부분을 줄여 전송 크기 축소
- **콘텐츠 해시**: 파일 내용이 달라질 때 파일명도 달라지게 하여 장기 캐시와 새 버전 갱신을 양립
- **소스 맵**: 변환된 코드의 위치를 원본 소스와 연결해 오류 추적과 디버깅 지원

빌드는 단순히 여러 파일을 하나로 합치는 작업에 그치지 않습니다. 대상 브라우저와 실행 환경에 맞게 코드를 변환하고, 초기 로딩에 필요한 네트워크 비용을 줄이며, 결과물을 일관된 형태로 만드는 과정입니다.

#### 배포 대상에 따른 차이

| 유형 | 대표 결과물 | 대표 배포 대상 | 실행 위치 |
| --- | --- | --- | --- |
| **정적 SPA** | HTML, JS, CSS, 이미지 | S3·Cloud Storage·CDN, Vercel·Netlify | 주로 브라우저 |
| **정적 사이트 생성(SSG)** | 미리 생성된 HTML과 정적 자산 | 오브젝트 스토리지와 CDN | 빌드 시 HTML 생성, 브라우저에서 상호작용 |
| **SSR 애플리케이션** | 서버 번들, 클라이언트 번들, 정적 자산 | 서버리스·Node.js 서버·컨테이너 | 서버와 브라우저 |

- **정적 배포**: 파일 업로드, CDN 배포, 캐시 정책과 SPA 라우팅 설정이 핵심
- **서버 배포**: 런타임, 프로세스, 포트, 헬스 체크, 확장과 로그 수집까지 고려
- **공통 요구사항**: 버전 식별, 환경 설정, 접근 권한, 모니터링, 장애 시 롤백 경로

#### CI와 CD

| 개념 | 역할 | 일반적인 자동화 항목 |
| --- | --- | --- |
| **CI(지속적 통합)** | 변경 사항을 자주 통합하고 조기에 결함 탐지 | 의존성 설치, 린트, 타입 검사, 테스트, 빌드 |
| **Continuous Delivery(지속적 제공)** | 모든 변경을 프로덕션에 배포 가능한 상태로 유지 | 아티팩트 생성·보관, 스테이징 배포, 검증, 프로덕션 승인 대기 |
| **Continuous Deployment(지속적 배포)** | 검증을 통과한 변경을 승인 없이 자동으로 프로덕션 배포 | 프로덕션 배포, 검증, 트래픽 전환, 자동 롤백 |

- **CD의 두 의미**: 조직과 문맥에 따라 Continuous Delivery 또는 Continuous Deployment를 지칭
- **지속적 제공**: 프로덕션 반영 직전에 사람이나 비즈니스 규칙의 승인 단계 존재 가능
- **지속적 배포**: 품질 게이트를 통과하면 별도의 명시적 승인 없이 프로덕션까지 진행

> 책에서는 CD를 지속적 배포로 설명하지만, 면접이나 협업에서는 상대가 Delivery와 Deployment 중 어느 의미로 사용하는지 먼저 확인하는 편이 정확함

> 참고: [AWS - Understanding CI/CD](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-cicd-litmus/understanding-cicd.html)

#### 일반적인 프런트엔드 파이프라인

```text
commit / pull request
  → 의존성 설치
  → lint·format·type check
  → unit·component·E2E test
  → production build
  → 아티팩트 저장
  → preview·staging 배포
  → 승인 또는 자동 품질 게이트
  → production 배포
  → 모니터링·검증·롤백
```

- **빠른 실패**: 비용이 적고 빠른 정적 검사부터 실행하고, 오래 걸리는 E2E 테스트는 뒤에 배치
- **품질 게이트**: 필수 검사에 실패한 변경의 병합이나 배포 차단
- **아티팩트 보관**: 빌드 결과와 버전을 연결하여 어떤 코드가 배포됐는지 추적
- **환경 보호**: 프로덕션 환경의 승인자, 배포 가능 브랜치, 시크릿 접근 범위 제한
- **배포 후 검증**: 헬스 체크, 스모크 테스트, 오류율과 핵심 지표 확인
- **롤백**: 이전 정상 아티팩트로 빠르게 되돌릴 수 있는 경로 확보

#### 재현 가능한 의존성 설치

CI 환경에서는 일반적으로 `npm install`보다 `npm ci`가 적합합니다.

- `package-lock.json` 필수
- `package.json`과 잠금 파일의 의존성 불일치 시 오류 종료
- 기존 `node_modules` 제거 후 깨끗한 설치
- 설치 과정에서 잠금 파일을 수정하지 않는 동작
- 로컬과 CI의 의존성 버전 차이 감소

> 참고: [npm CLI - npm-ci](https://docs.npmjs.com/cli/commands/npm-ci/)

#### Build once, deploy many

- **한 번만 빌드**: CI에서 검증을 마친 아티팩트를 한 번 생성
- **동일 아티팩트 승격**: 같은 결과물을 개발·스테이징·프로덕션 순서로 이동
- **불변성**: 배포 후 아티팩트 내용 수정 금지, 변경이 필요하면 새 버전 생성
- **추적 가능성**: 커밋 SHA, 빌드 번호, 아티팩트 버전과 배포 이력을 연결
- **환경 차이 최소화**: 환경별 재빌드로 서로 다른 결과물이 만들어지는 문제 방지

환경별 API 주소처럼 실행 시 달라져야 하는 값은 런타임 설정 파일이나 서버 주입 방식으로 분리할 수 있습니다. 다만 빌드 도구가 환경변수를 클라이언트 코드에 치환했다면 그 값은 최종 번들에서 누구나 확인할 수 있습니다.

> 프런트엔드 환경변수는 이름에 `SECRET`이 붙어 있거나 CI의 시크릿 저장소에서 주입했더라도 브라우저 번들에 포함되는 순간 비밀 정보가 아님. 서버 전용 API 키와 자격 증명은 클라이언트 코드에 포함하지 않아야 함

#### GitHub Actions를 이용한 CI 예시

```yaml
name: frontend-ci

on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: frontend-dist
          path: dist
```

- **워크플로**: 저장소 이벤트에 의해 실행되는 하나 이상의 자동화 작업 정의
- **잡**: 같은 러너에서 순서대로 실행되는 스텝의 묶음
- **아티팩트 업로드**: 빌드 결과를 후속 배포 잡이나 검증 과정에서 재사용
- **프로젝트별 조정**: 테스트 명령과 빌드 출력 경로는 프로젝트 설정에 맞게 변경

> 참고: [GitHub Docs - GitHub Actions 이해하기](https://docs.github.com/ko/actions/get-started/understand-github-actions), [GitHub Docs - Continuous integration](https://docs.github.com/ko/actions/get-started/continuous-integration)

#### 도커 멀티 스테이지 빌드

정적 프런트엔드 결과물을 Nginx로 서비스하는 예시입니다.

```dockerfile
# 빌드에 필요한 도구와 의존성을 사용하는 단계
FROM node:22-alpine AS builder
WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

# 실행에 필요한 결과물만 포함하는 단계
FROM nginx:stable-alpine AS runtime
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

- **빌드 단계**: Node.js, 패키지 매니저, 소스 코드와 개발 의존성 포함
- **실행 단계**: Nginx와 정적 빌드 결과물만 포함
- **이미지 크기 감소**: `node_modules`, 소스 코드, 빌드 도구가 최종 이미지에서 제외
- **공격 표면 감소**: 운영에 불필요한 도구와 패키지 제거
- **환경 일관성**: 개발·CI·운영에서 같은 이미지 실행 가능
- **적용 범위 확인**: `dist`를 생성하는 정적 빌드 예시이며 SSR 앱은 서버 런타임과 서버 번들을 실행 단계에 포함해야 함

> 참고: [Docker Docs - Multi-stage builds](https://docs.docker.com/get-started/docker-concepts/building-images/multi-stage-builds/)

#### 안전한 배포와 롤백

| 전략 | 방식 | 장점 | 주의점 |
| --- | --- | --- | --- |
| **Preview 배포** | PR마다 독립 URL 생성 | 리뷰와 QA를 프로덕션 전 수행 | 테스트 데이터와 접근 권한 관리 |
| **Rolling** | 인스턴스를 순차 교체 | 추가 자원 부담이 비교적 적음 | 잠시 두 버전이 함께 동작 |
| **Blue-Green** | 구·신 환경을 함께 두고 트래픽 전환 | 빠른 전환과 롤백 | 이중 환경 비용 |
| **Canary** | 일부 사용자부터 점진적으로 새 버전 노출 | 실제 지표로 위험 제어 | 트래픽 분배와 관측 체계 필요 |

- **정적 자산 캐시**: 해시가 포함된 JS·CSS에 긴 `max-age`와 `immutable` 적용 가능
- **HTML 캐시**: 최신 해시 파일을 참조하도록 짧은 캐시 또는 재검증 정책 고려
- **관측 가능성**: 배포 버전별 오류율, 성능, 핵심 사용자 행동 지표 확인
- **자동 롤백 기준**: 헬스 체크 실패, 오류율 급증, 핵심 지표 악화 등 명시

> 참고: [GitHub Docs - Managing deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments)

#### 자주 혼동하는 부분

- **빌드 성공과 배포 성공의 구분**: 아티팩트 생성 성공이 실제 서비스 정상 동작을 보장하지는 않음
- **배포와 릴리스의 구분**: 코드는 배포하되 기능 플래그로 사용자 노출을 미룰 수 있음
- **CI와 CD의 구분**: CI는 변경 통합과 검증, CD는 검증된 변경을 환경으로 전달하는 과정
- **시크릿과 클라이언트 설정의 구분**: CI 시크릿도 브라우저 번들에 포함하면 공개 정보
- **최신 빌드만 보관하는 방식의 위험**: 이전 정상 버전으로 즉시 되돌릴 수 없으므로 버전별 아티팩트 보관 필요
- **배포 때마다 다시 빌드하는 방식의 위험**: 의존성이나 설정 변화로 검증한 결과물과 실제 배포 결과물이 달라질 가능성

### 모의 면접

#### 1. 프런트엔드 개발에서 CI와 CD가 각각 담당하는 역할은 무엇이며 이를 자동화했을 때 얻을 수 있는 이점은 무엇인가요?

CI는 개발자의 변경 사항을 자주 통합하면서 린트, 타입 검사, 테스트와 빌드를 자동으로 실행해 결함을 조기에 발견하는 역할을 합니다. CD는 이 검증을 통과한 아티팩트를 스테이징이나 프로덕션 같은 실행 환경에 일관된 절차로 전달합니다. 이때 Continuous Delivery라면 프로덕션 반영 전에 승인 단계가 있을 수 있고, Continuous Deployment라면 품질 게이트를 통과한 변경이 자동으로 프로덕션까지 배포됩니다.

두 과정을 자동화하면 사람마다 다른 수동 절차와 누락을 줄이고, 모든 변경에 같은 품질 기준을 적용할 수 있습니다. 또한 실패 지점을 빠르게 확인하고 검증된 아티팩트와 배포 이력을 남길 수 있어 배포 속도와 재현성, 추적 가능성, 롤백 안정성이 높아집니다.

#### 2. 도커 멀티 스테이지 빌드를 활용하면 어떤 문제를 해결할 수 있으며 최종 배포 이미지가 어떻게 개선되나요?

멀티 스테이지 빌드는 애플리케이션을 만드는 빌드 환경과 실제로 실행하는 런타임 환경을 하나의 Dockerfile 안에서 분리합니다. 첫 단계에서는 Node.js와 개발 의존성을 사용해 프런트엔드를 빌드하고, 마지막 단계에서는 생성된 정적 파일처럼 실행에 꼭 필요한 결과물만 Nginx 등의 경량 런타임 이미지에 복사합니다.

그 결과 소스 코드, `node_modules`, 컴파일러와 빌드 도구가 최종 이미지에서 제외되어 이미지 크기와 전송 시간이 줄어듭니다. 운영에 필요하지 않은 패키지가 제거되므로 공격 표면도 작아지고, 빌드와 실행 환경이 명확히 분리되어 재현성과 유지보수성도 높아집니다.

## Q92. 번들러를 사용하는 이유는 무엇인가요?

### 면접 답변

번들러는 진입점에서 시작해 모듈 간 의존성을 분석하고, 브라우저에 전달하기 적합한 하나 이상의 파일로 묶는 도구입니다. 과거에는 여러 스크립트를 직접 불러오면서 요청 수가 늘고, 개발자가 실행 순서를 관리해야 하며, 사용하지 않는 라이브러리 코드까지 내려받는 문제가 있었습니다. 번들러는 의존성 그래프를 바탕으로 이런 문제를 줄이고, 트리 셰이킹과 코드 분할 등으로 필요한 코드가 적절한 시점에 전달되도록 돕습니다.

실제 빌드 환경에서는 번들러와 변환 도구, 플러그인을 함께 사용해 TypeScript·JSX 변환, 코드 최소화, CSS·이미지 처리와 소스 맵 생성도 수행합니다. 현대 브라우저는 ES 모듈을 직접 실행하고 HTTP/2·3도 다중 요청의 비용을 줄여 주지만, 불필요한 코드의 전송·실행 비용이나 중첩된 의존성의 로딩 지연까지 해결하지는 않습니다. 따라서 번들러의 목적은 파일 개수를 무조건 줄이는 것이 아니라, 초기 로딩과 후속 탐색, 캐시 재사용을 함께 최적화하는 데 있습니다.

Webpack은 로더와 플러그인을 통한 세밀한 제어와 축적된 생태계가 강점이고, Vite는 네이티브 ES 모듈을 활용한 개발 서버와 기본 설정을 제공해 빠르게 개발을 시작하기 좋습니다. Vite도 프로덕션에서는 최적화된 번들을 생성하므로, 개발 중의 코드 제공 방식과 배포 결과물의 생성 방식을 구분해서 설명해야 합니다.

### 핵심 개념

#### 여러 스크립트를 직접 불러오던 방식의 한계

```html
<!-- 전역 변수에 의존한다면 사용하는 쪽보다 제공하는 쪽을 먼저 실행해야 함 -->
<script src="/js/library.js"></script>
<script src="/js/utils.js"></script>
<script src="/js/api.js"></script>
<script src="/js/main.js"></script>
```

| 문제 | 발생 이유 | 과거의 완화 방법과 한계 |
| --- | --- | --- |
| **네트워크 병목** | 파일별 요청·응답 비용, 연결 제약, 파서 차단 스크립트의 실행 대기 | 파일 수동 병합, 최소화, 브라우저 캐시·CDN 활용. 배포 때 병합 순서와 갱신 관리 필요 |
| **의존성 관리** | `main.js`가 사용하는 전역 함수를 앞선 파일에서 제공해야 하는 구조 | HTML 태그 순서 수동 관리, 네임스페이스·IIFE로 전역 충돌 완화. 파일 간 관계는 여전히 별도 관리 |
| **불필요한 코드 로딩** | 라이브러리 전체를 불러오거나 모든 페이지에 같은 스크립트 포함 | 페이지별 파일 분리, 필요한 기능만 담은 커스텀 빌드, 스크립트 동적 삽입. 변경 시 누락·중복 관리 부담 |

- **요청과 실행의 구분**: 브라우저가 미리 요청하거나 병렬 다운로드할 수 있으므로 모든 스크립트 요청이 반드시 직렬로 발생하는 것은 아님
- **`defer`**: 외부 클래식 스크립트를 HTML 파싱과 병렬로 내려받고, 파싱 이후 문서에 작성된 순서대로 실행. 실행 순서 문제는 완화하지만 의존성 관계 자체를 분석하지는 않음
- **`async`**: 준비되는 대로 실행하므로 태그 작성 순서를 보장하지 않음. 서로 의존하는 스크립트에 무작정 적용하면 오류 가능
- **수동 병합의 한계**: 요청 수는 줄일 수 있지만 미사용 코드 제거, 기능별 지연 로딩과 캐시 단위를 자동으로 결정하지는 못함

> 참고: [MDN - script 요소](https://developer.mozilla.org/ko/docs/Web/HTML/Reference/Elements/script)

#### 진입점과 의존성 그래프

- **진입점(Entry point)**: 분석을 시작할 파일. SPA의 시작 스크립트, 여러 페이지의 진입 파일 등 프로젝트에 따라 하나 또는 여러 개 지정
- **모듈 해석(Resolve)**: `import` 경로와 패키지 설정 등을 읽고 실제 대상 파일 결정
- **의존성 분석**: 각 파일의 `import`, `export`, 지원하는 `require()` 등을 따라 연결된 모듈 탐색
- **그래프 구성**: 모듈을 노드로, 의존 관계를 간선으로 표현. 공통 의존성과 동적 로딩 경계 파악
- **결과물 생성**: 그래프와 설정을 바탕으로 필요한 코드를 묶고, 공통 코드와 나중에 필요한 코드는 별도 청크로 분리 가능

```text
main.js (진입점)
  ├─ 정적 import → api.js → utils.js
  ├─ 정적 import → home.js → utils.js
  └─ 동적 import → editor.js → 큰 편집기 라이브러리

가능한 출력 예시
  ├─ main.[hash].js       : 초기 화면 코드와 공통 유틸리티
  └─ editor.[hash].js     : 편집기를 열 때 불러올 코드
```

- **모듈과 청크의 차이**: 모듈은 소스 코드의 구성 단위, 청크는 빌드 도구가 모듈들을 묶어 만든 출력 단위. 소스 파일 하나와 출력 파일 하나가 반드시 대응하지는 않음
- **분석 범위의 한계**: 실행 시에만 결정되는 임의의 경로까지 완벽히 추론할 수는 없음. 동적 import의 경로 작성 방식과 도구별 분석 규칙 확인 필요

> 참고: [Webpack - Entry Points](https://webpack.js.org/concepts/entry-points/), [Webpack - Module Resolution](https://webpack.js.org/concepts/module-resolution/), [Webpack - Code Splitting](https://webpack.js.org/guides/code-splitting/)

#### 번들링과 함께 수행하는 작업

| 작업 | 목적 | 주의할 점 |
| --- | --- | --- |
| **번들링** | 의존 모듈을 분석해 적절한 출력 파일로 구성 | 전체 코드를 하나로 묶으면 초기 로딩과 캐시 갱신에 불리할 수 있음 |
| **트랜스파일링** | TypeScript·JSX·최신 문법을 실행 가능한 JavaScript로 변환 | 문법 변환과 타입 검사는 별개. 대상 브라우저에 맞는 변환 설정 필요 |
| **트리 셰이킹** | 사용되지 않고 안전하게 제거할 수 있는 코드 제외 | 정적 분석 가능성과 부수 효과 판단에 따라 제거 범위가 달라짐 |
| **최소화(Minification)** | 불필요한 공백·주석 제거, 식별자 축약 등으로 코드 크기 감소 | gzip·Brotli 같은 HTTP 전송 압축과 별개의 작업 |
| **코드 분할(Code splitting)** | 기능·경로별로 청크를 나누어 필요한 시점에 로딩 | 분할 자체가 코드 총량을 줄이는 것은 아니며, 추가 요청과 대기 발생 가능 |
| **자산 처리** | CSS·이미지·폰트의 출력 경로와 참조 관계 관리 | 출력 파일 분리·인라인 여부와 배포 기준 경로 확인 |

- **도구의 역할 구분**: 번들러가 모든 변환을 직접 구현하는 것은 아님. 컴파일러, 로더, 플러그인과 연동해 하나의 빌드 파이프라인 구성
- **문법과 API의 구분**: 문법을 변환해도 `Promise`나 다른 브라우저 API가 자동으로 생기지는 않음. 지원 환경에 따라 별도 폴리필 검토
- **개발과 운영의 차이**: 개발 중에는 빠른 갱신과 디버깅, 프로덕션에서는 전송량·실행 비용·캐시 효율에 우선순위 부여

> 참고: [Webpack - Concepts](https://webpack.js.org/concepts/), [Vite - Building for Production](https://vite.dev/guide/build.html)

#### 브라우저가 ES 모듈을 지원해도 번들러를 쓰는 이유

```html
<script type="module" src="/src/main.js"></script>
```

- **네이티브 ESM**: 브라우저가 `import`·`export`를 이해하고 모듈 간 의존성을 처리. 단순한 앱은 번들러 없이도 구성 가능
- **패키지 이름 해석**: 브라우저는 Node.js처럼 `node_modules`를 자동 탐색하지 않음. `import 'some-package'` 같은 이름에는 import map을 제공하거나 빌드 도구로 경로를 해석하는 과정 필요
- **변환 요구사항**: TypeScript 타입 구문이나 JSX를 그대로 실행할 수는 없으므로 일반적으로 JavaScript로 변환하는 단계 필요
- **최적화의 공백**: 네이티브 ESM으로 특정 내보내기만 import해도 브라우저가 해당 파일에서 나머지 코드를 잘라 내려받는 것은 아님. 배포 전에 미사용 코드를 제거하는 최적화는 별도 역할

> 참고: [MDN - JavaScript modules](https://developer.mozilla.org/ko/docs/Web/JavaScript/Guide/Modules), [Webpack - Tree Shaking](https://webpack.js.org/guides/tree-shaking/)

#### HTTP/2·3 시대의 번들링 판단

- **전송 계층의 개선**: HTTP/2의 멀티플렉싱과 헤더 압축은 여러 요청의 비용을 완화. HTTP/3는 QUIC을 사용해 패킷 손실 시 서로 다른 스트림 간의 전송 차단 문제도 줄임
- **남아 있는 의존성 지연**: `main.js`를 받은 뒤에야 `a.js`를 발견하고, 다시 `a.js`를 받은 뒤 `b.js`를 발견한다면 중첩된 import로 추가 왕복 발생 가능
- **남아 있는 CPU 비용**: 전송 프로토콜이 개선되어도 불필요한 JavaScript의 파싱·컴파일·실행 비용은 남음. 트리 셰이킹과 지연 로딩으로 필요한 코드부터 전달할 이유
- **거대한 단일 번들의 비용**: 첫 화면에서 쓰지 않는 기능까지 다운로드하고 처리하며, 작은 변경에도 큰 파일의 캐시가 무효화될 수 있음
- **지나친 분할의 비용**: 작은 파일을 과도하게 만들면 요청 처리와 의존성 탐색 부담 증가. 요청 개수만으로 성능을 판단하기 어려움
- **실무 판단**: 네트워크 지연, 압축 후 전송량, 초기 실행 시간, 재방문 캐시와 화면 전환 지연을 함께 측정해 청크 경계 조정

> 참고: [MDN - Evolution of HTTP](https://developer.mozilla.org/ko/docs/Web/HTTP/Guides/Evolution_of_HTTP), [Vite - Why Vite](https://vite.dev/guide/why.html), [web.dev - Reduce JavaScript payloads with code splitting](https://web.dev/articles/reduce-javascript-payloads-with-code-splitting)

#### 트리 셰이킹의 전제와 한계

```js
// math.js: 모듈을 불러오기만 해도 실행되는 별도 부수 효과가 없는 예시
export const add = (a, b) => a + b;
export const subtract = (a, b) => a - b;

// main.js
import { add } from './math.js';
console.log(add(1, 2));
```

- **정적 ESM 구조**: `add`만 사용한다는 사실을 빌드 시 분석할 수 있어, 최적화 설정에 따라 `subtract` 제거 가능
- **ESM 보존**: 번들러가 분석하기 전에 모듈을 CommonJS로 변환하면 ESM의 정적 구조를 활용하기 어려워질 수 있음
- **부수 효과(Side effect)**: 전역 값 수정, 이벤트 등록, 폴리필 적용, CSS import처럼 모듈 로딩 자체가 필요한 동작 수행
- **제거의 안전성**: 사용하지 않는 export가 있어도 모듈의 부수 효과는 유지해야 할 수 있음. `sideEffects: false`를 잘못 지정하면 필요한 초기화나 스타일이 사라지는 오류 발생
- **라이브러리 구조의 영향**: CommonJS나 런타임에 속성을 결정하는 코드 등은 분석이 제한될 수 있음. CommonJS를 전혀 최적화할 수 없다는 의미는 아니며 도구와 코드 형태에 따라 차이 존재
- **확인 방법**: named import를 썼다는 이유만으로 최적화를 단정하지 말고 프로덕션 결과물과 번들 분석으로 실제 포함된 모듈 확인

부수 효과가 있는 CSS와 초기화 파일을 명시하는 `package.json` 설정 예시입니다. 실제 프로젝트의 부수 효과 파일에 맞게 목록을 작성해야 합니다.

```json
{
  "sideEffects": ["**/*.css", "./src/register.js"]
}
```

> 참고: [Webpack - Tree Shaking](https://webpack.js.org/guides/tree-shaking/)

#### 동적 import와 청크 전략

```js
// 편집기 버튼을 누를 때 편집기 모듈을 요청하는 예시
const editorButton = document.querySelector('#open-editor');

editorButton?.addEventListener('click', async () => {
  editorButton.disabled = true;

  try {
    const { openEditor } = await import('./editor.js');
    openEditor();
  } catch (error) {
    console.error('편집기를 불러오지 못했습니다.', error);
    // 실제 UI에서는 오류 안내와 재시도 수단 제공
  } finally {
    editorButton.disabled = false;
  }
});
```

- **`import()`**: 모듈 로딩 결과를 Promise로 반환. 빌드 도구는 이 지점을 지연 로딩 청크의 경계로 활용 가능
- **코드 분할과 지연 로딩**: 전자는 출력 파일을 나누는 작업, 후자는 필요한 시점까지 로딩을 미루는 동작. `import()`를 시작 시점에 즉시 실행하면 다운로드도 즉시 시작
- **라우트·기능 단위 분할**: 관리자 화면, 편집기, 차트 등 초기 화면에서 필요하지 않은 큰 기능을 우선 후보로 검토
- **공통 의존성 분리**: 여러 청크에서 사용하는 모듈의 중복 포함을 줄이고 재사용. 모든 라이브러리를 거대한 vendor 파일 하나로 고정하는 방식에는 초기 로딩과 캐시 갱신 비용 검토 필요
- **로딩 UX**: 비동기 로딩 동안 대기 상태를 표시하고 실패·재시도 처리. 빠른 첫 화면과 느린 첫 상호작용 사이의 균형 고려
- **선행 로딩**: 다음 탐색에 필요할 코드의 prefetch, 현재 화면에 필요한 코드의 preload·modulepreload 등을 검토하되 불필요한 선행 요청으로 초기 자원과 경쟁하지 않도록 조정
- **분할 효과 검증**: 같은 모듈을 다른 경로에서 정적으로 import하면 초기 청크에 포함될 수 있음. 동적 import 한 줄이 지연 로딩을 무조건 보장하지는 않음

> 참고: [Webpack - Code Splitting](https://webpack.js.org/guides/code-splitting/), [web.dev - Reduce JavaScript payloads with code splitting](https://web.dev/articles/reduce-javascript-payloads-with-code-splitting)

| 구분 | Webpack | Vite |
| --- | --- | --- |
| **도구의 성격** | 모듈 번들러를 중심으로 개발 서버·변환 도구 조합 | 개발 서버와 프로덕션 빌드를 함께 제공하는 빌드 도구 |

| **선택을 검토할 상황** | 기존 Webpack 설정·플러그인 의존이 크거나 특수한 빌드 제어가 필요한 프로젝트 | 기본 설정으로 빠르게 시작하고 개발 피드백 시간을 줄이려는 프로젝트 |

- **Webpack에 대한 보완**: 기본값으로 설정 파일 없이 시작할 수도 있음. 변경할 때마다 전체 코드를 처음부터 다시 처리하는 방식으로 단정하면 캐시·증분 컴파일·HMR을 놓치게 됨
- **Vite에 대한 보완**: 개발 중에도 의존성 사전 번들링이 있으므로 모든 파일을 전혀 번들링하지 않는다고 설명하면 부정확
- **규모에 대한 보완**: 큰 프로젝트는 반드시 Webpack, 작은 프로젝트는 반드시 Vite라는 구분은 부적절. 프레임워크 호환성, 플러그인, 기존 설정의 이전 비용과 실제 성능으로 판단

### 모의 면접

#### 1. 번들러가 없던 시절에는 네트워크 병목, 의존성 관리, 불필요한 코드 로딩 문제를 각각 어떻게 해결했나요?

네트워크 병목은 스크립트를 수동으로 합치거나 최소화하고, 브라우저 캐시와 CDN을 활용해 완화했습니다. 의존성은 HTML에서 라이브러리와 유틸리티를 먼저, 이를 사용하는 코드를 나중에 배치하는 방식으로 관리했습니다. 네임스페이스나 IIFE를 이용해 전역 이름 충돌도 줄였습니다. 불필요한 코드 로딩은 페이지별로 스크립트를 나누거나 라이브러리의 필요한 기능만 담은 빌드를 사용하고, 필요할 때 스크립트를 삽입하는 방식으로 줄였습니다.

다만 이런 방식은 코드가 추가되거나 의존성이 바뀔 때 개발자가 병합 순서와 파일 목록을 계속 맞춰야 한다는 한계가 있었습니다. 번들러는 모듈에 선언한 의존성을 분석하고 미사용 코드 제거와 코드 분할을 자동화해 관리 부담을 줄입니다. 현대에는 브라우저의 ESM으로 의존성을 처리할 수도 있지만, 배포 전 최적화와 자산 처리에는 빌드 도구가 여전히 도움이 됩니다.

#### 2. 웹팩과 비트의 개발 환경 설정 방식의 차이는 무엇이며 각각 어떤 상황에 더 적합할까요?

Webpack은 entry, output, loader, plugin 등의 설정으로 빌드 과정을 세밀하게 제어하는 방식입니다. Vite는 일반적인 개발 서버와 빌드 설정을 기본 제공하고, 필요한 부분을 설정 파일과 플러그인으로 확장합니다. Vite의 일반적인 개발 환경에서는 네이티브 ESM으로 소스 모듈을 요청 시 변환·제공하기 때문에, 앱 전체의 번들 생성을 기다리는 부담을 줄일 수 있습니다.

기존 Webpack 전용 플러그인이나 복잡한 빌드 설정에 의존한다면 Webpack을 유지하는 편이 유리할 수 있습니다. 기본 설정으로 빠르게 시작하거나 개발 서버 시작과 변경 반영 시간을 줄이는 것이 중요하다면 Vite를 검토할 수 있습니다. 다만 Webpack도 캐시와 HMR을 지원하고 Vite도 큰 프로젝트에 사용되므로, 규모만으로 결정하기보다 프레임워크와 플러그인 호환성, 이전 비용, 실제 성능을 비교하겠습니다.

## Q97. 프런트엔드에서 사용하는 TDD 기법을 설명할 수 있나요?

### 면접 답변

TDD는 구현할 동작을 테스트로 먼저 정의하고, 실패하는 테스트를 통과시키는 최소한의 코드를 작성한 뒤, 테스트 통과 상태를 유지하면서 구조를 개선하는 개발 방식입니다. 이 Red-Green-Refactor 주기를 작게 반복하면서 요구사항과 코드의 인터페이스를 구체화합니다. 테스트를 작성하는 시점뿐 아니라, 테스트가 구현과 설계를 이끌고 리팩터링을 뒷받침한다는 점이 핵심입니다.

프런트엔드에서는 주어진 props에 따른 컴포넌트 렌더링, 클릭·입력·제출에 따른 화면 변화, 상태 관리와 비즈니스 로직을 중심으로 적용합니다. 예를 들어 버튼을 누르면 안내 문구가 나타나야 한다는 테스트를 먼저 작성하고 실패를 확인한 다음, 이벤트 처리와 렌더링 코드를 구현합니다. 이때 내부 상태 변수나 함수 호출 순서보다 사용자가 확인할 수 있는 결과를 검증해야 구현 구조를 바꾸어도 테스트를 유지하기 좋습니다.

도구는 역할에 따라 조합합니다. Jest·Vitest는 테스트 실행과 단언·모킹을, React Testing Library·Vue Test Utils는 컴포넌트 렌더링과 상호작용 검증을, Cypress·Playwright는 실제 브라우저에서의 흐름 검증을 지원합니다. 빠른 단위·통합 테스트로 개발 중 피드백을 받고 핵심 사용자 시나리오는 E2E로 보완하되, 테스트 경계와 외부 의존성 제어를 명확히 해 신뢰할 수 있는 테스트를 만드는 것이 중요합니다.

### 핵심 개념

#### Red-Green-Refactor

| 단계 | 수행할 작업 | 확인할 점 |
| --- | --- | --- |
| **Red** | 다음에 구현할 작은 동작을 테스트로 작성하고 실패 확인 | 기능이 없거나 잘못되어 실패했는지 확인. 환경 설정 오류를 기능 검증 실패와 구분 |
| **Green** | 테스트를 통과시키는 최소한의 동작 구현 | 현재 요구사항에 집중하고 아직 필요하지 않은 기능·추상화는 미루기 |
| **Refactor** | 외부 동작을 유지하며 중복·이름·책임 분리 등 개선 | 관련 테스트를 계속 실행해 기존 동작을 유지하는지 확인. 테스트 코드도 정리 대상 |

```text
요구사항과 테스트 후보 목록 작성
  → 한 가지 동작 선택
  → Red: 실패하는 테스트와 실패 이유 확인
  → Green: 최소 구현으로 통과
  → Refactor: 통과 상태에서 구조 개선
  → 다음 동작 선택 후 반복
```

- **테스트 후보 목록**: 정상 동작뿐 아니라 빈 입력, 경계값, 오류 응답, 중복 제출 등 검증할 사례를 먼저 정리
- **작은 주기**: 화면 전체를 한꺼번에 구현하기보다 입력 검증 하나, 상태 전이 하나처럼 빠르게 확인할 수 있는 단위로 진행
- **Red를 확인하는 이유**: 처음부터 통과한 테스트만으로는 새 기능이 빠졌을 때 실패하는지 알기 어려움. 기대한 단언이 실제로 동작하는지 점검
- **Refactor의 조건**: 기능 추가와 구조 변경을 분리하고 동작이 유지되는지 확인. 개선할 부분이 없다면 억지로 추상화를 추가할 필요는 없음
- **자동화 테스트와 TDD의 차이**: 구현 후 작성한 테스트도 회귀 방지에 유용하지만, 테스트가 구현을 이끄는 개발 주기를 거쳤는지와는 별개의 문제

> 참고: [Kent Beck - Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd), [Martin Fowler - Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html)

#### 프런트엔드에서 검증할 대상

| 대상 | 테스트할 동작 예시 | 피할 결합 |
| --- | --- | --- |
| **컴포넌트 렌더링** | 사용자 이름 props가 화면에 표시되고, 권한에 따라 버튼 노출 여부 변경 | 컴포넌트 내부 변수명이나 불필요하게 상세한 DOM 구조에 의존 |
| **사용자 이벤트** | 입력 후 제출하면 결과 표시, 잘못된 값이면 오류 안내, 로딩 중 중복 제출 방지 | 이벤트 핸들러를 직접 호출하고 실제 UI 연결 검증 생략 |
| **상태 관리 로직** | 장바구니 수량과 합계 계산, reducer의 상태 전이와 경계값 처리 | 상태 라이브러리 내부 구현이나 모든 action 호출 순서 고정 |
| **비동기 흐름** | 요청 중 로딩 표시, 성공 시 데이터 표시, 실패 시 재시도 제공 | 성공 응답만 검증하거나 임의의 시간만 기다린 뒤 단언 |

- **순수 로직**: 복잡한 계산·검증 규칙은 입력과 출력 중심의 단위 테스트로 다양한 사례 검증
- **연결된 UI**: 컴포넌트·스토어·사용자 이벤트가 함께 동작해야 하는 요구사항은 통합 테스트로 검증
- **상태 저장소 격리**: 테스트마다 새로운 스토어 생성. 앞선 테스트의 상태가 다음 테스트에 영향을 주지 않도록 초기화
- **검증 범위 선택**: 모든 구현 조각을 각각 테스트하기보다, 오류가 발생할 위험과 실패했을 때의 영향을 기준으로 경계 결정

> 참고: [Redux - Writing Tests](https://redux.js.org/usage/writing-tests), [Testing Library - Guiding Principles](https://testing-library.com/docs/guiding-principles/)

#### 구현 세부사항보다 관찰 가능한 행위

| 요구사항 | 권장 검증 | 변경에 취약한 검증 |
| --- | --- | --- |
| **클릭하면 안내 문구 표시** | 이름으로 버튼을 찾고 클릭한 뒤 문구 확인 | `setState` 호출 여부나 내부 상태 값 직접 확인 |
| **유효하지 않은 입력 제출** | 입력·제출 후 오류 메시지와 제출 차단 확인 | 특정 이름의 검증 함수가 호출됐는지만 확인 |
| **데이터 로딩 성공** | 응답 이후 사용자에게 표시되는 목록 확인 | 내부 훅과 데이터 가공 함수의 호출 순서 고정 |

- **사용자 관점의 요소 탐색**: 버튼의 role과 접근 가능한 이름, 입력의 label 등을 우선 사용. CSS 클래스나 `nth-child`는 구조 변경에 쉽게 영향받는 선택자
- **테스트 ID의 위치**: 적절한 role·label·텍스트로 요소를 찾기 어려울 때 명시적인 테스트 계약으로 활용 가능. 모든 요소에 먼저 적용할 필요는 없음
- **공개 인터페이스 검증**: 재사용 컴포넌트의 `onSubmit` 같은 공개 콜백은 전달된 값 검증이 적절할 수 있음. 외부에 약속한 동작과 비공개 구현을 구분
- **접근성 검증의 한계**: role·label 기반 탐색은 접근성을 의식한 마크업에 도움이 되지만, 키보드 사용성·색 대비·스크린리더 경험 전체를 보장하지는 않음

> 참고: [Testing Library - About Queries](https://testing-library.com/docs/queries/about/), [Testing Library - Guiding Principles](https://testing-library.com/docs/guiding-principles/)

#### 컴포넌트 TDD 예시

요구사항은 ‘인사하기 버튼을 누르기 전에는 환영 문구가 없고, 누르면 환영 문구가 나타난다’입니다. 아래 코드는 React·Vitest·React Testing Library를 사용하는 학습 예시이며, React의 JSX 변환 설정과 `jsdom`, `@testing-library/user-event`, `@testing-library/jest-dom` 등의 의존성이 갖춰진 환경을 전제로 합니다.

**1. Red: 사용자 행동과 결과를 테스트로 먼저 작성**

```jsx
// WelcomePanel.test.jsx
// @vitest-environment jsdom
import { afterEach, expect, test } from 'vitest';
import { cleanup, render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import '@testing-library/jest-dom/vitest';
import { WelcomePanel } from './WelcomePanel';

afterEach(cleanup);

test('인사하기 버튼을 누르면 환영 문구가 나타난다', async () => {
  const user = userEvent.setup();
  render(<WelcomePanel />);

  expect(screen.queryByText('환영합니다')).not.toBeInTheDocument();

  await user.click(screen.getByRole('button', { name: '인사하기' }));

  expect(screen.getByRole('status')).toHaveTextContent('환영합니다');
});
```

- **예상한 Red**: 버튼만 렌더링하는 컴포넌트에서는 클릭 후 `status` 요소가 없어 실패하는지 확인
- **환경 오류와 구분**: 모듈·패키지를 찾지 못하거나 DOM 환경이 없어서 실패했다면, 이를 해결한 뒤 요구한 동작 때문에 실패하는지 다시 확인
- **Arrange-Act-Assert**: 렌더링과 준비 → 사용자 행동 → 결과 단언 순서. 이는 테스트 코드의 구성 방식이고, Red-Green-Refactor는 개발 과정의 반복 주기
- **비동기 이벤트 처리**: `userEvent` 동작을 `await`해 이벤트와 관련된 갱신을 기다리고 결과 확인

**2. Green: 요구한 동작을 만족하는 코드 구현**

```jsx
// WelcomePanel.jsx
import { useState } from 'react';

export function WelcomePanel() {
  const [hasGreeted, setHasGreeted] = useState(false);

  return (
    <section>
      <button type="button" onClick={() => setHasGreeted(true)}>
        인사하기
      </button>
      {hasGreeted && <p role="status">환영합니다</p>}
    </section>
  );
}
```

**3. Refactor와 다음 주기**

- 테스트 통과 후 중복이나 책임 혼합이 있는지 검토하고, 필요하면 내부 코드를 개선한 뒤 재실행
- 상태 변수나 이벤트 처리 방식을 바꾸어도 같은 버튼과 결과가 유지되면 테스트도 유지 가능
- 다음 요구사항이 추가되면 새로운 테스트부터 작성. 서버 요청이 추가된다면 로딩·성공·실패를 나누어 검증
- 이 예시는 DOM 환경에서 상호작용을 검증하며, 실제 브라우저의 레이아웃이나 서버 연동까지 검증한 것은 아님

> 참고: [Vitest - Test Environment](https://vitest.dev/guide/environment.html), [React Testing Library - API](https://testing-library.com/docs/react-testing-library/api/), [Testing Library - user-event](https://testing-library.com/docs/user-event/intro/), [jest-dom - Vitest integration](https://github.com/testing-library/jest-dom#with-vitest)

#### 단위·통합·E2E의 경계

| 구분 | 검증 범위 | 대표 사례 | 주요 한계 |
| --- | --- | --- | --- |
| **단위(Unit)** | 작은 로직이나 컴포넌트의 독립적인 동작 | 가격 계산, 입력 검증 함수, reducer의 상태 전이 | 실제 모듈 연결이나 브라우저 환경의 문제를 놓칠 수 있음 |
| **통합(Integration)** | 여러 구성 요소가 연결된 동작 | 폼·검증·스토어·API 응답 처리가 함께 동작하는지 확인 | 외부 경계를 대체했다면 그 경계의 실제 연동은 보장하지 못함 |
| **E2E** | 정의한 시스템 경계를 통과하는 사용자 시나리오 | 브라우저에서 로그인 후 상품을 담고 주문 결과 확인 | 실행 비용과 데이터·네트워크 관리 부담, 실패 원인 추적의 어려움 |

- **범위와 실행 환경의 구분**: 브라우저에서 실행해도 컴포넌트 하나만 검증하면 컴포넌트 테스트. Testing Library로 페이지와 스토어를 함께 검증하면 통합 테스트가 될 수 있음
- **E2E 경계 명시**: 브라우저·프런트엔드·백엔드·데이터베이스 중 어디까지 실제로 연결했는지 기록. API를 전부 mock한 브라우저 테스트가 실제 서버 연동을 증명하지는 않음
- **DOM 에뮬레이션의 한계**: jsdom은 실제 브라우저의 렌더링 엔진이 아니므로 레이아웃·일부 브라우저 API 검증에 한계. 필요한 동작은 실제 브라우저 테스트로 보완
- **TDD와 테스트 수준**: TDD를 단위 테스트에만 한정할 필요는 없지만, 개발 중 반복 주기에는 실행이 빠르고 실패 원인이 명확한 테스트가 유리

> 참고: [Vue.js - Testing](https://vuejs.org/guide/scaling-up/testing.html), [Cypress - Testing Types](https://docs.cypress.io/app/core-concepts/testing-types), [Vitest - Test Environment](https://vitest.dev/guide/environment.html)

#### 테스트 피라미드와 테스트 트로피

| 관점 | 강조하는 구성 | 프런트엔드에 적용할 때의 의미 |
| --- | --- | --- |
| **테스트 피라미드** | 빠르고 범위가 좁은 테스트를 충분히 두고, 통합·E2E는 비용에 맞게 구성 | 복잡한 비즈니스 규칙은 단위 테스트로 넓게 검증하고 전체 사용자 흐름은 선별 |
| **테스트 트로피** | 정적 검사·단위·통합·E2E를 함께 두되 통합 테스트의 투자 대비 신뢰도 강조 | UI·상태·이벤트가 함께 동작하는지 검증해 각 부분을 따로 테스트할 때 놓치는 연결 오류 탐지 |

- **정적 검사의 역할**: 타입 검사와 린트는 실행 전에 잡을 수 있는 오류를 저렴하게 탐지. 실제 사용자 행동과 런타임 결과 검증은 별도로 필요
- **비율보다 위험과 비용**: 단위 70%, 통합 20%, E2E 10% 같은 수치를 모든 앱에 고정할 근거는 없음. 기능 특성·실행 시간·유지 비용에 따라 구성
- **영역별 조합**: 계산 규칙이 많은 영역은 단위 테스트 비중을 높이고, 여러 UI와 상태가 얽힌 흐름은 통합 테스트에 집중
- **핵심 흐름의 보완**: 로그인·결제처럼 실패 영향이 큰 시나리오는 실제 연결을 포함한 E2E로 확인할 가치가 큼

> 참고: [Martin Fowler - Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html), [Kent C. Dodds - The Testing Trophy and Testing Classifications](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)

#### 테스트 도구의 역할

| 도구 | 주된 역할 | 함께 이해할 점 |
| --- | --- | --- |
| **Jest** | 테스트 탐색·실행, 단언, mock·spy, 커버리지 등 제공 | React 렌더링과 사용자 중심 요소 탐색에는 별도 유틸리티 조합 |
| **Vitest** | Vite와 연계한 테스트 실행·변환, 단언·모킹·커버리지 등 제공 | Jest와 유사한 API를 제공하지만 설정과 모킹 동작이 완전히 같지는 않음 |
| **React Testing Library** | React 컴포넌트를 렌더링하고 DOM을 사용자 관점에서 탐색·검증 | 테스트 러너와 함께 사용. `user-event`로 클릭·입력 등의 상호작용 지원 |

| **Cypress** | 실제 브라우저에서 사용자 흐름과 컴포넌트 동작 등 검증 | E2E뿐 아니라 컴포넌트 테스트도 지원하므로 테스트 범위에 맞게 선택 |
| **Playwright** | Chromium·Firefox·WebKit 등에서 브라우저 자동화와 테스트 실행 | 자동 대기, 재시도 가능한 단언, 격리된 브라우저 컨텍스트와 추적 도구 활용 |

- **도구와 방법론의 구분**: Jest를 사용하거나 테스트 파일이 있다고 자동으로 TDD가 되는 것은 아님. 같은 도구로 구현 후 테스트를 작성할 수도 있음
- **일반적인 조합**: Vitest 또는 Jest + 컴포넌트 테스트 유틸리티로 빠른 피드백, Cypress 또는 Playwright로 브라우저에서 핵심 흐름 확인

#### mock의 경계와 남용의 위험

- **mock·stub·spy**: 외부 응답을 대신 제공하거나, 의존 동작을 대체하거나, 함수 호출을 관찰하는 테스트 대역. 용어와 API의 범위는 도구마다 차이 존재
- **통제할 의존성**: 네트워크 응답, 현재 시간, 랜덤 값, 외부 서비스처럼 느리거나 비결정적인 경계를 필요에 따라 제어
- **네트워크 수준의 대체**: 통합 테스트에서는 내부 데이터 훅을 모두 mock하기보다 MSW 등으로 HTTP 응답을 제어하면 실제 요청·상태·UI 연결을 더 많이 검증 가능
- **과도한 내부 모킹의 위험**: 컴포넌트·훅·스토어를 모두 가짜로 바꾸면 각 부분을 연결했을 때 생기는 오류를 놓치고, 테스트가 mock의 동작만 확인하는 상태가 될 수 있음
- **계약 차이의 위험**: 가짜 응답의 필드나 상태 코드가 실제 API와 다르면 테스트가 통과해도 서비스는 실패 가능. 서버 계약 검증과 실제 연동 테스트로 보완
- **정리와 격리**: 테스트별 mock 호출 기록·구현, 서버 핸들러, 전역 상태와 타이머를 적절히 초기화·복원. 호출 기록 초기화와 원래 구현 복원은 다른 작업

> 참고: [Vitest - Mocking](https://vitest.dev/guide/mocking.html), [Vitest - Mocking Requests](https://vitest.dev/guide/mocking/requests.html), [Redux - Writing Tests](https://redux.js.org/usage/writing-tests)

#### 비동기 테스트와 flaky test

같은 코드와 조건에서 실행해도 통과와 실패가 간헐적으로 바뀌는 테스트를 flaky test라고 합니다. 제품의 실제 경쟁 상태나 테스트의 잘못된 대기가 원인일 수 있으므로 실패 근거를 확인해야 합니다.

| 원인 | 개선 방향 |
| --- | --- |
| **고정된 시간 대기** | `sleep(1000)` 대신 문구·요소·응답 등 의미 있는 완료 조건을 기다리기 |
| **Promise·사용자 이벤트 대기 누락** | 비동기 함수와 사용자 동작을 `await`하고, 비동기 단언도 완료까지 기다리기 |
| **시간·랜덤 값 의존** | 테스트 시계·고정 데이터·제어 가능한 랜덤 입력 사용, 종료 후 복원 |
| **공유 상태와 실행 순서 의존** | DOM·스토어·스토리지·쿠키·서버 데이터를 테스트마다 독립적으로 준비 |
| **실제 외부 서비스 변동** | 제어 가능한 테스트 서버·응답으로 격리하고 실제 연결 검증은 목적에 맞게 별도 구성 |
| **취약한 선택자** | 사용자에게 보이는 role·label 등 안정적인 계약으로 요소 탐색 |

- **Testing Library의 쿼리 구분**: `getBy*`는 즉시 존재하는 요소, `queryBy*`는 부재 확인, `findBy*`는 나중에 나타나는 요소를 기다릴 때 활용
- **`waitFor`**: 단언이 성공할 때까지 콜백을 재실행할 수 있으므로, 클릭·제출 같은 부수 효과는 콜백 밖에서 수행. 재시도할 검증만 넣는 편이 안전
- **Playwright의 자동 대기**: 클릭 가능한 상태 확인과 `await expect(locator).toBeVisible()` 같은 재시도 가능한 단언을 활용. 임의의 고정 대기를 줄일 수 있음
- **가짜 타이머 주의**: 디바운스·타임아웃 테스트에 유용하지만 이벤트 유틸리티와 타이머 진행 방식도 맞춰야 함. 무조건 타이머를 가짜로 바꾸면 오히려 테스트가 멈출 수 있음
- **재시도의 위치**: 실패 후 재실행으로 통과한 테스트도 안정성 문제를 조사할 대상. trace·로그·네트워크 기록을 보고 원인을 고쳐야 하며 재시도 횟수 증가만으로 해결하지 않기

> 참고: [Testing Library - About Queries](https://testing-library.com/docs/queries/about/), [Testing Library - Async Methods](https://testing-library.com/docs/dom-testing-library/api-async/), [Playwright - Assertions](https://playwright.dev/docs/test-assertions), [Playwright - Retries](https://playwright.dev/docs/test-retries), [Vitest - Timers](https://vitest.dev/guide/mocking/timers.html)

#### 적용할 때의 실무 판단

- **적합한 대상**: 입력 검증, 계산 규칙, 상태 전이, 알려진 버그 재현처럼 기대 결과를 명확히 정할 수 있는 동작
- **기존 코드에 적용**: 버그를 재현하는 실패 테스트를 먼저 추가한 뒤 수정. 테스트가 전혀 없다면 관련 동작을 보호할 테스트 경계부터 확보
- **탐색 단계의 한계**: 요구사항·인터랙션·기술 선택을 찾는 프로토타입 단계에서는 구체적인 기대 동작을 먼저 고정하기 어려움. 짧은 실험으로 방향을 확인한 뒤 안정된 요구사항에 TDD 적용
- **테스트와 UX 판단의 경계**: 테스트 통과는 작성한 기대를 충족했다는 뜻. 사용하기 편한지, 시각적으로 적절한지, 빠진 요구사항은 없는지는 별도 검토 필요
- **커버리지의 한계**: 실행된 줄과 분기 비율이 높아도 잘못된 결과를 제대로 단언하지 않으면 결함을 놓칠 수 있음. 수치와 테스트 품질을 구분
- **스냅샷의 한계**: 큰 DOM 스냅샷만으로 동작을 보장하기 어려움. 변경을 무심코 승인하지 말고 핵심 동작은 명시적인 단언으로 검증
- **빠른 피드백 유지**: 개발 중에는 관련 테스트를 짧게 반복하고, 변경 마무리와 CI에서는 관련 통합·브라우저 검사까지 실행해 누락된 연결 문제 확인

> 참고: [Vitest - Coverage](https://vitest.dev/guide/coverage.html), [Jest - Snapshot Testing](https://jestjs.io/docs/snapshot-testing)

### 모의 면접

#### 1. TDD의 핵심 주기인 Red-Green-Refactor는 각각 어떤 의미를 가지며 왜 이 순서로 진행할까요?

Red는 다음에 구현할 동작을 테스트로 먼저 표현하고, 해당 기능이 없어 테스트가 실패하는지 확인하는 단계입니다. Green은 그 테스트를 통과시키는 최소한의 기능을 구현하는 단계이고, Refactor는 테스트 통과 상태를 유지하면서 중복과 구조를 개선하는 단계입니다.

이 순서는 구현 전에 기대 동작과 인터페이스를 명확히 하고, 테스트가 그 동작의 누락을 감지하는지 확인하기 위해 필요합니다. 그다음 동작을 먼저 완성하고 구조 개선을 분리하면 기능 구현과 리팩터링의 문제를 구분하기 쉽습니다. 작은 주기를 반복하면 피드백이 빨라지고, 쌓인 테스트를 통해 변경 시 기존 동작이 깨지는 것을 발견할 수 있습니다.

#### 2. 프런트엔드에서 TDD를 적용할 때 자주 활용되는 테스트 도구(제스트, 테스팅 라이브러리, 사이프레스 등)의 역할 차이는 무엇인가요?

Jest와 Vitest는 테스트를 찾아 실행하고 결과를 보고하며, 단언과 모킹 등의 기반 기능을 제공합니다. React Testing Library는 컴포넌트를 렌더링하고 사용자가 인식하는 DOM과 상호작용을 검증하는 유틸리티이므로 Jest나 Vitest와 함께 사용합니다. Vue Test Utils는 Vue 컴포넌트의 마운트와 이벤트·렌더링 검증을 지원합니다.

Cypress와 Playwright는 실제 브라우저에서 클릭·입력·탐색 등을 자동화해 사용자 흐름을 검증할 수 있습니다. Cypress는 컴포넌트 테스트도 지원하므로 도구 이름만으로 단위·통합·E2E를 고정해서 분류하지는 않겠습니다. 개발 중에는 빠른 로직·컴포넌트·통합 테스트로 TDD 주기를 돌리고, 실제 브라우저와 시스템 연결이 중요한 핵심 흐름은 E2E로 보완하겠습니다.
