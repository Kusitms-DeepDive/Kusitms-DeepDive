# 6장. 프런트엔드 개발자가 알아야 할 인프라·보안·네트워크

## Q83. 웹 앱의 세션 관리와 쿠키 기반의 보안 이슈에 대해 설명할 수 있나요?

### 면접 답변

HTTP는 상태를 유지하지 않는 프로토콜이므로 서버는 각각의 요청만으로 동일한 사용자의 요청인지 알 수 없습니다. 이를 보완하기 위해 로그인에 성공하면 서버가 사용자 정보를 세션 저장소에 보관하고, 해당 세션을 식별할 수 있는 추측하기 어려운 세션 ID를 쿠키로 전달합니다. 이후 브라우저가 요청에 쿠키를 자동으로 포함하면 서버는 세션 ID로 사용자 상태를 조회합니다.

이때 쿠키가 요청에 자동으로 포함된다는 특성은 CSRF 공격에 악용될 수 있습니다. 사용자가 로그인한 상태에서 공격자가 만든 페이지에 접속하면, 공격자가 대상 서비스로 요청을 보내도록 유도하고 브라우저는 해당 서비스의 세션 쿠키를 함께 전송할 수 있습니다. 서버가 요청의 출처와 의도를 검증하지 않으면 이를 사용자의 정상 요청으로 오인할 수 있습니다.

따라서 세션 쿠키에는 `Secure`, `HttpOnly`, `SameSite`를 설정하고 범위와 만료 시간을 최소화해야 합니다. `SameSite`는 가능한 경우 `Strict`, 일반적인 서비스에서는 탐색 경험을 고려해 `Lax`를 사용하며, 크로스 사이트 전송이 꼭 필요한 `None`은 반드시 `Secure`와 함께 사용합니다. 다만 `SameSite`만으로 모든 CSRF를 막을 수는 없으므로 상태를 변경하는 요청에는 CSRF 토큰과 `Origin` 검증을 함께 적용해야 합니다. 로그인 직후에는 세션 ID를 재발급하고, 로그아웃·만료 시 서버에서도 세션을 폐기해야 합니다.

### 핵심 개념

#### HTTP의 무상태성과 세션

- **HTTP의 무상태성**: 서버가 이전 요청의 사용자 상태를 다음 요청에 자동으로 연결하지 않는 특성
- **쿠키**: 브라우저가 저장하고 적용 범위에 맞는 HTTP 요청에 포함하는 이름과 값의 데이터
- **세션**: 로그인 상태, 권한, 장바구니처럼 여러 요청에 걸쳐 유지할 사용자 상태
- **세션 저장소**: 세션 데이터를 보관하는 서버 메모리, 데이터베이스, Redis 등의 저장 공간
- **세션 ID**: 브라우저의 쿠키와 서버의 세션 데이터를 연결하는 무작위 식별자
- **핵심 원칙**: 개인정보와 권한 정보를 쿠키에 직접 담기보다 의미 없는 세션 ID만 저장하고 실제 상태는 서버에서 관리

> 브라우저의 `sessionStorage`와 서버의 로그인 세션은 서로 다른 개념. `sessionStorage`는 탭 단위의 클라이언트 저장소이고, 서버 세션은 여러 HTTP 요청에 걸쳐 사용자 상태를 식별하는 방식

#### 쿠키 기반 세션의 흐름

```text
1. 사용자가 아이디와 비밀번호로 로그인 요청
2. 서버가 인증에 성공하면 새로운 세션과 예측하기 어려운 세션 ID 생성
3. 서버가 세션 저장소에 사용자 정보와 세션 상태 저장
4. 응답의 Set-Cookie 헤더로 세션 ID 전달
5. 브라우저가 쿠키를 저장하고 이후 적용 대상 요청에 자동 포함
6. 서버가 세션 ID로 세션을 조회하여 사용자와 권한 확인
7. 로그아웃·만료·위험 감지 시 서버 세션 폐기와 쿠키 만료 처리
```

```http
Set-Cookie: __Host-session=<random-id>; Path=/; Secure; HttpOnly; SameSite=Lax
```

- **`__Host-` 접두사**: `Secure`, `Path=/`, `Domain` 미지정을 브라우저가 강제하는 쿠키 이름 규칙
- **불투명한 세션 ID**: 값만 보고 사용자 정보나 권한을 알 수 없고 충분한 엔트로피를 가진 식별자
- **서버 검증**: 쿠키를 받았다는 사실만 신뢰하지 않고 세션의 유효 기간, 사용자 상태, 권한을 매 요청마다 확인

#### 안전한 세션 수명 주기

- **로그인 전후 세션 ID 교체**: 공격자가 미리 정한 세션 ID를 로그인 후에도 사용하게 만드는 세션 고정 공격 방지
- **권한 변경 시 세션 갱신**: 로그인, 관리자 권한 획득, 비밀번호 변경처럼 권한 수준이 바뀌는 시점에 새 ID 발급
- **유휴 만료**: 일정 시간 동안 요청이 없으면 세션 폐기
- **절대 만료**: 사용 중이더라도 최대 수명이 지나면 재인증 요구
- **로그아웃 처리**: 브라우저 쿠키 삭제뿐 아니라 서버 저장소의 세션도 즉시 무효화
- **전체 로그아웃**: 비밀번호 유출이나 계정 탈취가 의심될 때 사용자의 기존 세션을 모두 폐기할 수 있는 기능
- **민감 작업 재인증**: 결제, 비밀번호 변경, 계정 삭제 전에 비밀번호나 추가 인증 다시 요구

#### 세션 쿠키의 주요 보안 속성

| 속성 | 역할 | 주의점 |
| --- | --- | --- |
| `Secure` | HTTPS 요청에서만 쿠키 전송 | 전송 구간을 보호하지만 XSS나 CSRF 자체를 해결하지는 못함 |
| `HttpOnly` | `document.cookie`를 통한 자바스크립트 접근 차단 | XSS의 세션 ID 탈취 위험을 낮추지만 요청에는 쿠키가 포함되므로 CSRF 방어 수단은 아님 |
| `SameSite` | 크로스 사이트 요청에서 쿠키를 전송할 조건 제한 | 단독 방어가 아닌 심층 방어 수단으로 사용 |
| `Domain` | 쿠키를 전송할 호스트와 하위 도메인 범위 지정 | 생략한 host-only 쿠키가 더 제한적인 범위 |
| `Path` | 쿠키를 전송할 URL 경로 범위 지정 | 접근 권한을 보장하는 보안 경계로 사용 불가 |
| `Max-Age`·`Expires` | 쿠키의 지속 시간 지정 | 세션 ID는 필요한 최소 기간만 유지 |

#### CSRF 공격이 성립하는 과정

**CSRF(Cross-Site Request Forgery)**는 인증된 사용자의 브라우저가 사용자의 의도와 다른 요청을 보내도록 위조하는 공격입니다.

```text
1. 사용자가 bank.example에 로그인하여 유효한 세션 쿠키 보유
2. 로그아웃하지 않은 상태로 attacker.example 방문
3. 공격자 페이지가 bank.example의 상태 변경 URL로 요청 유도
4. 브라우저가 대상 도메인의 세션 쿠키를 자동으로 첨부
5. 서버가 요청의 출처와 위조 여부를 검증하지 않으면 정상 요청으로 처리
```

- **악용되는 특성**: 대상 사이트의 쿠키를 브라우저가 해당 사이트 요청에 자동 첨부
- **공격자가 알아야 하는 것**: 상태 변경 엔드포인트, HTTP 메서드와 매개변수 구조
- **공격자가 몰라도 되는 것**: 피해자의 비밀번호나 세션 ID 값
- **주요 피해**: 이메일 변경, 송금, 게시물 삭제, 비밀번호 변경 등 사용자의 권한으로 실행되는 상태 변경
- **전제 조건**: 쿠키처럼 브라우저가 자동으로 전송하는 인증 정보와 서버의 불충분한 위조 요청 검증

```html
<!-- 상태를 변경하는 GET 요청을 허용한 취약한 서버의 예 -->
<img src="https://bank.example/transfer?to=attacker&amount=1000000" alt="" />
```

> 조회 목적의 `GET` 요청이 서버 상태를 변경하지 않도록 설계하는 것도 기본적인 방어 원칙

#### `SameSite` 속성

`SameSite`는 요청이 시작된 **사이트**와 쿠키가 속한 사이트의 관계를 기준으로 쿠키 전송 여부를 제한합니다. 여기서 사이트는 출처(origin)와 완전히 같은 개념이 아니며, 스킴과 등록 가능한 도메인을 중심으로 판단합니다.

| 값 | 크로스 사이트 요청에서의 동작 | 장점 | 단점과 적합한 경우 |
| --- | --- | --- | --- |
| `Strict` | 크로스 사이트에서 시작된 요청에는 쿠키를 보내지 않음 | 가장 강한 CSRF 완화 | 외부 링크로 들어올 때 로그인 상태가 바로 반영되지 않는 등 UX 저하 가능 |
| `Lax` | 대부분 차단하지만 안전한 메서드를 사용하는 최상위 탐색에는 전송 | 보안과 일반적인 링크 탐색 경험의 균형 | 일부 크로스 사이트 탐색에는 쿠키가 포함되므로 상태 변경을 `GET`으로 구현하면 위험 |
| `None` | same-site와 cross-site 요청 모두에 전송 | 임베드, 도메인 간 인증 등 크로스 사이트 쿠키가 필요한 경우 | 반드시 `Secure`와 함께 사용하며 CSRF 방어를 별도로 구성 |

- **안전한 메서드**: 조회 의미를 가진 `GET`, `HEAD`, `OPTIONS` 등
- **안전하지 않은 메서드**: 서버 상태를 변경하는 `POST`, `PUT`, `PATCH`, `DELETE` 등
- **명시적 설정**: 브라우저 기본값에 의존하지 않고 서비스 요구 사항에 맞는 값을 쿠키에 직접 지정
- **방어의 한계**: 같은 사이트의 취약한 하위 도메인, 잘못 설계한 `GET` 상태 변경, 브라우저별 동작 차이까지 모두 해결하지 못함

#### CSRF 방어 조합

- **CSRF 토큰**: 공격자가 알 수 없는 값을 폼이나 요청 헤더에 포함하고 서버에서 세션과 함께 검증
- **Synchronizer Token Pattern**: 서버 세션에 토큰을 저장하고 요청의 토큰과 일치하는지 확인
- **Signed Double Submit Cookie**: 세션과 연결해 서명한 값을 쿠키와 요청 매개변수 양쪽에서 받아 비교
- **`Origin` 검증**: 상태 변경 요청이 허용한 출처에서 시작되었는지 서버에서 확인
- **`Referer` 검증**: `Origin`을 사용할 수 없을 때 보조적으로 요청 출처 확인
- **Fetch Metadata**: `Sec-Fetch-Site` 같은 헤더로 cross-site 요청을 식별하여 서버에서 차단
- **사용자 상호작용 확인**: 고위험 작업에 재인증, OTP, 확인 단계 적용
- **단순 요청 방지**: JSON API에서 사용자 정의 헤더와 엄격한 `Content-Type` 검증을 사용하고 CORS 허용 범위를 최소화

> `SameSite`는 유용한 방어선이지만 CSRF 토큰을 대체하는 만능 수단이 아님. 특히 중요한 상태 변경 요청은 여러 방어 수단을 함께 적용

#### CSRF와 XSS의 차이

| 구분 | CSRF | XSS |
| --- | --- | --- |
| 공격 목표 | 사용자의 권한으로 원하지 않는 요청 실행 | 신뢰하는 페이지에서 공격자의 스크립트 실행 |
| 세션 ID 탈취 필요 | 필요 없음 | 가능하며 계정 탈취로 이어질 수 있음 |
| 쿠키 자동 전송 악용 | 핵심 조건 | 스크립트 실행 후 다양한 동작 가능 |
| 대표 방어 | CSRF 토큰, `SameSite`, `Origin` 검증 | 출력 인코딩, 안전한 DOM API, CSP, 입력 처리 |
| `HttpOnly` 효과 | 요청에는 쿠키가 실리므로 직접적인 방어가 아님 | 자바스크립트의 세션 쿠키 읽기 차단에 도움 |

> 참고: [MDN - `Set-Cookie` 헤더](https://developer.mozilla.org/ko/docs/Web/HTTP/Reference/Headers/Set-Cookie), [MDN - 안전한 쿠키 설정](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/Cookies), [OWASP - Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP - Cross-Site Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

### 모의 면접

**1. CSRF 공격이 어떻게 발생하며 쿠키의 어떤 특성이 악용되나요?**

CSRF는 사용자가 대상 서비스에 로그인한 상태에서 공격자가 만든 페이지를 방문했을 때, 그 페이지가 사용자의 의도와 다른 상태 변경 요청을 대상 서비스로 보내도록 유도하는 공격입니다. 브라우저는 요청을 만든 페이지가 어디인지와 관계없이 쿠키의 적용 조건을 만족하면 대상 서비스의 쿠키를 자동으로 첨부합니다. 서버가 요청의 출처나 CSRF 토큰을 검증하지 않으면 유효한 세션 쿠키가 포함된 위조 요청을 사용자의 정상 요청으로 오인할 수 있습니다.

이를 막기 위해 상태 변경 요청에는 예측할 수 없는 CSRF 토큰을 검증하고 `Origin`이나 Fetch Metadata 헤더를 확인해야 합니다. 세션 쿠키에는 `SameSite=Lax` 또는 가능한 경우 `Strict`를 명시해 크로스 사이트 전송을 제한해야 합니다. `HttpOnly`는 자바스크립트가 쿠키 값을 읽지 못하게 하지만 요청에는 쿠키가 자동으로 포함되므로 CSRF를 직접 막지는 못합니다.

**2. SameSite 쿠키 속성 Strict, Lax, None의 차이를 비교하고 각각의 장단점을 설명할 수 있나요?**

`Strict`는 크로스 사이트에서 시작된 요청에 쿠키를 보내지 않아 CSRF 방어 효과가 가장 강합니다. 다만 외부 사이트의 링크를 통해 들어올 때 로그인 상태가 즉시 반영되지 않는 등 사용자 경험이 저하될 수 있습니다.

`Lax`는 대부분의 크로스 사이트 요청에서 쿠키를 제한하지만, `GET`처럼 안전한 메서드를 이용한 최상위 탐색에는 쿠키를 허용합니다. 외부 링크로 방문하는 일반적인 흐름을 유지하면서 상태 변경 요청의 상당수를 차단하므로 보안과 편의성의 균형이 좋습니다. 다만 서버가 `GET` 요청으로 상태를 변경하도록 설계되어 있다면 충분한 방어가 되지 않습니다.

`None`은 same-site와 cross-site 요청 모두에 쿠키를 전송하므로 외부 사이트에 삽입되는 콘텐츠나 도메인 간 인증처럼 크로스 사이트 쿠키가 필요한 경우 사용합니다. 반드시 `Secure`를 함께 지정해야 하며, CSRF 토큰과 출처 검증 같은 별도의 방어가 필요합니다.

## Q87. 웹 브라우저가 웹 사이트를 렌더링하는 과정을 네트워크 관점에서 설명할 수 있나요?

### 면접 답변

사용자가 URL을 입력하면 브라우저는 먼저 URL을 해석하고 캐시나 서비스 워커로 응답할 수 있는지 확인합니다. 네트워크 요청이 필요하면 DNS를 통해 도메인을 IP 주소로 변환하고 서버와 연결을 수립합니다. HTTP/1.1과 HTTP/2를 HTTPS로 사용할 때는 일반적으로 TCP 연결과 TLS 핸드셰이크가 필요하고, HTTP/3는 QUIC을 사용해 전송과 보안 연결을 구성합니다. 이미 열어 둔 연결이 있다면 이를 재사용하여 일부 과정을 생략할 수 있습니다.

연결 후 브라우저는 HTTP 요청을 보내고 서버는 상태 코드, 헤더와 HTML을 응답합니다. 첫 바이트가 도착하면 브라우저는 전체 문서의 다운로드가 끝나기를 기다리지 않고 HTML을 점진적으로 파싱하여 DOM을 만들고, 발견한 CSS, 자바스크립트, 이미지, 폰트 등의 하위 리소스를 추가로 요청합니다. CSSOM과 DOM으로 렌더 트리를 구성한 뒤 레이아웃, 페인트, 합성 과정을 거쳐 화면을 표시합니다.

성능 병목은 DNS 조회와 연결의 RTT, 서버 처리 시간과 TTFB, 리소스 전송량, 렌더링 차단 리소스에서 발생합니다. 자주 사용하는 외부 출처에는 `dns-prefetch`나 중요한 경우 `preconnect`를 적용하고, CDN·캐시·압축으로 전송 비용을 줄일 수 있습니다. 렌더링 단계에서는 핵심 CSS를 우선 제공하고 불필요한 CSS와 자바스크립트를 줄이며, 실행 의존성에 맞춰 `defer` 또는 `async`를 사용해야 합니다.

### 핵심 개념

#### 전체 흐름

```text
1. URL 해석과 캐시 확인
2. DNS 조회로 서버 주소 확인
3. 전송 및 보안 연결 수립
4. HTTP 요청과 응답 수신
5. HTML 파싱과 하위 리소스 요청
6. DOM·CSSOM 생성
7. 렌더 트리 → 레이아웃 → 페인트 → 합성
```

- **개념적인 순서**: 실제 브라우저는 캐시, 기존 연결, 병렬 다운로드와 스트리밍을 활용하므로 단계 일부가 생략되거나 겹쳐서 진행
- **동일 출처 재방문**: DNS 캐시와 기존 HTTP 연결 재사용 가능
- **캐시 응답**: 메모리·디스크 캐시 또는 서비스 워커가 응답하면 실제 네트워크 요청 생략 가능
- **리다이렉트**: 응답의 `Location`이 다른 출처라면 새 주소에 대해 DNS 조회와 연결 과정이 다시 필요할 수 있음

#### 1단계: URL 해석과 DNS 조회

브라우저는 URL에서 스킴, 호스트, 포트, 경로 등을 구분합니다. 네트워크 접근이 필요하지만 호스트가 도메인 이름이면 IP 주소를 알아내기 위한 DNS 조회를 수행합니다.

```text
브라우저·운영체제 DNS 캐시 확인
  → 재귀 DNS 리졸버 질의
    → 루트 네임 서버
      → TLD 네임 서버
        → 권한 있는 네임 서버
          → IP 주소 반환
```

- **브라우저와 운영체제 캐시**: 유효한 DNS 결과가 있으면 외부 질의 없이 사용
- **재귀 리졸버**: 통신사나 별도 DNS 제공자가 사용자를 대신해 최종 주소 탐색
- **루트 네임 서버**: `.com`, `.org` 같은 TLD를 담당하는 서버 안내
- **TLD 네임 서버**: 대상 도메인의 권한 있는 네임 서버 안내
- **권한 있는 네임 서버**: 도메인의 실제 DNS 레코드 반환
- **TTL**: DNS 응답을 캐시할 수 있는 시간

##### `dns-prefetch`

나중에 필요할 가능성이 높은 외부 출처의 DNS 조회를 미리 수행하라는 힌트입니다.

```html
<link rel="dns-prefetch" href="https://fonts.googleapis.com" />
```

- DNS 조회만 미리 수행
- 현재 문서에서 사용할 것이 확실한 주요 외부 출처에 선택적으로 적용
- 같은 출처의 DNS는 현재 문서를 요청하면서 이미 해결되므로 주로 교차 출처에 사용
- 브라우저가 자원 상황에 따라 수행 여부를 결정할 수 있는 힌트

#### 2단계: 연결 수립

##### HTTP/1.1·HTTP/2 over HTTPS

```text
DNS 완료
  → TCP 3-way handshake
    → TLS handshake
      → HTTP 요청 전송
```

- **TCP SYN**: 클라이언트의 연결 시작 요청
- **SYN-ACK**: 서버의 요청 수락과 연결 확인
- **ACK**: 클라이언트의 최종 확인으로 TCP 연결 성립
- **TLS 핸드셰이크**: 서버 인증서 검증, 사용할 암호 방식 협상, 세션 키 생성
- **RTT**: 요청이나 핸드셰이크 메시지가 상대에게 갔다가 응답이 돌아오는 데 필요한 왕복 시간
- **HTTP/2 멀티플렉싱**: 하나의 TCP 연결에서 여러 요청과 응답을 스트림 단위로 처리

##### HTTP/3

- **전송 기반**: TCP가 아닌 UDP 위의 QUIC 사용
- **보안 통합**: QUIC 연결 수립 과정에 TLS 1.3 기능 통합
- **스트림 멀티플렉싱**: 하나의 QUIC 연결에서 여러 요청·응답 스트림 처리
- **스트림 독립성**: 한 스트림의 패킷 손실이 다른 독립 스트림의 진행까지 막는 TCP 수준의 HOL 블로킹 완화
- **연결 이동**: 네트워크가 Wi-Fi에서 셀룰러로 바뀌는 상황 등에 대응할 수 있는 연결 식별 방식

> HTTP/3도 HTTP의 메서드, 상태 코드, 헤더 같은 의미는 유지하며 전송 계층을 QUIC으로 변경

##### `preconnect`

브라우저가 특정 외부 출처에 DNS 조회뿐 아니라 전송 연결과 TLS 협상까지 미리 준비할 수 있도록 제공하는 힌트입니다.

```html
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
```

| 구분 | 미리 수행하는 작업 | 적합한 대상 |
| --- | --- | --- |
| `dns-prefetch` | DNS 조회 | 연결할 가능성이 있는 여러 외부 출처 |
| `preconnect` | DNS + 전송 연결 + 필요한 경우 TLS | 곧 사용할 것이 확실한 핵심 외부 출처 |

- **선별 사용**: 너무 많은 출처에 `preconnect`하면 불필요한 소켓과 CPU·메모리 사용 증가
- **`crossorigin`**: 폰트처럼 익명 CORS 방식으로 가져오는 리소스와 실제 연결을 재사용하려면 요청 모드를 맞추기 위해 필요할 수 있는 속성
- **연결 재사용**: 이미 사용 가능한 연결이 있다면 브라우저가 새로운 핸드셰이크 대신 기존 연결 활용

#### 3단계: HTTP 요청과 응답

```http
GET /products HTTP/2
Host: example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=...
```

```http
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: public, max-age=60

<!doctype html>...
```

- **요청 정보**: HTTP 메서드, 경로, 요청 헤더, 필요한 경우 본문
- **응답 정보**: 상태 코드, 응답 헤더, HTML과 같은 표현 데이터
- **콘텐츠 협상**: `Accept`, `Accept-Encoding` 등으로 지원하는 형식과 압축 방식 전달
- **스트리밍 파싱**: HTML 전체 수신 완료 전에도 도착한 바이트부터 파싱 가능
- **하위 리소스 발견**: 파서와 preload scanner가 CSS, 스크립트, 이미지, 폰트 요청 시작

##### TTFB와 다운로드 시간

- **TTFB(Time to First Byte)**: 탐색을 시작한 뒤 응답의 첫 바이트를 받기까지의 시간
- **영향 요소**: 리다이렉트, DNS와 연결, 네트워크 지연, 서버 애플리케이션과 데이터베이스 처리
- **다운로드 시간**: 첫 바이트 이후 응답 본문을 모두 받기까지의 시간
- **영향 요소**: 문서와 리소스 크기, 대역폭, 패킷 손실, 압축 여부

| 병목 | 개선 방법 |
| --- | --- |
| 느린 서버 처리 | 쿼리와 애플리케이션 로직 최적화, 서버 캐시 |
| 먼 물리적 거리 | CDN과 엣지 서버 사용 |
| 큰 전송 크기 | Brotli·gzip 압축, 이미지 최적화, 코드 축소 |
| 반복 전송 | `Cache-Control`, ETag 등 적절한 HTTP 캐시 정책 |
| 과도한 요청 | 번들 분할 전략 점검, 중요한 요청의 우선순위 관리 |

#### 4단계: 파싱과 렌더링

```text
HTML 바이트 → 토큰화·파싱 → DOM
CSS 바이트  → 파싱       → CSSOM
DOM + CSSOM → 렌더 트리 → 레이아웃 → 페인트 → 합성
```

- **DOM**: HTML 문서의 구조와 콘텐츠를 표현하는 노드 트리
- **CSSOM**: 적용 가능한 CSS 규칙을 표현하는 객체 구조
- **렌더 트리**: 화면에 그려질 노드와 계산된 스타일을 결합한 구조
- **레이아웃**: 각 요소의 크기와 위치 계산
- **페인트**: 텍스트, 배경, 테두리, 그림자 등을 그릴 명령 생성
- **합성**: 여러 레이어를 적절한 순서로 조합하여 화면에 표시

#### 렌더링 차단과 파서 차단

| 리소스 | 기본 동작 | 주요 영향 |
| --- | --- | --- |
| 스타일시트 | HTML 파싱과 병렬 다운로드 가능하지만 CSSOM 준비 전 렌더링 차단 | 첫 화면 표시 지연 |
| 일반 외부 스크립트 | HTML 파싱 중단 후 다운로드와 실행 | DOM 생성과 렌더링 지연 |
| `defer` 스크립트 | 파싱과 병렬 다운로드, 파싱 완료 후 문서 순서대로 실행 | DOM 의존 코드에 적합 |
| `async` 스크립트 | 파싱과 병렬 다운로드, 준비되는 즉시 실행 | 실행 중 파싱 중단 가능, 실행 순서 보장 없음 |
| 이미지 | 일반적으로 HTML 파싱을 막지 않고 병렬 다운로드 | 크기 미지정 시 레이아웃 이동 가능 |

> CSS는 일반적으로 HTML 파싱 자체를 중단시키는 리소스가 아니라 화면 렌더링을 차단하는 리소스. 반면 `async`, `defer`, `type="module"`이 없는 일반 스크립트는 HTML 파싱을 중단시킬 수 있음

#### CSS 최적화

- **핵심 CSS 우선 제공**: 첫 화면에 반드시 필요한 최소 스타일을 빠르게 전달하거나 인라인 처리
- **사용하지 않는 CSS 제거**: 현재 페이지에 필요하지 않은 규칙의 다운로드와 파싱 비용 감소
- **코드 분할**: 페이지나 컴포넌트별로 필요한 CSS만 로드
- **압축과 축소**: Brotli·gzip 전송 압축과 minification 적용
- **미디어 조건**: 특정 환경에서만 필요한 스타일시트에 적절한 `media` 조건 지정
- **과도한 인라인 방지**: 핵심 CSS 이외의 대용량 스타일은 캐시 가능한 외부 파일로 제공

#### 자바스크립트 최적화

```html
<!-- DOM과 다른 스크립트에 의존하는 애플리케이션 코드 -->
<script src="app.js" defer></script>

<!-- 다른 코드와 독립적인 분석 스크립트 -->
<script src="analytics.js" async></script>

<!-- 모듈 스크립트는 기본적으로 지연 실행 -->
<script type="module" src="main.js"></script>
```

- **`defer`**: DOM 파싱 후 실행, 문서에 작성된 순서 보장, `DOMContentLoaded` 전에 실행 완료
- **`async`**: 다운로드가 끝나는 즉시 실행, 여러 스크립트 사이 실행 순서 보장 없음
- **`type="module"`**: 기본적으로 지연 실행하며 모듈 의존성 그래프 사용
- **코드 분할**: 초기 화면에 필요하지 않은 기능을 동적 `import()` 등으로 나중에 로드
- **트리 셰이킹과 축소**: 사용하지 않는 코드와 불필요한 문법 제거
- **긴 작업 분할**: 메인 스레드를 오래 점유하는 실행을 나누거나 계산 작업을 Web Worker로 이동

#### 병목을 찾는 기준

- **Network 패널**: DNS, 연결, TTFB, 콘텐츠 다운로드 시간과 요청 폭포 확인
- **Timing 정보**: Queueing, Stalled, DNS, Initial connection, SSL, Waiting, Content Download 구간 확인
- **Performance 패널**: HTML 파싱, 스크립트 실행, 스타일 계산, 레이아웃, 페인트의 메인 스레드 비용 확인
- **Server-Timing**: 서버가 데이터베이스나 애플리케이션 처리 시간을 응답 헤더로 제공하도록 구성
- **측정 우선**: 리소스 힌트나 preload를 무조건 추가하지 않고 실제 병목이 확인된 출처와 리소스에 적용

> 참고: [MDN - `dns-prefetch` 사용하기](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/dns-prefetch), [MDN - `<script>` 요소](https://developer.mozilla.org/ko/docs/Web/HTML/Reference/Elements/script), [MDN - 중요 렌더링 경로](https://developer.mozilla.org/ko/docs/Web/Performance/Guides/Critical_rendering_path), [RFC 9114 - HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)

### 모의 면접

**1. 브라우저가 URL 입력 후 웹 페이지를 화면에 그리기까지 거치는 주요 네트워크 4단계를 순서대로 설명할 수 있나요?**

첫 번째는 DNS 조회 단계입니다. 브라우저와 운영체제의 캐시를 먼저 확인하고, 필요한 경우 DNS 리졸버를 통해 도메인 이름을 서버의 IP 주소로 변환합니다.

두 번째는 연결 수립 단계입니다. HTTP/1.1이나 HTTP/2를 HTTPS로 사용할 때는 일반적으로 TCP 3-way handshake 후 TLS 핸드셰이크를 수행합니다. HTTP/3는 TCP 대신 QUIC을 사용하고 TLS 기능을 연결 과정에 통합합니다. 이미 사용할 수 있는 연결이 있다면 브라우저가 이를 재사용할 수 있습니다.

세 번째는 HTTP 요청과 응답 단계입니다. 브라우저가 서버에 문서를 요청하면 서버는 상태 코드와 헤더, HTML을 응답합니다. 이때 서버 처리 시간과 네트워크 지연은 TTFB에 영향을 주고, 문서의 크기와 네트워크 속도는 다운로드 시간에 영향을 줍니다.

네 번째는 파싱과 렌더링 단계입니다. 브라우저는 HTML을 점진적으로 파싱해 DOM을 만들면서 CSS, 자바스크립트, 이미지 같은 하위 리소스를 요청합니다. DOM과 CSSOM을 기반으로 렌더 트리를 구성하고 레이아웃, 페인트, 합성 과정을 거쳐 화면을 표시합니다.

**2. 렌더링 차단 리소스 문제를 줄이기 위한 CSS와 자바스크립트 최적화 방법에는 어떤 것들이 있나요?**

CSS는 화면을 그리는 데 필요한 CSSOM을 구성하므로 기본적으로 렌더링을 차단합니다. 첫 화면에 필요한 핵심 CSS는 빠르게 제공하고, 나머지는 페이지별로 분할하거나 조건부로 로드해야 합니다. 사용하지 않는 규칙을 제거하고 파일을 축소·압축하는 것도 필요합니다. 핵심 CSS를 인라인할 수 있지만 너무 많은 CSS를 인라인하면 HTML 크기가 커지고 별도 캐시가 어려워지므로 최소한으로 사용해야 합니다.

자바스크립트는 초기 화면에 필요하지 않은 코드를 분할하고 지연 로드해야 합니다. DOM이나 다른 스크립트에 의존하며 실행 순서가 중요하면 `defer`를 사용하고, 분석 코드처럼 독립적이며 순서가 중요하지 않으면 `async`를 사용할 수 있습니다. 번들에서 사용하지 않는 코드를 제거하고 긴 작업을 나누어 메인 스레드 점유 시간도 줄여야 합니다. 최적화 전후에는 Network와 Performance 패널을 사용해 실제 병목이 줄었는지 확인해야 합니다.

## Q88. 웹소켓은 어떤 경우에 사용하며, HTTP 폴링 방식과 비교했을 때의 장단점은 무엇인가요?

### 면접 답변

웹소켓은 채팅, 협업 편집, 온라인 게임처럼 클라이언트와 서버가 낮은 지연으로 데이터를 계속 주고받아야 할 때 사용합니다. 처음에는 HTTP 기반 핸드셰이크로 연결을 시작하고, 연결이 성립한 뒤에는 하나의 지속적인 통신 채널에서 양방향으로 메시지를 교환합니다.

HTTP 폴링은 클라이언트가 일정한 간격으로 서버에 새 데이터가 있는지 반복해서 요청합니다. 구현과 운영이 비교적 단순하지만 새 데이터가 없어도 요청이 발생하고, 갱신 주기에 따라 응답 지연과 요청 오버헤드가 생깁니다. 롱 폴링은 서버가 새 데이터가 생길 때까지 응답을 보류하여 불필요한 응답을 줄이지만, 응답이 끝날 때마다 다시 요청해야 하는 HTTP 요청·응답 구조는 남아 있습니다.

웹소켓은 연결 후 반복되는 HTTP 요청과 헤더를 줄이고 서버도 즉시 데이터를 보낼 수 있어 실시간성과 효율성이 높습니다. 반면 연결 상태, 인증, 재연결, 하트비트, 메시지 유실·중복, 트래픽 급증과 서버 확장까지 직접 고려해야 하므로 구현과 운영이 복잡합니다. 따라서 서버에서 클라이언트로만 갱신하면 되는 알림이나 스트리밍은 SSE를, 변경 빈도가 낮고 약간의 지연을 허용한다면 폴링을 선택할 수 있습니다.

### 핵심 개념

#### HTTP 폴링

```text
클라이언트 ── 요청 ──> 서버
클라이언트 <─ 응답 ─── 서버
              ... 일정 시간 대기 ...
클라이언트 ── 요청 ──> 서버
클라이언트 <─ 응답 ─── 서버
```

- **동작 방식**: 클라이언트가 정해진 주기마다 새 데이터 유무를 요청
- **장점**: 일반 HTTP 인프라와 캐시·인증 방식을 활용하기 쉬움, 구현과 장애 분석이 단순함
- **단점**: 변경이 없어도 요청 발생, 요청 주기가 짧으면 서버·네트워크 부담 증가
- **지연 시간**: 최악의 경우 다음 폴링 주기까지 대기
- **주의점**: HTTP 연결을 재사용할 수 있더라도 요청과 응답, 헤더 처리 비용은 반복됨
- **적합한 사례**: 갱신 빈도가 낮은 작업 상태 확인, 느슨한 알림, 관리 화면의 주기적 동기화

폴링 주기를 짧게 설정하면 지연은 줄지만 요청량이 늘고, 길게 설정하면 요청량은 줄지만 사용자가 최신 데이터를 늦게 보게 됩니다. 실시간성과 비용 사이의 직접적인 절충 관계가 존재합니다.

#### 롱 폴링

```text
클라이언트 ── 요청 ─────────────> 서버
             서버가 새 데이터가 생길 때까지 응답 보류
클라이언트 <────────────── 응답 ── 서버
클라이언트 ── 다음 요청 ────────> 서버
```

- **동작 방식**: 서버가 새 데이터 또는 타임아웃이 발생할 때까지 요청을 열린 상태로 유지
- **장점**: 일반 폴링보다 빈 응답과 불필요한 요청 감소, 서버 데이터가 생긴 직후 전달 가능
- **단점**: 응답이 끝나면 클라이언트가 다시 요청해야 함, 타임아웃·재연결·동시 연결 관리 필요
- **적합한 사례**: 웹소켓 도입이 어렵지만 비교적 빠른 서버 알림이 필요한 환경

#### 웹소켓의 연결과 통신

```text
1. 클라이언트 ── HTTP 핸드셰이크 ──> 서버
2. 클라이언트 <── 연결 수락 ───────── 서버
3. 클라이언트 <====== 지속적인 양방향 메시지 ======> 서버
```

HTTP/1.1 환경에서는 클라이언트가 `Upgrade: websocket` 헤더를 포함한 요청을 보내고 서버가 `101 Switching Protocols`로 수락하면 웹소켓 연결로 전환됩니다. 이후에는 HTTP 요청·응답을 반복하지 않고 텍스트 또는 바이너리 메시지 프레임을 양방향으로 교환합니다.

```js
const socket = new WebSocket("wss://example.com/chat");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "JOIN", roomId: "frontend" }));
});

socket.addEventListener("message", (event) => {
  const message = JSON.parse(event.data);
  console.log(message);
});

socket.addEventListener("close", () => {
  // 네트워크 상태와 재시도 횟수를 고려해 재연결
});

socket.addEventListener("error", (error) => {
  console.error(error);
});
```

- **전이중 통신**: 클라이언트와 서버가 서로의 요청을 기다리지 않고 메시지 전송 가능
- **낮은 반복 비용**: 최초 연결 후 매 메시지마다 HTTP 헤더를 반복해서 보내지 않음
- **텍스트·바이너리 지원**: JSON 메시지뿐 아니라 바이너리 데이터도 전송 가능
- **연결 유지**: 장시간 열린 연결의 생명주기를 클라이언트와 서버가 함께 관리

#### 방식별 비교

| 구분 | 일반 폴링 | 롱 폴링 | SSE | 웹소켓 |
| --- | --- | --- | --- | --- |
| 통신 방향 | 클라이언트 요청 중심 | 클라이언트 요청 후 서버 응답 보류 | 서버 → 클라이언트 | 양방향 |
| 연결 방식 | 주기적으로 HTTP 요청 | 응답까지 HTTP 요청 유지 후 재요청 | HTTP 스트림 유지 | 핸드셰이크 후 웹소켓 연결 유지 |
| 전달 지연 | 폴링 주기에 영향 | 데이터 생성 직후 응답 가능 | 서버 이벤트 즉시 전송 | 양쪽 모두 즉시 전송 가능 |
| 데이터 형식 | HTTP 응답 형식 | HTTP 응답 형식 | UTF-8 텍스트 | 텍스트·바이너리 |
| 재연결 | 직접 구현 | 타임아웃과 재요청 구현 | `EventSource`가 기본 재연결 지원 | 직접 정책 설계 |
| 구현·운영 난도 | 낮음 | 중간 | 낮음~중간 | 높음 |
| 주요 사례 | 저빈도 상태 확인 | 웹소켓 대체 알림 | 뉴스·알림·진행률·LLM 응답 | 채팅·게임·협업·양방향 제어 |

#### 웹소켓이 적합한 경우

- 사용자 입력과 서버 이벤트가 모두 즉시 전달되어야 하는 채팅
- 플레이어 상태와 게임 이벤트를 빠르게 교환하는 온라인 게임
- 여러 사용자의 변경 사항을 동시에 반영하는 협업 편집 도구
- 주문서, 대시보드, 관제 화면처럼 데이터가 빈번하게 갱신되는 서비스
- 단말 위치나 장치 상태를 지속적으로 주고받는 추적·제어 기능

단순히 “데이터가 실시간으로 보인다”는 이유만으로 웹소켓이 필요한 것은 아닙니다. 통신 방향, 메시지 빈도, 허용 지연, 인프라 복잡도를 함께 판단해야 합니다.

#### SSE가 더 적합한 경우

SSE는 서버가 `text/event-stream` 형식으로 이벤트를 계속 보내고 브라우저의 `EventSource`가 이를 수신하는 단방향 스트리밍 방식입니다.

- 서버 알림, 뉴스 피드, 경기 점수, 작업 진행률처럼 서버 → 클라이언트 전송이 중심인 기능
- 클라이언트 입력은 기존 `fetch()` 요청으로 충분한 기능
- 텍스트 데이터만 필요하고 간단한 재연결 동작이 중요한 기능
- 이벤트 ID를 이용해 연결이 끊긴 뒤 이어받기가 필요한 기능

SSE는 연결이 끊기면 기본적으로 재연결하며, 서버가 `id` 필드를 보냈다면 브라우저가 마지막 이벤트 ID를 전달해 이어받기를 구현할 수 있습니다. 서버는 `retry` 필드로 재연결 대기 시간도 제안할 수 있습니다. 반면 클라이언트와 서버가 동일한 채널에서 양방향으로 빈번하게 메시지를 보내야 하거나 바이너리 메시지가 필요하면 웹소켓이 더 적합합니다.

#### 운영 환경에서 확인할 사항

- **보안 연결**: 운영 환경에서는 암호화된 `wss://` 사용
- **출처 검증**: 브라우저가 보내는 `Origin`을 서버에서 허용 목록과 대조하여 교차 사이트 웹소켓 하이재킹 방지
- **인증과 권한**: 연결 성공만으로 신뢰하지 않고 사용자와 채널 권한 검증, 인증 만료 정책 마련
- **재연결 정책**: 지수 백오프와 무작위 지연을 적용하여 장애 복구 시 재연결 폭주 방지
- **하트비트**: Ping/Pong 또는 애플리케이션 수준 신호로 끊어진 연결과 유휴 연결 탐지
- **메시지 복구**: 메시지 ID, 순서 번호, 확인 응답 등을 이용해 유실·중복·순서 문제 처리
- **서버 확장**: 여러 서버가 연결을 나눠 가질 때 세션 라우팅과 Redis Pub/Sub 같은 메시지 브로커 고려
- **백프레셔**: 고전적인 브라우저 `WebSocket` API에는 자동 백프레셔가 없으므로 `bufferedAmount`, 송신 큐 제한, 유입 속도 제한으로 메모리 증가 방지
- **프록시 설정**: 로드 밸런서와 프록시의 웹소켓 업그레이드, 유휴 타임아웃, 최대 연결 수 점검

> 참고: [MDN - WebSocket API](https://developer.mozilla.org/ko/docs/Web/API/WebSockets_API), [MDN - Server-sent events 사용하기](https://developer.mozilla.org/ko/docs/Web/API/Server-sent_events/Using_server-sent_events), [RFC 6455 - The WebSocket Protocol](https://www.rfc-editor.org/rfc/rfc6455.html), [WHATWG HTML - Server-sent events](https://html.spec.whatwg.org/dev/server-sent-events.html)

### 모의 면접

**1. HTTP 폴링, 롱 폴링 방식과 웹소켓의 가장 큰 차이는 무엇인가요?**

가장 큰 차이는 통신을 지속하는 방식과 서버가 데이터를 전달하는 방식입니다. 일반 폴링은 클라이언트가 일정한 주기로 요청해야 서버가 응답하며, 새 데이터가 없어도 요청이 반복됩니다. 롱 폴링은 서버가 새 데이터가 생길 때까지 응답을 보류해 불필요한 응답을 줄이지만, 한 번 응답한 뒤에는 클라이언트가 다시 요청해야 합니다.

웹소켓은 최초 핸드셰이크 후 하나의 연결을 계속 유지하며 클라이언트와 서버가 모두 필요할 때 바로 메시지를 보낼 수 있습니다. 따라서 양방향 실시간성이 필요하고 메시지 빈도가 높을수록 웹소켓의 장점이 커집니다. 다만 지속 연결과 재연결, 인증, 장애 복구, 서버 확장까지 관리해야 하므로 변경 빈도가 낮거나 단방향 알림만 필요하면 폴링이나 SSE가 더 단순하고 적합할 수 있습니다.

**2. 웹소켓 대신 SSE를 사용하는 것이 더 적합한 상황은 언제인가요?**

서버에서 클라이언트로 데이터를 계속 보내는 것이 핵심이고, 클라이언트에서 서버로 보내는 데이터는 일반 HTTP 요청으로 충분할 때 SSE가 더 적합합니다. 뉴스 피드, 알림, 경기 점수, 작업 진행률, LLM의 텍스트 응답 스트리밍이 대표적입니다.

SSE는 일반 HTTP 기반의 UTF-8 텍스트 스트림이라 기존 인프라와 결합하기 쉽고 `EventSource`가 기본 재연결을 지원합니다. 이벤트 ID를 활용하면 연결이 끊긴 뒤 마지막 지점부터 이어받는 흐름도 구현할 수 있습니다. 반면 채팅이나 게임처럼 양쪽이 같은 연결에서 빈번하게 메시지를 보내야 하거나 바이너리 데이터가 필요하다면 웹소켓을 선택하는 것이 적합합니다.
