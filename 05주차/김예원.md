# 5주차 정리

## Q83. 웹 앱의 세션 관리와 쿠키 기반의 보안 이슈에 대해 설명할 수 있나요?

해당 보안 이슈가 언급되는 이유는 **CSRF(Cross-Site Request Forgery)** 때문이다.

### CSRF란?

- 사이트 간 요청 위조
- 사용자가 로그인한 상태를 악용해, 공격자가 사용자의 의도와 상관없이 특정 서버에 요청을 보내도록 만드는 공격

### 공격 시나리오

1. 사용자가 은행 사이트에 로그인 → 서버는 로그인 상태를 유지하기 위해 세션 ID를 발급하고, 이 ID를 쿠키에 저장
2. 이후 사용자가 은행에 요청을 보낼 때 브라우저는 해당 쿠키를 자동으로 첨부
3. 사용자가 로그아웃을 하지 않은 채 다른 악성 사이트에 접속
4. 악성 사이트에서 "1000만 원 특정 계좌로 송금"과 같은 요청을 보내도록 유도
5. 은행 서버가 세션 쿠키만 확인하고 사용자의 정상 요청이라 판단하여 송금이 이루어짐

### 이 공격이 가능한 이유

- 브라우저가 쿠키를 자동으로 전달하기 때문
- 쿠키의 적용 범위(도메인)가 `bank.com`으로 설정되어 있어도, 요청을 **시작하는 페이지**가 `bank.com`일 필요는 없음 → 요청을 **처리하는 페이지**가 `bank.com`이면 쿠키가 첨부되어 CSRF 공격이 가능해짐
- 브라우저는 해당 요청이 사용자의 의도에서 비롯된 것인지까지는 판단할 수 없음

### 공격이 성립하는 조건

- 브라우저가 인증 정보(쿠키)를 자동으로 전송하는 경우
- 세션 쿠키를 이용해 로그인 상태를 관리하는 경우
- 공격자가 사용자를 대신해 요청을 보내는 경우
- 서버가 요청의 정당성(출처 등)을 충분히 검증하지 않는 경우

### 배경 지식: 웹의 근본적 특징

- **HTTP는 무상태(stateless) 프로토콜**: 모든 요청을 이전 요청과 무관한 새로운 요청으로 취급

- **쿠키(Cookie)**
  - 서버가 브라우저에 저장하도록 전달하는 작은 데이터
  - 로그인 성공 시 `200 OK, Set-Cookie: ~` 응답 헤더를 통해 브라우저에 저장 지시
  - 이후 같은 사이트로 요청 시 자동으로 첨부됨
  - 특징: 브라우저에 저장됨 / 요청에 자동 첨부 가능 / 다양한 데이터 저장 가능(단, 비밀번호 같은 민감 정보는 저장 금지) / 다양한 보안 속성 설정 가능
    - `HttpOnly`: JavaScript에서 쿠키를 직접 접근하지 못하도록 제한
    - `Secure`: HTTPS 연결에서만 쿠키 전송
    - `SameSite`: 사이트 간 요청에서 쿠키가 전송되는 조건 제한
    - `Path`: 쿠키를 전송할 URL 경로 제한
    - `Domain`: 쿠키를 사용할 수 있는 도메인 범위 설정

- **세션(Session)**
  - 서버가 사용자별 상태를 유지하기 위해 사용하는 방식
  - 사용자가 로그인하면 서버는 로그인한 사용자 정보를 저장(세션 생성)
  - 세션 ID를 확인해 해당 사용자를 찾아 정보를 제공하는 구조
  - 특징: 서버에서 사용자 상태 관리 / 세션 ID로 사용자 식별 / 세션의 만료·종료 관리 / 세션 데이터를 저장·조회할 공간 필요
  - 쿠키와 세션은 양자택일이 아니라, 일반적인 서버 세션 기반 로그인에서 함께 사용하는 구조

### 방어책: SameSite 속성

쿠키를 전송할 때 요청이 같은 사이트에서 시작되었을 때만 쿠키를 보내도록 제한하는 규칙. 다른 사이트에서 시작한 요청에 쿠키를 보낼지 말지를 결정한다.

| 값 | 설명 |
| --- | --- |
| `Strict` | 가장 엄격한 방식. 동일 사이트에서 시작된 요청에만 쿠키 전송. 외부 링크로 정상 유입된 경우에도 로그인 상태가 유지되지 않는 단점 존재 |
| `Lax` | 대부분 브라우저의 기본값. 사용자의 탐색 의도가 명확한 GET 요청에는 쿠키 허용, POST/PUT 등 데이터 변경 요청에는 전송하지 않음 |
| `None` | 어떤 사이트에서 시작된 요청이든 쿠키를 항상 전송. 반드시 `Secure` 속성과 HTTPS 연결을 함께 사용해야 함 |

### 모의 면접

**Q1. CSRF 공격이 어떻게 발생하며 쿠키의 어떤 특성이 악용되나요?**

CSRF 공격은 브라우저가 요청을 보낼 때 쿠키를 자동으로 포함하는 특성을 악용한 공격이다. 사용자가 A 사이트에 로그인한 상태에서 악성 사이트에 접속했다고 가정하면, 악성 사이트가 A 사이트에 송금 요청을 보내도록 유도할 때 브라우저는 쿠키 전송 조건에 따라 A 사이트의 세션 쿠키를 요청에 포함할 수 있다. 이때 서버가 별도의 검증 없이 쿠키만으로 사용자를 인증하고 요청을 처리하면, 사용자가 의도하지 않은 동작이 실행될 수 있다.

**Q2. SameSite 쿠키 속성 Strict, Lax, None의 차이를 비교하고 각각의 장단점을 설명할 수 있나요?**

SameSite는 다른 사이트에서 시작한 요청에 쿠키를 전송할지 결정하는 속성이다. `Strict`는 가장 엄격한 설정으로 다른 사이트에서 시작한 요청에는 쿠키를 전송하지 않아 보안성이 높지만, 외부 링크를 통해 방문할 때 로그인 상태가 유지되지 않을 수 있다. `Lax`는 일반적으로 기본값으로 사용되며, 다른 사이트에서 시작한 일부 최상위 탐색(GET) 요청에는 쿠키를 전송하지만 사이트 간 POST 요청에는 전송하지 않는다. `None`은 다른 사이트에서 시작한 요청에도 쿠키를 전송하도록 허용하는 설정으로, 사이트 간 쿠키가 필요한 경우 유용하지만 CSRF 공격에 주의해야 하며 `Secure` 속성과 HTTPS 환경이 필수적이다.

## Q87. 웹 브라우저가 웹 사이트를 렌더링하는 과정을 네트워크 관점에서 설명할 수 있나요?

### 웹 사이트 렌더링 과정이란?

- 웹 브라우저가 URL을 입력받은 후, 서버와 통신하여 HTML, CSS, JavaScript 등의 리소스를 가져오고 화면에 표시하는 과정
- DNS 조회, TCP/TLS 연결, HTTP 통신, HTML 파싱 및 렌더링 등 여러 단계가 순서대로 진행됨
- 각 단계에서 발생하는 네트워크 지연과 렌더링 차단 문제를 이해하면 웹 사이트의 성능을 개선할 수 있음

### 1. 도메인 이름을 IP 주소로 변환 (DNS)

**DNS (Domain Name System)**: 사람이 읽기 쉬운 도메인 이름을 컴퓨터가 통신할 때 사용하는 IP 주소로 변환하는 시스템 (예: `example.com` → `1.2.3.4`)

**DNS 조회 과정**

1. 브라우저 캐시 확인: 이전에 조회한 도메인의 IP 주소가 캐시되어 있는지 확인
2. 운영체제 캐시 확인: 운영체제에 해당 도메인의 IP 주소가 저장되어 있는지 확인
3. DNS 리졸버에 요청: 캐시에서 찾지 못하면 DNS 리졸버에 IP 주소를 요청
4. DNS 서버 조회: 필요한 경우 루트 DNS 서버 → TLD DNS 서버 → 권한 있는 DNS 서버 순서로 조회
5. IP 주소 반환: 조회 결과를 DNS 리졸버가 받아 브라우저에 전달하고 일정 시간 캐시함

- **DNS 리졸버**: DNS 조회 요청을 받아 필요한 DNS 서버들을 통해 IP 주소를 찾아주는 역할
- **루트 DNS 서버**: `.com`, `.org` 등 최상위 도메인을 담당하는 DNS 서버의 위치를 알려줌
- **TLD DNS 서버**: 최상위 도메인에 속한 도메인의 권한 있는 DNS 서버 정보를 알려줌
- **권한 있는 DNS 서버**: 특정 도메인의 DNS 정보를 실제로 관리하며 IP 주소 등을 제공함

**DNS 조회 시 발생하는 성능 문제**: 여러 서버와 통신하면서 추가 지연이 발생하며, 특히 처음 방문한 도메인은 캐시가 없어 조회 시간이 길어질 수 있음

**DNS 조회 지연 줄이기: `dns-prefetch`**

```html
<link rel="dns-prefetch" href="//fonts.googleapis.com">
```

- 브라우저가 특정 도메인의 DNS를 미리 조회하도록 힌트를 제공
- 외부 폰트, 이미지 CDN 등 나중에 요청할 가능성이 높은 도메인에 사용
- DNS 조회만 미리 수행하며 TCP 연결이나 TLS 핸드셰이크까지 진행하지는 않음

### 2. 서버와 통신하기 위한 연결 수립

**TCP (Transmission Control Protocol)**: 클라이언트와 서버가 데이터를 안정적으로 주고받을 수 있도록 지원하는 전송 계층 프로토콜

**TCP 3-way handshake**

1. **SYN**: 클라이언트가 서버에 연결 시작을 요청
2. **SYN-ACK**: 서버가 요청을 받았으며 연결 준비가 되었다는 응답
3. **ACK**: 클라이언트가 서버의 응답을 확인하고 연결 수립 완료

→ 왕복 통신이 필요하므로 서버와의 물리적 거리가 멀거나 네트워크 상태가 좋지 않으면 지연이 커질 수 있음

**HTTPS와 TLS handshake**

- **HTTPS**: HTTP 통신에 TLS를 적용하여 데이터를 암호화하고 서버의 신원을 검증
- **TLS handshake**: 암호화 방식과 키를 설정하고 서버 인증서 등을 검증하는 과정
- 일반적인 HTTPS 연결 순서: ① TCP 연결 수립 → ② TLS 핸드셰이크로 암호화 통신 준비 → ③ 암호화된 HTTP 요청/응답 교환
- TLS 핸드셰이크에서도 추가적인 왕복이 발생하며, 왕복 횟수는 TLS 버전과 연결 재사용 여부에 따라 달라짐

**연결 수립 시 발생하는 성능 문제**

- **RTT(Round-Trip Time)**: 요청을 보낸 뒤 응답을 받을 때까지 걸리는 왕복 시간
- TCP 연결과 TLS 핸드셰이크에 여러 왕복이 필요하면 실제 데이터 교환 전부터 지연이 누적됨

**연결 수립 지연 줄이기: `preconnect`**

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
```

- DNS 조회뿐 아니라 TCP 연결과 필요한 TLS 협상까지 미리 수행
- `dns-prefetch`보다 더 많은 작업을 수행하므로 불필요하게 사용하면 네트워크 자원 낭비

**HTTP/2와 HTTP/3의 멀티플렉싱**

- 하나의 연결에서 여러 요청과 응답을 동시에 처리하는 멀티플렉싱 지원
- 요청마다 별도의 연결을 수립하는 부담을 줄일 수 있음
- HTTP/2는 TCP 기반, HTTP/3은 QUIC 기반 UDP 사용

### 3. HTTP 요청과 응답

**HTTP 통신 과정**

1. 브라우저가 서버에 HTTP 요청 전송
2. 서버가 요청을 처리하고 HTTP 응답 반환
3. 브라우저가 응답 본문의 HTML을 파싱 시작
4. HTML에 연결된 CSS, JavaScript, 이미지 등 추가 리소스를 필요에 따라 요청

**성능 문제: TTFB(Time to First Byte)**

- 요청을 보낸 뒤 응답의 첫 바이트를 받을 때까지 걸리는 시간
- 서버 처리 시간이 길거나 DB 조회가 느리면 증가, 네트워크 지연도 영향을 줌

**TTFB 개선 방법**

- 서버 코드와 DB 쿼리 최적화로 응답 대기 시간 단축
- CDN 활용으로 사용자와 가까운 서버에서 콘텐츠 제공
- HTTP 캐싱 활용으로 중복 요청 부담 감소

### 4. HTML 파싱과 렌더링

- **DOM(Document Object Model)**: HTML을 해석하여 생성한 트리로, HTML 문서의 요소와 구조를 객체 형태로 표현
- **CSSOM(CSS Object Model)**: CSS를 파싱하여 생성한 트리로, 요소에 적용할 스타일 정보를 표현
- 브라우저는 DOM과 CSSOM을 결합해 렌더 트리를 구성하고, 레이아웃과 페인팅을 거쳐 화면을 표시

**렌더링 차단 리소스(Render-blocking resources)**

1. **CSS**: 스타일 계산을 위해 다운로드·파싱해야 하므로 CSSOM이 준비되기 전에는 스타일이 적용된 화면 렌더링이 어려움
2. **JavaScript**: 동기식 `<script>`는 HTML 파싱을 중단시키고 다운로드·실행함. DOM 구조를 변경할 수 있어 브라우저가 실행이 끝날 때까지 파싱을 멈춤

**렌더링 차단 문제를 줄이는 방법**

1. **CSS 최적화**: 초기 화면에 필요한 CSS 우선 제공, 중요하지 않은 CSS는 로딩 우선순위 조정, 불필요한 스타일 제거
2. **JavaScript 로딩 최적화**

   ```html
   <script src="main.js" defer></script>
   <script src="analytics.js" async></script>
   ```

   - `defer`: HTML 파싱과 병렬로 다운로드하고, 파싱이 끝난 뒤 문서 순서대로 실행 → DOM/다른 스크립트에 의존하는 코드에 적합
   - `async`: HTML 파싱과 병렬로 다운로드하고, 완료되는 즉시 실행(실행 순서 보장 안 됨) → 독립적으로 실행 가능한 분석 스크립트 등에 적합
3. **CDN 활용**: 사용자와 가까운 서버에서 리소스를 전달해 물리적 거리에 따른 전송 지연 감소
4. **리소스 압축 및 코드 최적화**: HTML/CSS/JS 크기 축소, 불필요한 코드·주석 제거, 압축 및 번들 최적화

### 5. 주요 성능 최적화 기법 비교

| 기법 | 목적 | 주요 효과 |
| --- | --- | --- |
| `dns-prefetch` | DNS 조회 미리 수행 | DNS 조회 지연 감소 |
| `preconnect` | 서버와의 연결 미리 준비 | 연결 수립 지연 감소 |
| HTTP/2 · HTTP/3 | 하나의 연결에서 여러 요청 처리 | 연결 관리 부담 감소 |
| HTTP 캐싱 | 기존 리소스 재사용 | 중복 요청 및 다운로드 감소 |
| CDN | 사용자와 가까운 서버에서 리소스 제공 | 네트워크 지연 감소 |
| CSS 최적화 | 초기 렌더링에 필요한 스타일 우선 처리 | 렌더링 지연 감소 |
| `defer` | HTML 파싱 이후 스크립트 실행 | HTML 파싱 중단 방지 |
| `async` | 스크립트 다운로드와 HTML 파싱 병렬 진행 | 독립적인 스크립트의 로딩 부담 감소 |
| 파일 압축 | 리소스 전송 크기 감소 | 다운로드 시간 감소 |

### 6. 전체 과정 한눈에 보기

1. **URL 입력**: 브라우저에 접속할 주소 입력
2. **DNS 조회**: 도메인 이름을 IP 주소로 변환
3. **연결 수립**: TCP 연결 및 HTTPS의 TLS 핸드셰이크 진행
4. **HTTP 요청·응답**: 서버에 리소스를 요청하고 HTML 문서를 수신
5. **HTML 파싱**: HTML을 해석하여 DOM 생성
6. **CSS 파싱**: CSS를 해석하여 CSSOM 생성
7. **렌더 트리 구성 및 렌더링**: DOM과 CSSOM을 바탕으로 레이아웃과 페인팅을 수행하여 화면 표시

웹 성능을 개선하려면 특정 단계만 최적화하기보다 전체 과정을 이해하고 병목 지점을 파악하는 것이 중요하다.

### 모의 면접

**Q1. 브라우저가 URL을 입력받은 후 웹 페이지를 화면에 그리기까지 거치는 주요 네트워크 단계를 설명해 보세요.**

브라우저는 먼저 DNS 조회를 통해 도메인 이름을 IP 주소로 변환한다. 이후 TCP 연결을 수립하고, HTTPS라면 TLS 핸드셰이크를 진행한다. 연결이 준비되면 HTTP 요청을 보내 HTML 문서를 받아오고, 브라우저는 HTML과 CSS를 파싱하여 DOM과 CSSOM을 생성한다. 이를 바탕으로 렌더 트리를 구성하고 레이아웃과 페인팅을 거쳐 화면을 표시한다.

**Q2. 렌더링 차단 리소스 문제를 줄이기 위한 CSS와 JavaScript 최적화 방법에는 어떤 것들이 있나요?**

CSS는 초기 화면에 필요한 스타일을 우선적으로 제공하고, 불필요한 스타일을 제거하여 로딩 부담을 줄일 수 있다. JavaScript는 `defer`나 `async`를 사용해 HTML 파싱을 불필요하게 차단하지 않도록 할 수 있다. 또한 리소스 압축과 CDN 활용으로 다운로드 시간을 줄여 초기 렌더링 성능을 개선할 수 있다.

## Q88. 웹소켓은 어떤 경우에 사용하며, HTTP 폴링 방식과 비교했을 때의 장단점은 무엇인가요?

### 웹소켓이란?

- 클라이언트와 서버가 하나의 연결을 유지하면서 양방향으로 데이터를 주고받을 수 있는 통신 기술
- 일반적인 HTTP 통신은 클라이언트가 요청해야 서버가 응답할 수 있지만, 웹소켓은 연결이 유지되는 동안 서버도 클라이언트에게 먼저 데이터를 전송할 수 있음
- 실시간으로 데이터를 주고받아야 하는 서비스에서 사용

### 기존 방식의 한계: HTTP 폴링(Polling)

HTTP는 기본적으로 클라이언트가 요청을 보내면 서버가 응답하는 요청·응답 구조로 동작하므로, 서버에 새로운 데이터가 생겨도 클라이언트가 요청하지 않으면 즉시 전달하기 어렵다.

- **일반 폴링(Polling)**: 클라이언트가 일정한 간격으로 서버에 요청을 보내 데이터를 확인
  - 새로운 데이터가 없어도 요청과 응답이 반복되어 네트워크 자원이 낭비될 수 있음
  - 요청 주기가 길면 데이터가 갱신되어도 클라이언트에 늦게 반영됨
- **롱 폴링(Long Polling)**: 클라이언트가 요청을 보내면 서버는 새로운 데이터가 생기거나 일정 시간이 지날 때까지 응답을 보류
  - 새로운 데이터가 생기면 서버가 응답하고 클라이언트는 다시 요청을 보냄
  - 일반 폴링보다 불필요한 응답을 줄일 수 있지만, 요청과 응답이 반복되는 구조는 유지됨

### 웹소켓 통신 과정

1. **연결 요청**: 클라이언트가 서버에 웹소켓 연결을 요청
2. **핸드셰이크(Handshake)**: 서버가 요청을 확인하고 연결을 승인하면 웹소켓 연결 수립 (최초에는 HTTP 기반 핸드셰이크 → 이후 웹소켓 프로토콜로 전환)
3. **양방향 데이터 전송**: 클라이언트와 서버가 연결을 통해 자유롭게 데이터를 주고받음
4. **연결 종료**: 더 이상 통신이 필요하지 않으면 연결을 종료

- `ws://`: 암호화되지 않은 웹소켓 연결
- `wss://`: TLS를 적용한 암호화 웹소켓 연결

### 웹소켓의 장단점

**장점**

- 서버와 클라이언트가 모두 먼저 데이터를 전송할 수 있음
- 매번 HTTP 요청과 응답을 반복하는 오버헤드를 줄일 수 있음
- 연결이 유지되므로 실시간 데이터 전달에 적합함

**단점**

- 연결을 유지하기 위한 서버 자원이 필요함
- 연결 종료 및 재연결, 오류 처리 등을 고려해야 함
- 서버에서 많은 클라이언트의 연결을 관리해야 하므로 구현과 운영이 복잡해질 수 있음

### 웹소켓의 주요 사용 사례

- 실시간 채팅: 사용자와 상대방의 메시지를 실시간으로 주고받는 서비스
- 온라인 멀티플레이어 게임: 플레이어의 움직임이나 게임 상태를 실시간으로 공유
- 실시간 협업 도구: 여러 사용자의 입력이나 편집 내용을 실시간으로 공유
- 실시간 위치 공유: 사용자의 위치 변화를 지속적으로 전달하고 공유

### SSE (Server-Sent Events)

**SSE란?**

- 서버에서 클라이언트로 데이터를 지속적으로 전송할 수 있는 단방향 통신 기술
- 클라이언트가 연결을 시작하면 서버는 연결을 유지하면서 새로운 이벤트가 발생할 때마다 데이터를 전송
- 일반 HTTP 기반으로 동작하며, 브라우저에서는 `EventSource` API를 통해 사용

**SSE의 특징**

- **통신 방향**: 서버 → 클라이언트
- **연결 방식**: HTTP 연결을 유지하면서 이벤트 데이터를 지속적으로 전송
- **자동 재연결**: 연결이 끊어지면 브라우저가 자동으로 재연결을 시도함
- **데이터 형식**: 기본적으로 텍스트 기반 이벤트 스트림을 사용함

**SSE의 장단점**

장점

- HTTP 기반이므로 웹소켓보다 구현이 간단한 경우가 많음
- 브라우저의 자동 재연결 기능을 활용할 수 있음
- 서버에서 발생한 이벤트를 클라이언트에 실시간으로 전달하기에 적합함

단점

- 기본적으로 서버 → 클라이언트 방향의 단방향 통신만 지원함
- 클라이언트가 서버로 데이터를 보내려면 별도의 HTTP 요청 등을 사용해야 함
- 연결이 오래 유지되므로 서버의 연결 관리와 프록시 등의 네트워크 환경을 고려해야 함

**SSE의 주요 사용 사례**

- 실시간 뉴스 피드: 새로운 뉴스나 게시글을 클라이언트에 전달
- 주식 시세 및 실시간 알림: 서버에서 변경된 가격이나 알림을 전달
- AI 응답 스트리밍: 서버에서 생성되는 답변을 여러 조각으로 나누어 순차적으로 표시
- 작업 진행 상황 표시: 서버에서 처리 중인 작업의 진행 상태를 전달

### 웹소켓과 SSE 비교

| 구분 | 웹소켓(WebSocket) | SSE(Server-Sent Events) |
| --- | --- | --- |
| 통신 방향 | 양방향 | 단방향(서버 → 클라이언트) |
| 연결 방식 | 웹소켓 연결 유지 | HTTP 연결 유지 |
| 프로토콜 | `ws://`, `wss://` | 일반 HTTP 기반 |
| 데이터 전송 | 양쪽에서 자유롭게 전송 | 서버에서 클라이언트로 이벤트 전송 |
| 재연결 | 애플리케이션에서 직접 구현하는 경우가 많음 | 브라우저의 자동 재연결 지원 |
| 구현 복잡도 | 상대적으로 높음 | 상대적으로 낮음 |
| 주요 사용 사례 | 채팅, 게임, 실시간 협업 | 알림, 뉴스 피드, AI 응답 스트리밍 |

### 어떤 상황에서 사용해야 할까?

**웹소켓을 사용하는 경우**

- 클라이언트와 서버가 서로 데이터를 실시간으로 주고받아야 할 때
- 사용자의 입력이 서버에 즉시 전달되고, 서버의 응답도 실시간으로 공유되어야 할 때
- 예: 실시간 채팅, 온라인 게임, 협업 편집 도구

**SSE를 사용하는 경우**

- 서버에서 발생하는 데이터를 클라이언트가 실시간으로 받아 표시하면 될 때
- 클라이언트에서 서버로 보내는 데이터는 일반 HTTP 요청으로 처리해도 충분할 때
- 예: 실시간 알림, 뉴스 피드, AI 답변 스트리밍

핵심은 실시간 기능이 필요한지뿐만 아니라, 통신 방향이 어떻게 되는지 판단하는 것이다. 서버에서 클라이언트로 데이터를 전달하면 충분한 경우 SSE가 적합할 수 있고, 양방향 실시간 통신이 필요하다면 웹소켓을 고려할 수 있다.

### 모의 면접

**Q1. HTTP 폴링, 롱 폴링 방식과 웹소켓의 가장 큰 차이는 무엇인가요?**

일반 폴링은 클라이언트가 일정한 주기로 요청을 보내 새로운 데이터가 있는지 확인하는 방식이고, 롱 폴링은 서버가 새로운 데이터가 생길 때까지 응답을 보류하는 방식이다. 두 방식 모두 요청과 응답 구조를 반복한다. 반면 웹소켓은 연결을 유지하면서 클라이언트와 서버가 양방향으로 데이터를 주고받을 수 있어 실시간 통신에 더 적합하다.

**Q2. 웹소켓 대신 SSE를 사용하는 것이 더 적합한 상황은 언제인가요?**

서버에서 클라이언트로 데이터를 실시간으로 전달하면 충분한 경우 SSE가 적합하다. 예를 들어 실시간 알림이나 AI 응답 스트리밍처럼 서버가 생성한 데이터를 클라이언트에 전달하는 기능에 사용할 수 있다. SSE는 HTTP 기반으로 구현할 수 있고 자동 재연결 기능도 지원하므로, 양방향 통신이 필요하지 않다면 웹소켓보다 간단하게 구현할 수 있다.
