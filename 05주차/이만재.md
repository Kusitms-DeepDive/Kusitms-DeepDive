### Q83 웹 앱의 세션 관리와 쿠키 기반의 보안 이슈에 대해 설명할 수 있나요?

#### **책을 읽기 전 혼자 답해보기**

> CSRF는 공격자가 script 코드에 쿠키를 탈취하는 코드를 심어두는 공격을 의미하고(근데 이건 찾아보니 XSS 공격임) SameSite=Strict를 설정해두면 같은 경로의? 경우에만 쿠키가 전달돼서 방어가 가능한 걸로 알고 있다.

#### 책정리

**쿠키와 세션**

먼저 웹의 근본적인 특징 하나를 이해해야 한다. HTTP 프로토콜은 본질적으로 상태가 없는 프로토콜이다. 이걸 무상태(Stateless)라고 한다. 그래서 상태를 기억하지 못하기 때문에 요청을 보낼 때 항상 사용자 관련 인증 정보와 요청 정보를 모두 담아서 보내줘야 한다. 이를 해결하기 위한 것이 `쿠키와 세션`이다. 쿠키는 사용자의 브라우저에 저장되는 작은 텍스트 조각으로 서버가 사용자를 식별할 수 있는 단서를 제공한다. 세션은 로그인 상태나 장바구니처럼 사용자의 중요한 정보를 서버에 저장하는 공간이다.

**세션 관리**

쿠키와 세션이 어떻게 함께 동작하는지 수영장 입장 예시를 통해 알아보자.

1. 수영장(`웹사이트`) 입구에서 신분증을 보여주고 입장료를 내면(`로그인`), 직원은 여러분의 소지품을 라커(`서버의 세션 저장소`)에 보관해준다. 그리고 라커 키(`세션 ID`)가 달린 손목 입장권(`쿠키`)을 채워준다.
2. 이제 여러분은 수영장 안을 자유롭게 돌아다니며 음료를 주문하거나 시설을 이용할 수 있다. 관리자가 일일이 신분증을 다시 확인하는 대신 손목에 있는 입장권(`쿠키`)만 보고 입장이 허가된 손님이라는 걸 인지한다.
3. 라커에 맡긴 소지품이 필요하면 직원에게 손목 입장권의 라커 키(`세션 ID`)를 보여준다. 직원은 그 키에 맞는 라커를 열어 물건(`세션 정보`)을 꺼내 준다.

여기서 핵심은 민감한 개인 소지품(`개인정보`)은 안전한 라커(`서버`)에 있고 여러분의 손목에는 그 라커를 열 수 있는 열쇠만 들고 있다는 점이다. 여기서 열쇠가 `세션 쿠키`이다.

**CSRF 공격과 SameSite 쿠키 속성**

편리한 쿠키 기반 인증 방식에는 1가지 큰 약점이 존재하는데, 바로 `요청이 어디서 시작되었는지 확인하지 않고` 유효한 쿠키만 있으면 정상 요청으로 믿어버린다는 것이다.

한마디로 CSRF는 사용자의 인증 정보를 훔치는 것이 아니라 쿠키가 요청에 자동으로 포함되는 것을 이용해 악의적인 명령을 사용자 모르게 실행시키는 기법이다.

**SameSite 속성**

SameSite는 쿠키를 전송할 때 요청이 같은 웹 사이트에서 시작되었을 때만 쿠키를 보내도록 제한하는 규칙이다.

아래 3가지 옵션이 존재한다.

1. `SameSite=Strict`  
   가장 엄격한 방식으로 동일한 사이트에서 시작된 요청에만 쿠키를 전송한다.  
   CSRF 방어에는 가장 강력하지만 구글 검색 결과 클릭처럼 다른 웹사이트에서 정상으로 유입된 경우에도 로그인이 유지되지 않아 사용자 경험에 영향을 줄 수 있다.
2. `SameSite=Lax`  
   현재 대부분의 브라우저에서 `기본값`으로 사용하는 정책이다. Strict와 비슷하게 동작하지만 사용자의 탐색 의도가 명확한 GET과 같은 비교적 안전한 메서드에는 쿠키를 허용한다. 대신 POST, PUT처럼 데이터를 변경하는 요청에는 쿠키를 보내지 않는다. CSRF 공격은 대부분 `<img>`, `<form>` 제출을 통해 사용자 모르게 일어나므로 Lax는 이러한 위험을 효과적으로 차단한다.
3. `SameSite=None`  
   어떤 사이트에서 시작된 요청이든 쿠키를 항상 전송하는 방식이다.  
   이 옵션을 사용하려면 반드시 HTTPS 연결에서만 사용할 수 있으며 `Secure` 속성을 함께 사용해야 한다.

추가로 `Secure` 속성은 공용 네트워크 등에서 통신 데이터가 탈취당하는 것을 막아주는 속성이다. HTTP 밖으로는 쿠키가 전달되지 않는다.

**여기서 생긴 궁금증**

그러면 요즘 서비스는 HTTPS가 대부분인데 HTTP 밖으로만 쿠키가 전달되지 않는 건 의미가 없는 것이 아닌가?

아래 두 가지 상황에서 `Secure` 속성이 막아준다.

- **최초 HTTP 접속 찰나의 유출 방지:** 서버가 HTTPS로 리다이렉트 시켜주기 전, 브라우저가 시도하는 아주 짧은 최초의 HTTP 요청 순간에 쿠키가 새어나가는 것을 막는다.
- **SSL Stripping(강제 HTTP 전환) 공격 방어:** 해커가 네트워크를 가로채 사용자 브라우저를 강제로 HTTP 상태로 조작하더라도, 쿠키가 전송되지 않도록 원천 차단한다.

#### 모의 면접

Q1: CSRF 공격이 어떻게 발생하며 쿠키의 어떤 특성이 악용되나요?

> CSRF는 브라우저가 요청에 쿠키를 자동으로 포함한다는 부분에서 발생하는 취약점을 공격하는 기법이다.  
> 사용자의 인증 정보를 탈취하는 것이 목적이 아닌 악의적인 명령을 사용자의 권한으로 실행하는 데에 초점이 맞춰져 있다. 어디서 시작된 요청인지 확인하지 않고 유효한 쿠키만 있으면 정상 요청으로 판단해버리는 특성을 악용한다.

Q2: SameSite 쿠키 속성 Strict, Lax, None의 차이를 비교하고 각각의 장단점을 설명할 수 있나요?

> Strict는 같은 도메인인 경우에만 쿠키를 전송하는 속성이다. CSRF 공격 대응에 가장 효과적이지만 외부 사이트로 넘어갈 때 인증이 풀리는 부분에서 사용자 경험이 저해될 수 있다.  
> 
> Lax는 현재 브라우저의 기본값이며 GET과 같이 비교적 안전한 요청(서버 데이터를 변경하지 않는 요청)의 경우에는 쿠키를 전송하고 POST, PUT, PATCH와 같이 서버 데이터를 변경하는 요청의 경우에는 쿠키를 전송하지 않는 속성이다.  
> 
> None은 모든 요청에 쿠키를 전송하는 속성이며, Secure 속성이 같이 설정되어 있어야 하고 HTTPS 연결에서만 사용 가능하다.

### Q87 웹 브라우저가 웹 사이트를 렌더링하는 과정을 네트워크 관점에서 설명할 수 있나요?

#### **책을 읽기 전 혼자 답해보기**

> 사용자가 www.naver.com이라고 URL 창에 치면 브라우저는 DNS 서버에 이 이름으로 된 IP가 뭐야? 라고 물어보고 해당 IP를 받아서 접속하는 것으로 알고 있다.

#### 책정리

**1단계: 도메인 이름을 IP 주소로 변환**

컴퓨터는 naver.com 같은 사람이 읽기 편하게 바꾼 도메인을 읽지 못하고 1.2.3.4 같은 숫자 형태의 IP만 읽을 수 있다. DNS는 도메인 주소를 IP 주소로 변환해주는 인터넷의 전화번호부 역할을 한다. 루트 서버는 전 세계 도메인의 뿌리 역할을 하며 각 도메인 확장자의 위치를 알려준다. TLD 서버는 `.com` 같은 상위 도메인을 관리하며 해당 도메인에 대한 정보를 제공한다.  
권한 관리 서버는 실제 도메인의 IP 주소를 알고 있는 서버로 최종 목적지의 정확한 정보를 제공한다.  

웹 브라우저는 먼저 자신의 캐시에 해당 도메인의 IP 정보가 있는지 확인하고 최근 방문 기록에 있다면 이 단계에서 바로 반환된다. 정보가 없다면 운영체제의 캐시를, 이어서 공유기의 캐시까지 확인하고 찾지 못했다면 계약된 통신사의 DNS 서버에 질문한다. 대부분 `이 단계에서 IP 주소를 반환`받는다. 만약 통신사 DNS 서버에도 없다면 루트 DNS 서버부터 최상위 도메인 서버를 거쳐서 IP 주소를 알아낸다.

**2단계: 통신을 위한 연결 수립**

IP 주소를 알았다면 실제 데이터를 주고받는 통로를 열어야 한다. 그게 TCP이며 TCP에서는 3단계 핸드셰이크 과정을 거친다. `SYN, SYN-ACK, ACK`는 TCP 연결을 시작할 때 사용하는 제어신호다. 이 신호를 통해 클라이언트와 서버가 서로 통신 준비가 되었음을 확인한다.

1. 클라이언트가 서버에 SYN을 보내 연결을 시작하고 싶다고 한다.
2. 서버가 클라이언트에게 SYN-ACK로 응답하며 본인의 요청도 받으라고 한다.
3. 클라이언트가 서버에 ACK를 보내면 통신을 시작한다는 의미가 되어 연결이 성립된다.

**3단계: 웹 사이트 문서 요청과 수신**

연결이 수립되면 HTTP 요청을 보내 웹 사이트를 달라고 한다. 이 요청에는 어떤 경로의 자원을 원하는지, 어떤 브라우저를 사용 중인지, 쿠키 정보는 무엇인지 등 다양한 메타데이터가 함께 포함된다. 서버는 이 요청을 HTTP 응답과 함께 HTML 문서로 보낸다.

**4단계: 렌더링 과정의 병목**

웹 브라우저는 HTML 문서를 받으면 즉시 파싱하여 DOM 트리를 구성한다. 이 과정에서 CSS, 자바스크립트, 이미지 등 필요한 리소스를 추가로 다운로드하는데 이 지점에서 성능 병목이 발생한다.

**병목 현상 해결하기**

파싱 도중 `<link>`나 `<script>` 태그를 만나면 해당 리소스를 받기 위해 추가 요청을 보낸다.

이때 렌더링을 지연시키는 차단 문제가 발생할 수 있다.

CSS는 기본적으로 `렌더링 차단 리소스`이다. 웹 브라우저는 모든 CSS를 내려받고 파싱하여 CSSOM 트리를 만들기 전까지는 화면을 그리지 않는다. 어떤 요소가 어떻게 보여야 할지 모르기 때문이다.

반면 자바스크립트는 기본적으로 `파서 차단 리소스`이다. 웹 브라우저는 `<script>` 태그를 만나면 HTML 파싱을 중지하고 스크립트를 내려받은 후 실행한다. 스크립트가 DOM 구조를 변경할 수 있기 때문에 실행이 끝난 다음 안전하게 다음 단계로 넘어가는 것이다.

이러한 병목을 해결하기 위해 CSS와 자바스크립트에 대해 최적화가 필요하다.

- `CSS`: 웹 사이트 상단에 보이는 필수적인 스타일만 추출하여 HTML에 인라인으로 삽입하고 나머지 CSS는 비동기적으로 로드한다.
- `자바스크립트`: `<script>` 태그에 `defer` 또는 `async` 속성을 사용해 차단을 최소화할 수 있다.
  - `defer`는 HTML 파싱과 병렬로 스크립트를 내려받고 파싱이 모두 끝난 후에 실행한다. 가장 권장하는 방식이다.
  - `async`는 파싱과 병렬로 내려받고 다운로드가 완료되는 즉시 실행되므로 실행 순서가 보장되지 않는다. 주로 분석 스크립트처럼 다른 코드에 의존하지 않는 경우에 적합하다.

#### 모의 면접

Q1: 브라우저가 URL 입력 후 웹 페이지를 화면에 그리기까지 거치는 네트워크 4단계를 순서대로 설명할 수 있나요?

> 1단계: 도메인 이름을 IP로 변환. 컴퓨터는 사람이 읽기 편하게 만든 도메인인 www.naver.com을 읽지 못한다. 그래서 1.2.3.4 같은 형태의 숫자 IP로 변환해야 한다. 그걸 DNS가 해준다.  
> 
> 2단계: 실제 데이터를 주고받기 위해 클라이언트와 서버 사이에 TCP 프로토콜을 사용해서 연결을 진행한다. 총 3단계로 클라이언트가 서버에 연결하고 싶다는 요청(SYN)을 보내면 서버가 알겠다고 응답(SYN-ACK)을 준다. 그러면 클라이언트가 마지막으로 이제 연결을 시작하겠다는 응답(ACK)을 보내 연결이 성립된다. 이것이 3단계 핸드셰이크(3-Way Handshake)이며 SYN, SYN-ACK, ACK로 구성된다.  
> 
> 3단계: 웹 브라우저는 서버한테 웹 사이트를 달라고 요청하고, 이 요청에는 어떤 경로의 자원을 원하는지, 어떤 브라우저를 사용 중인지 등 다양한 메타데이터가 있다. 서버는 이를 처리해서 HTML 문서로 응답한다.  
> 
> 4단계: 웹 브라우저는 HTML 문서를 받으면 즉시 DOM 트리를 구성한다. 이때 `<link>`, `<script>` 태그를 만나면 해당 리소스를 받기 위해 추가 요청을 보내는데, 이때 발생하는 병목이 렌더링 차단 리소스이다. CSS는 기본적으로 렌더링 차단 리소스이고 자바스크립트는 파서 차단 리소스이다. 이를 해결하기 위해 CSS는 웹 사이트 상단에 보이는 필수적인 스타일만 추출하여 HTML에 인라인으로 삽입하고 나머지 CSS는 비동기적으로 로드한다. 자바스크립트는 `<script>` 태그에 `defer` 또는 `async` 속성을 사용해서 병목을 해결할 수 있다.

Q2: 렌더링 차단 리소스 문제를 줄이기 위한 CSS와 자바스크립트 최적화 방법에는 어떤 것들이 있나요?

> CSS에서는 웹 사이트 상단에 필수적으로 필요한 스타일만 추출하여 HTML에 인라인으로 삽입하고 나머지 CSS는 비동기적으로 로드한다.  
> 
> 자바스크립트는 `defer`, `async` 속성이 있는데, `defer` 속성의 경우 HTML 파싱과 병렬로 스크립트를 내려받고 파싱이 끝난 후에 스크립트를 실행한다. `async` 속성의 경우 파싱과 병렬로 스크립트를 내려받고 다운로드가 끝난 즉시 실행하기 때문에 실행 순서를 보장하지 못한다.

### Q88 웹소켓은 어떤 경우에 사용하며, HTTP폴링 방식과 비교했을 때 장단점은 무엇인가요?

#### **책을 읽기 전 혼자 답해보기**

> 웹소켓의 경우 실시간으로 응답을 주고받아야 하는 채팅과 같은 경우에 사용된다. HTTP 폴링의 경우 서버에 요청을 계속 보내야 하지만 웹소켓의 경우 한 번 연결하면 추가로 요청을 보내지 않는다?

#### 책정리

**기존 방식의 한계: HTTP 폴링**

과거 웹소켓이 없었을 때 실시간 통신을 흉내 내는 방법으로 HTTP 폴링을 사용했다.

HTTP는 기본적으로 클라이언트가 서버에 요청을 하고 서버는 응답만 할 수 있는 단방향 구조이다. 폴링을 활용하면 클라이언트는 계속 서버에게 요청을 하고 서버는 변경이 없음에도 같은 결과를 계속 내려주는 형태를 띤다. 이때 서버는 과한 요청으로 부하가 걸리게 된다.

이를 개선한 방식이 롱폴링으로 클라이언트가 한 번 요청을 보내면 서버는 즉시 응답하지 않고 변경 사항이 있을 때까지 연결을 유지한 후 변경 사항이 있을 때 응답하는 방식이다.

**웹소켓의 등장**

이런 비효율을 해결하기 위해 2011년 HTML5 표준으로 등장한 게 웹소켓이다. 웹소켓은 클라이언트와 서버 간에 하나의 TCP 연결을 계속 유지하며 양방향으로 자유롭게 데이터를 주고받을 수 있는 통신 프로토콜이다. 먼저 클라이언트 요청으로 통신이 시작되고 서버와의 핸드셰이크 과정을 거쳐 기존 HTTP 프로토콜에서 웹소켓 프로토콜로 전환된다. 일단 연결이 맺어지면 매번 새로운 요청을 할 필요 없이 서버와 클라이언트가 하나의 통로를 통해 실시간으로 양방향 데이터를 주고받을 수 있게 된다.

**웹소켓과 SSE**

웹소켓과 함께 알아두어야 하는 SSE는 클라이언트가 데이터를 `수신`만 하면 되는 상황에서 사용된다. 이때 웹소켓을 사용하는 것은 과한 선택일 수 있다. SSE는 클라이언트가 서버에 구독을 요청하고 그게 승인되면 서버로부터 단방향으로 업데이트된 데이터를 수신할 수 있는 방식이다.

#### 모의 면접

Q1: HTTP 폴링, 롱폴링 방식과 웹소켓의 가장 큰 차이는 무엇인가요?

> HTTP 폴링은 서버가 변경 사항이 없음에도 클라이언트 요청에 응답을 하기 때문에 서버에 과한 부하가 걸린다. 이를 개선하기 위해 생긴 것이 HTTP 롱폴링으로 클라이언트 요청에 서버가 매번 응답하는 것이 아닌 실제 데이터가 변경될 때까지 연결을 유지하다가 변경 후 응답하는 방식이다.  
> 
> 2011년 HTML5 표준으로 등장한 웹소켓의 경우 최초 서버와 연결된 이후에는 따로 요청을 보내지 않고 실시간으로 데이터를 주고받을 수 있다는 점이 앞서 말한 HTTP 폴링, 롱폴링 방식과의 가장 큰 차이점이다.

Q2: 웹소켓 대신 SSE를 사용하는 것이 더 적합한 상황은 언제인가요?

> 웹소켓은 실시간 양방향 통신으로 클라이언트와 서버가 실시간으로 주고받아야 하는 경우(예: 채팅 등)에 적합하다. 단, 클라이언트가 서버의 최신 데이터만을 필요로 하는 경우 단방향 통신인 SSE가 더 적합하며 웹소켓은 과한 선택일 수 있다.
